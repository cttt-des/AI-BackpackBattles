## 1 bundle 是什么、怎么用

`native_sim_cpp/` 是从 AI-BackpackBattles-0.5.0 抽出的独立 bundle：
GDScript 3.6 → C++20 转译内核（`native_sim/gen/` 663 脚本 + `gd_rt.*` 运行时 + `engine_wrapper.cpp` 引擎封装），
经 ctypes 由 `native_sim/sim.py` 驱动。物品注册表来自 `assets/gd_core_runtime.json`（519 物品，与主仓资产逐字节一致，已比对）。

```bash
# Windows 构建（本台账新增 native_sim/build_windows.py；macOS/Linux 用原 build.py）
python native_sim/build_windows.py            # MinGW g++ -O3 -std=c++20 -ffp-contract=off，产物 libgdcore.dll
python native_sim/build_windows.py --clean    # 全量重编（20 编译单元，本机 ~197s）

# 冒烟
python -X utf8 -c "..."   # 见 README.md（seed=1001 truth 阵容）

# 三闸检验（本台账新增 tools/check_three_gates.py）
python -X utf8 native_sim_cpp/tools/check_three_gates.py --gates 123
# 事件流逐位对拍（本台账新增 tools/_cmp_events.py）
python -X utf8 native_sim_cpp/tools/_cmp_events.py run570_r18 ...            # REG9
python -X utf8 native_sim_cpp/tools/_cmp_events.py --expand run704507_...    # expand 语料
```

要点：
- `sim.py` 的 `pack_side` 接受神谕 case 字典（预平铺 occupied/collision/affected）或 v3/v4 嵌套阵容；
  `run_one/run_batch` 的 `BattleOptions` 旗标与主仓引擎参数一一对应（seed/round_id/below_master/label_rng/
  native_activation_order/reseed_after_player_character/formal_ev_gate/max_time）。
- **Windows 构建坑**：MinGW 的 as/ld 无法向中文路径写产物（GBK 乱码 → "No such file or directory"）——
  中间产物必须落 ASCII 临时目录（`%TEMP%/native_sim_obj`），再由 Python 复制回 bundle；g++ 诊断是 GBK，
  按字节捕获再宽松解码，否则 UnicodeDecodeError 会吞掉真实报错。
- 原预编译 `libgdcore.dylib` 是 macOS arm64 的，Windows 上必须重编。

## 2 旗标映射（与主仓引擎语义对应）

| 场景 | 旗标 | 依据 |
|---|---|---|
| 闸1（GDCoreEngine 默认路径，seed_gate 口径） | `native_activation_order=False, reseed_after_player_character=False, max_time=180, below_master=False` | GDCoreEngine 默认 `startBattle(preordered=False)`＝内核 ctx.rng.shuffle；GDScript 默认 max_time=180 |
| 闸2/3（神谕对齐路径，verify_oracle 口径） | `native_activation_order=True, reseed_after_player_character=True, max_time=90, below_master=True, formal_ev_gate=25000` | CoreContext(seed) 注入＋真链 seed(S)→shuffle×2→sort 直通；verify_oracle 对两语料均硬编码 `below_master=True`（tools/verify_oracle.py:518） |

- `native_activation_order=True` 时 C++ 侧 `bind_battle(seed)→shuffle×2→godot_sort_custom_items`，
  实测与真 Godot 留档终序**双侧逐位一致**（含 run1160 的 54+10 大平局组——gd_rt 的 Godot introsort 复刻是忠实的；
  注意主仓 gd_core_py 的 `_sort_custom` 是稳定排序，`_rt.py:729` 有「已知偏差」注释，两者对平局的处理不同，
  但 verify_oracle 路径用 recorded 终序直通，不经过该函数）。
- **⚠️ 主仓账本 convention 文本有陈旧记载**：`alignment_expand.json` 的 convention 写「below_master: false」，
  但 verify_oracle 的 py 腿实际硬编码 True，且归因实验（§5.1）实证 True 才复现账本。**建议主仓自行修订该文本**
  （本台账不代改）。
- 主仓 verify_oracle 的 np 系键控注入（np21/np22/np43/np44/np46 六表）**全部为空**（净化重录后退役），
  rng_state 注入经四臂实验实证**不承载语义**（A=B 臂全同）——native 无需实现。

## 4 事件计数口径（−1 的来历）

py 基线/神谕账本的 event_count 在 `run()` 结束后取值，含 `emit_combat_end` 追加的 **1 条合成行**
（simulator/gd_core_engine.py:1515→624，id=-1、type=combat_end）；native 钩子只数内核 `logEvent`。
故 **native event_count = 账本 oracleEvents − 1**（9 场+60 场逐场验证无一例外）。
`events_bytes`（py 侧事件 JSON 字节数）native 不导出事件流、不可比，闸1 已注明。

## 5 分歧与发现（如实记录）

### 5.1 已修：pack_side 的 charge_frame 取值（bundle 装配层，非内核）

- **现象**：闸2 首轮 run1160_r18 内核分叉（native 991 ticks vs 神谕 1093）；
  事件流对拍首分叉 = py id4 有 Resistor heat(amount=3)、native 没有（电荷接错物品）。
- **根因**：主仓引擎 `_build_side` 恒用**运行时数据按朝向的 charge_frame**
  （gd_core_engine.py:1434，np25 P3-3 旋转系原点；如 Battery rot90→(1,-1)），
  而 bundle `sim.py pack_side` 对预平铺夹具条目用 `(0,0)`。电荷落点公式
  `top_left + rot(cell) − chargeFrame[fd]` 整体偏移 → 电气阵容（Battery/Resistor/Charge Splitter）
  从开战批量起整条链错位。
- **修复**（sim.py，Python 侧，无需重编 DLL）：新增 `_charge_frame_of(key, rotation)` 恒取运行时真值。
- **验证**：run1160 修复后 415 行事件流逐位一致；闸2 9/9、闸3 59/60 均在修复后达成。
- 同族风险记录：bundle 自带的 `native_sim/test_parity.py` 的 py 臂同样用 `(0,0)` charge_frame
  （且其 `_sort_custom` 是稳定排序），其「bit-exact parity」结论对电气阵容/平局阵容不可信，使用时注意。

### 5.2 未修（native 侧内核真分歧）：run101354_r14_o101073_r14

- **现象**：闸3 唯一红场。胜负正确（opponent），native 事件 656 vs 神谕 670，ticks 1079 vs 1130。
- **定位**：终序与真 Godot 留档**双侧逐位一致**（非终序问题）；首分叉事件 #5（id=5）：
  native 的 Battery#4 激活后立即触发 Holy Collar 的 block+1/regen+2（事件 parent=4，挂在 Battery 链下），
  py 同位置是下一个 Battery 激活（py 侧 Holy Collar 事件在其后另行出现）。属**触发链/事件父子时序**类分歧。
- **处置**：按用户指令**不修，如实记录**。影响面 1/60 场，胜负不受影响。

### 5.3 其他发现（不修，备忘）

- bundle 自带 `simulator/gd_core_engine.py` 是**旧版副本**（无 p_stats/p_gem_lens/rng_state 等对齐参数）；
  `_attrib_expand.py` 归因实验曾因此误导入。bundle 的 C++ 内核不受影响（gen/ 转译自 .gd 真源）。
- 夹具 gems 数组长度系统性 = descr sockets − 1（60 场 96% 物品）；主仓 py 腿用夹具长度（np24）、
  native 用 descr sockets。四臂实验实证该差异**不改变**抽查场次的结局（state 直写/装配差异被
  开战边界吸收），但**不排除**对宝石遍历敏感的物品脚本有影响——与 run101354 的关联未排查（不修）。
- 归因实验过程中的环境干扰：另一会话 `build_cython` 占用 gd_core_py 的 pyd 导致 `DLL load failed`
  ——改用 `GD_PURE_PY=1 + tools/_purepy_arm` 纯 py 臂绕开。

### 5.4 归因实验（60 场初跑 58 红的定谳，tools/_attrib_expand.py 四臂）

| 臂 | 配置 | 结果（3 抽样场） |
|---|---|---|
| A | verify_oracle 复刻（bl=True+gl+state） | **== 账本**（959/616、432/115、991/2666） |
| B | A 去 rng_state | == A（state 注入不承载语义） |
| C | A 换 below_master=False | **== native**（ticks 全同，事件差 1 合成行） |
| D | A 去 gems 槽长 | == A（槽长口径不改变结局） |

⇒ 60 场初跑的 58 红是**闸旗标映射错**（按账本 convention 文本选了 False）；改 True 后 59/60。
native 内核与主仓内核在这些场上逐场同局。

## 6 事件流对拍工具与口径（tools/_cmp_events.py）

- native 侧：`engine_wrapper.cpp` 新增调试导出（默认关，单线程 run_one 前调
  `gd_sim_set_dbg_events(1)`）：`gd_sim_dbg_event_count()` / `gd_sim_dbg_event_line(i)` /
  `gd_sim_dbg_order(side, phase, n)`。每条 logEvent 记一行 canonical：
  `ts=f:<双精度位型>|type|id|tgt|parent|origin|params`（dict 键字典序、float 位型 hex、
  DamageSource/EventType 的 Int origin 按 py keyword 映射）。
- py 侧：神谕腿留档 `output/oracle/{align,align_expand}/py/<case>/events.json`（去 id=-1 合成行）。
- 口径归一：宝石事件 py 记宿主（kind=gem）↔ native 记宝石物品 identifier+ownerType=7 → 双方归一 `o:gem`；
  DamageSource py keyword ↔ native Int（98 unhealing/99 fatigue/102 regen/103 vampirism/104 spikes/
  108 poison/22 battlerageend）→ 双方归一 `o:dmgsrc:<kw>`。
- 除上述归一外**逐字符相等**（含 ts 的 IEEE 双精度位型）。

## 7 与主仓台账的关系（G2 视角，供参考不代写）

- 本 bundle 的 C++20 内核（约 6.6k 行 gd_core 转译 + 505 物品脚本转译）在与主仓内核的对照中
  表现出**逐位级语义等价**（事件流、终局、RNG 链位），仅 1/69 抽验场存在未修分歧。
  这对主仓 G2（整场 C++/Rust 重写）是一个正面可行性证据：**转写路线能保住确定性**，
  且「数据结构 C 化」的语义风险可用本台账的工具链（事件流对拍）检测。
- 性能未做严谨基准（本机调试导出开启、非隔离窗口、g++ -O3 无 PGO）；门面上 native 单场
  与主仓编译态同量级（~200-950 ms/场 vs 主仓 mean 212.5 ms），**未显示出优势**，勿据此刻推 G2 收益。
