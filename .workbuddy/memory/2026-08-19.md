## ★ 物品行为全量提取：GDScript → 可执行行为 DSL（4% → 94.2%）

### 背景
用户要求"自行解决"模拟器还原痛点（物品行为覆盖率仅 4%、无真值 oracle 等），并确认游戏代码已完整解包——所有机制都能在源码里找到。方案：**以 decompiled GDScript 为唯一真值源，把每个物品脚本的方法体转译成调用引擎 API 的 Python 函数，由引擎在对应钩子执行**。

### 交付
- `simulator/extract_items.py`（新）：GDScript→Python 行为转译器。
  - 扫描 Items/ + Exclusive/ + Gems/（499 个脚本），DB 的 `script` 字段优先，否则文件名匹配，品质变体（Chipped/Flawed/…Ruby、Strong X）去前缀映射到基类。
  - 转译规则：GDScript 控制流本就是 Python（if/for/return 直接可用）；差异处理 = `self.`→`_item.`、裸 `self`→`_item`、`getP1()`→`get_p(0)`（**索引从 0 起**）、`getP_m/getChance/getGemPower`、方法名 camelCase→snake_case（METHOD_RENAME 大字典）、视觉行剥离（preload/$/ObjectPool/animation/connector/Color/Vector2/buffTimer/.start( 等）、`for i in <int>`→`_range_or_value`、`.empty()/.push_back()/.erase()/.size()`、`var x: =` 推断类型、无初始化器变量按声明类型给默认值（Dictionary→{}、Array→[]）。

### 关键修复（都是从诊断中抓出来的真 bug）
1. **`character()` 语义**：GDScript `character()` 是方法，引擎里 `Item.character` 是**属性**（方法叫 `character_`）→ 转译映射 `character`→`character_`，且我自己写的 Item 方法里 `self.character()` 全改为 `self.character`（28 处）。
2. **preDealDamage_early 时序**：原版 Character.gd **先掷命中再调钩子**（CursedDagger 靠 `damageRes.hasHit()`），引擎原先在命中前调→ 随机减益永远不触发。已调整顺序。
3. **getP1() = getP(0)**：GDScript 索引从 0 开始，最初映射差 1。
4. **`var x: = 0` 推断类型**、**无初始化器 `Dictionary` 变量默认 `{}`**。
5. **`for i in <int>`**（GDScript 特有）→ `_range_or_value` 助手。
6. **实例变量默认值**：类级 var 在 Python Item 上不存在 → prepare 前按 instance_vars 置 0，onready 表达式走 _onready_init。
7. `BuffType` 需在 item.py 模块级导入 + 行为全局命名空间注入。

## ★★ 邻接联动 + 宝石（阶段2完成）

### 方案与真值源
- **邻接**：真值源 = 每物品 tscn 场景 `CollisionMap.tile_data`（PoolIntArray，每3个int=[格,瓦片ID,0]）。
  瓦片ID（Item.gd Tiles 枚举）：2=Extension(bag占格)、3=Collision(占格)、4=Affected(Primary)、6=AffectedSecondary。
- **宝石**：真值源 = Gem.gd（socket→宿主、getGemMode→weapon/armor/inventory、prepareWeapon/Armor 分发）。

### 关键发现（坐标系）
1. **40px 精细 tile → 80px 背包格 = 坐标 //2 合并**！CursedDagger 2 个纵向 tile 合并为 1 格。占格=unique(归一化(旋转后碰撞格)//2)。
2. tscn 格 (x,y)：x=横向=背包 col、y=纵向=背包 row，映射 (row,col)=(y+row, x+col)（之前行列颠倒导致药水联动不生效）。
3. lineup (row,col)=占格左上角（GUI 导出 min(rs)/min(cs)）。
4. **同名物品多份**：_place_items 不能用 {id:entry} 字典（互相覆盖）→ Item._lineup_entry 按序挂载。
5. 脚本覆盖的 affected（Potion 上方1格、BagofStones 上方直线）在 _script_affected_cells 实现，与 tscn affected 叠加。
6. canAffect 执行已提取的行为函数；has_type 需兼容 Type 枚举 int；gainsStack 检查 buff 相关。

### ★★ 冷却机制全面核对（271 个有 cd 物品实战验证）
- 原版真相（Item.gd）：`adjustCooldown()` = cd × randf_range(**0.95, 1.05**)（±5%，对手低段位 0.975~1.05）；递减 `triggerTime -= delta * getSpeed()`；`trigger()` 用 `triggerTime += iterationCooldown` 累加补偿超时；60Hz 物理帧；武器 `doCooldownEffect` 先 `useStamina()==Sufficient` 才攻击。
- 模拟器全部对齐 ✓；验证脚本 tools/verify_cooldowns.py（首触发 ∈ [cd×0.95, cd×1.05]，271/271 通过）。

### ★★★ 重大 bug：passive 机制错误（176 个物品受影响）
- **症状**：Pot/Cauldron/Book of Ice/Ukulele/Ultima/Thornburst 等 7+ 物品首触发偏离 ±5%（Pot 15s→13.7s、Book of Ice 2.8s→3.0s…）。
- **根因**：build_data.py 把 CSV `gain` 列提取成 `passive` 并在 prepare 时 `_apply_passive` 给角色加 heat/cold/mana/spikes。但原版 gain 列 = `descriptor.gainedStacks`（ItemBook.getFlags）——是 **canAffect 联动判定标志**（如 DeathScythe.canAffect 检查 `gainsStack(Stack.Poison)`），**不是 prepare 给 buff**！且带脚本物品（Pot.gd doCooldownEffect 已 giveHeat）被**双重叠加**，heat/cold 提前生效→冷却被错误速度修正。
- **修复**：build_data.py passive 恒 None（附注释说明 gainedStacks 语义）；item.py 删除 _apply_passive 调用与方法；DB 清理 176 个 passive 字段。
- **验证**：271/271 冷却通过；全物品激活 462 崩溃=0 告警=0（补 DamageResult.triggerOnAttacked/triggerOnHit 等 camelCase 别名修 Mercury Elemental）；8阵容×双向 56 场 ok=56 err=0 warns=0；exe 重建 64.7MB 冒烟通过。

## ★★★ RNG 语义修正：冷却固定 + 同帧先后（用户确认的游戏行为）

- **用户主张**：RNG 只影响同一帧物品的先后，不对冷却时长产生显著影响。
- **验证**：exe 字节级确认原版 adjustCooldown = cd×randf_range(0.95,1.05)（0.95@25741168 与 1.05@25741176 double 相邻=参数对）；但用户确认游戏实际行为 = 冷却固定、同帧先后。
- **修改**：`Item.adjust_cooldown()` 改为返回 `get_cooldown()`（固定，无 ±5%）。同帧先后由 combat.ordered_items（shuffle + TriggerPriority 排序，含 RNG）决定。
- **效果**：4 把匕首同一时间戳齐射（3.52/3.52/3.52/3.52），间隔精确 cd（3.5s）；不同 cd 物品各自固定时间触发。
- **速度修正保留**（原版核心）：heat/cold/speed 加成仍生效（Pot 触发给 heat→speed 1.12→冷却变快；Oil Lamp/Ruby Whelp/Dancing Dragon onCombatStart 给 heat→首触发=cd/speed）。
- **验证 v2**：tools/verify_cooldowns.py 改为"状态链期望（trigger_time/get_speed）vs 实战"对照，271/271 通过。
