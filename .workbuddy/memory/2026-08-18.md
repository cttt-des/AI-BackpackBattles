### 密钥获取（最终方案：运行时 hook）
- **真实密钥**：`8671424952511006d39f4c9e918f821391e2b06a80d946d693fb8757154ce849`（已存 tools/script_key.txt）
- 密钥在 exe 中是**混淆存储**的，运行时由 GDEC 解密函数重建为明文 32 字节。
- KeyDot 提取的 `8671...5292...` 是混淆 blob，**不是**真实密钥（第 5/12 字节不同：92→51、5e→91）。
- **获取方法**：DLL 注入 hook 游戏内 `FileAccessEncrypted` 的 GDEC 处理函数入口（RVA 0x1621820，含 "GDEC" magic 比较的那个函数），入口处抓寄存器参数 → 扫描 this 对象偏移 0x20 处的 Vector<uint8_t> → 得密钥。实现：`C:/tmp/bb/grabkey.c`（绝对跳转 hook：`mov rax,imm64; jmp rax` 12 字节，避免 rel32 溢出）+ `inject_cap.c`（CREATE_SUSPENDED 创建→先注入→等 hook 装好→ResumeThread）。
- 踩坑：hook 0x16223b0（错误位置，是错误处理代码非入口）→ calls=0 抓不到；rel32 jmp 会因 handler 与 target 距离超 2GB 溢出崩溃 → 必须用绝对跳转。
- 本机 exe 验证锚点（版本漂移会变）：GDEC magic 比较在 RVA 0x1621cca 附近；GDEC 处理函数入口 RVA 0x1621820。

### GDEC 容器格式（decrypt_gde.py 已确认）
```
[4 "GDEC"][4 version=1][16 MD5(plaintext)][8 LE plain_len][AES-256-ECB 密文]
```
- **AES-256-ECB，无 IV！** 密文从 offset 32 开始（16 对齐），解密后明文以 `GDSC\x0d\x00\x00\x00` 开头，MD5 校验。
- （之前一直误用 CBC+IV 假设，导致密钥验证失败——格式错了。）
