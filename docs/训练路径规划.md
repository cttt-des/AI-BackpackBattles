## 1. 问题定义

### 1.1 任务（2026-11-12 用户界定，以此为准）

```
输入：H = 当前持有的物品多重集（含包），|H| 随回合增长（R1 约 9 件 → R18 约 48 件）
输出：S ⊆ H（上哪些）+ 每件的 (位置, 朝向)
目标：给定回合/对手分布下，胜率最大

不做：任何获取决策（商店、合成、路线、职业选择）
```

**三个硬性界定：**

1. **输入是"当前拥有"，不是"全游戏可获得"**
   ⇒ 职业专属 / Unique / shop 可达性**都不是决策面**。物品在输入里就说明已拿到。
2. **只做摆盘**，不碰商店与获取。
3. **调用时机**：每回合一次，或持有物品变化时一次
   ⇒ 要**快**；且上一次摆盘是天然初值。

### 1.2 形式化

```
max_{B, I, layout}   E_{o ~ D_ladder}[ win(B, I, layout, o) ]

s.t.  B ⊆ (H ∩ 包池),   B 在 9×7 = 63 格上互不重叠
      I ⊆ (H \ B),      每格 ∈ ⋃_{b∈B} occ(b),  I 之间互不重叠
      Σocc(I) ≤ Σocc(B) ≤ 63

f(B, I) = Σ 包属性 + Σ_{i∈I} 物品属性×(1 + Σ_{b∋i} k_b) + 涌现协同（必须模拟）
```

- `Σ_{b∋i} k_b` 同时依赖 B 和 I ⇒ **两层不可解耦**（`assign_bonuses()` 已实现）
- B 和 I 都取自 H ⇒ **子集选择**，不是从 519 件里挑

### 1.3 约束紧度：全程都紧（**不存在"早期随便摆"**）

实测各回合容器预算（corpus 抽样中位数）：

| 回合 | 件数 | 包数 | **容器格** | 物品需格 | 充裕度 |
|---|---|---|---|---|---|
| R1 | 9 | 3 | **14** | 11 | +21% |
| R5 | 20 | 7 | 28 | 25 | +11% |
| R12 | 37 | 15 | 50 | 45 | +10% |
| R18 | 48 | 19 | **63** | 61 | **+3%** |

**R1 只有 14 格容器却要摆 9 件；R18 有 63 格要摆 48 件。两端都紧。**
⇒ 全程都是「取舍 + 布局」联合优化（用户明确）。

**动作权重应随回合调整：**

| 动作 | 早期 R1–R6 | 后期 R13+ |
|---|---|---|
| 换包（改容器层） | **主力** | 中等 |
| 跨包交换 | 弱 | **主力**（密铺，单挪无解） |
| 减物品 | 强 | 中 |

### 1.4 取舍是搜出来的，不是学出来的

```
H（持有列表）→ 采样子集 S → 摆盘 → 引擎实测胜率 → 保留最优 S*
```

**任意子集都能模拟** ⇒ 不需要"玩家当时舍弃了谁"这种标签。

**数据缺口只影响一件事**：H 的分布。真实阵容的"已摆集合"是玩家筛选后的结果，
比真实持有池更优 ⇒ 会**低估**取舍压力。对策：注入额外物品放大压力。

### 1.5 两条路径都要

| 路径 | 场景 | 起点 | 要求 |
|---|---|---|---|
| **冷启动** | 首次调用 / 物品大改 | 无（或解析分启发） | 限时给出可用解 |
| **增量** | 小改（±1–2 件） | 上一次摆盘 | 快，且不劣于冷启动 |

**增量必须做失效检测**（被删的物品可能是某条加成链的一环）：
`loss = base_wr(旧) − base_wr(冷启动) > 阈值` ⇒ 直接冷启动，不要硬改。

> ⚠️ 当前所有实验都是冷启动，**增量路径完全未实现**。

## 2. 空间规则（结论速查）

| 规则 | 结论 | 证据 |
|---|---|---|
| 两层结构 | 层0（63 格）只放包；层1（包格）才放物品 | `oracle/Core/Inventory.gd:717, 395-408, 621-627` |
| 面积转换率 | **1:1**，27/27 包 extension == collision | `trainer/p0_verify_report.json` R1 |
| 包不扩容 | 包占 K 格就给 K 格；空位 `63−Σ包格` 闲置 | §1.3 实测 |
| 包不叠包 | 包格各自独立 | 用户确认 |
| 物品可跨包 | `getItemsInside` 按格查、按物品去重 | `CoreGrid.py:192-202` |
| 加成可叠加 | 被 N 个包覆盖 = 吃 N 次 | 用户确认；`BAG_SPECS` 27 包普查 |
| 无禁区 | `inventorySize=Vector2(9,7)` 纯矩形 | `Inventory.gd:37-38` |
| 坐标系 | 9 列 × 7 行（**不是 7×9**） | 同上 |

**包的三重价值**：① 容器（占几格给几格）② 加成覆盖（跨包叠乘）③ 自身属性。

**包池 27 件**（占格 1–9）。可得性表（`oracle/Sheets/CSV/ItemData.csv` shop 列）
仅作背景知识，**不进入候选空间构造**——输入即权威。

### 3.2 吞吐（**三种口径，别混用**）

| 口径 | 数值 | 用途 |
|---|---|---|
| 单场延迟（R19 大阵容，37–60 件） | **143–936 ms** | 性能优化目标 |
| **纯战斗并行（8 worker）** | **24.6 场/s**（200 场/8.1 s） | 评估器预算 |
| 端到端数据采集（P3，含特征/写盘） | **7.0 场/s** | 数据集生成预算 |

```
每候选评估（100 对手 × 2 种子 = 200 场）≈ 8 s
双种子族确认 ⇒ ×2 ≈ 16 s
P3′ 1200 样本 × 60 候选 = 72,000 场 ≈ 3 小时（端到端口径）
```

> 历史错误已作废：旧版「36–66 ms/场」错 10–30 倍（性能台账 §4 记 15–30 倍）；
> 早期「1.49 场/s」错在每 job 重载数据。

### 3.3 确定性

1690 例三向对齐 + 60 例精选回归集；编译腿与纯 py 腿**逐位一致**（P2 Pass 3）。

**跨场状态泄漏已修复（2026-11-12）**：根因 `_bind_battle` 在常规路径从未被调用，
全局随机流与 gid 台账回落进程级单例。修复后同配置完全可复现
（同进程 4/4、跨进程 24/24 同指纹）。详见 [引擎跨场状态泄漏修复.md](引擎跨场状态泄漏修复.md)。

**重要**：修复后**泄漏噪声归零，但采样噪声仍在** ⇒ 双种子族确认仍必要（§6.2）。

## 5. 已判否（**不要重走**）

| 做法 | 为什么否 |
|---|---|
| 直接训练网络输出摆盘 | 无法保证约束、无法保证最优、出错无法归因 |
| 用人类对局学绝对胜率 | 学人类分布而非最优；标签混杂对手强弱与运气 |
| 分层解耦（先选包再装箱） | 两层强耦合（§1.2） |
| **单步邻域搜索** | **【已实测】效应 ≈ ±0.02，与噪声同量级** |
| 旧 placer 形状类置换 | 【已实测】不动覆盖关系的位移 Δ≡0 |
| v4 平铺形直传引擎 | `_build_side` 得空表 ⇒ 双侧空场疲劳战（症状：CRN Δ≡0） |

**旧 CNN 的失败模式**（`ai/placer.py` 文件头）：
「代理分在真值阵容上饱和到 0.94+ 而引擎实测只有 0.0–0.6」。
根因：学的是**绝对值**，而搜索需要**反事实增量**。

## 6. 当前已知的未解决问题

### 6.1 单步邻域效应 ≈ 噪声【已实测】

真实摆盘的单步邻域效应 **≈ ±0.02**，与评估噪声同量级。

**这不是搜索无效，是分辨率极限。** 已验证的对策：**加大邻域**（复合 LNS，
Pass 4 拿到 +0.030/+0.050）。但复合空间开发极浅——每血统只接受 1 步就撞耐心闸。

### 6.2 噪声分两种（修复后仍未归零）

| 类型 | 修复前 | 修复后 |
|---|---|---|
| **泄漏噪声**（跨场状态污染） | ±0.005 起 | **0**（完全可复现） |
| **采样噪声**（换 seed_base 的抽样波动） | 混在一起 | 仍在，16 对手×2 seeds 下 |Δ₁−Δ₂| ≈ 0.02 |

**结论：双种子族确认仍必要。** 它防的不再是"引擎不确定"，而是"单次 200 场的抽样运气"。
**降本要靠序贯检验，不靠砍确认。**

### 6.3 权重表未校准【推断值】

`layout_rules.WEIGHTS` 是推断初值，只影响"先测谁"，不影响终评正确性。

P3 首次给了实测锚点：speed **+0.007/条**、potion_amp **+0.003**、crit **0.0**
（`trainer/p3_model.json:edge_weights`）。与 Pass 4 接受的候选（+0.030/+0.050）量级吻合，
但样本仅 360、分段不稳（LOBO Spearman +0.136，−0.083~+0.430）。

### 6.4 H 的分布偏差

真实阵容的"已摆集合"是玩家筛选后的结果 ⇒ 比真实持有池更优 ⇒ **低估取舍压力**。
注入多少物品才够、注入分布怎么定，尚未定。

## 7. 后续路径（**本文重点**）

> 原则：先拿便宜的信息，再花钱。**先做能暴露"问题长什么样"的实验，再谈模型。**

### 7.1 五项工作，按建议顺序

| 序 | 工作 | 目的 | 成本 | 阻塞 |
|---|---|---|---|---|
| **①** | **回合分层实验** | 看清早期/中期/后期是不是**不同的问题** | **1 h** | 无 |
| **②** | **包集合动作消融** | 换包是连锁最强的动作，现在权重最低、从未单测 | 2–3 h | 无 |
| **③** | **真人标尺样本**（3–5 套） | 唯一的**绝对标尺**（见 §7.4） | 低（等玩家） | 无 |
| **④** | **P3′ 复测** | 学习预筛是否真能省预算 | 1–2 天 | 需 ①② 结论 |

### 7.2 ① 回合分层实验（**先做这个，最便宜**）

**问题**：R1 只有 14 格容器，R18 有 63 格——搜索行为是否完全不同？

**做法**：用同一套 `p2_search.py`，只换基线阵容的回合，各跑 3 血统 × 6 迭代。

| 分层 | 回合 | 容器格 | 预期观察 |
|---|---|---|---|
| 早期 | R1–R5 | 14–28 | **换包动作**能否拿到大增益 |
| 中期 | R8–R12 | 38–50 | 取舍与布局并重 |
| 后期 | R15–R18 | 59–63 | 密铺，跨包交换为主 |

**判据**：若早期的最优动作组合与后期**显著不同**（接受的动作类型分布差异 >50%），
则**必须做分档策略**；若相似，说明一套动作通吃。

**产出**：`trainer/p2_search_report_round{1,5,12,18}.json` + 一张动作接受率表。

### 7.3 ② 包集合动作消融（**可能藏大增益**）

**为什么值得做**：

- 换包会改**容器层 + 加成域 + 自身属性**，三样全变 ⇒ 效应量应远大于单步
- 但在 Pass 4 的动作菜单里**权重最低**，从未被单独评估
- §1.3 已指出：**早期（容器只有 14 格）换包应该是主力动作**

**做法**：固定其他动作不变，把换包权重从当前值提到 30–50%，跑 3 血统；
对照当前基线。同时单列**减物品动作**（用户明确关心的"少上几件换拓扑"，现在权重 1/12）。

**判据**：换包主导的搜索，在池 A 上的最终 wr 比当前基线高 ≥0.02。

### 7.4 ③ 真人标尺（**唯一能回答"够不够好"的东西**）

**不是训练标签**（3–5 个样本训不了任何东西）。用途是三个判断：

| 用途 | 怎么用 | 价值 |
|---|---|---|
| **验证合法性判定器** | 专家不可能摆出非法摆盘 ⇒ 若判非法，是**我错了** | 防规则错 |
| **校准解析分权重** | 专家摆盘在解析分排第几 ⇒ 判断方向对不对 | 免去训模型 |
| **专家 vs 搜索** | 搜索能否打赢高手 ⇒ **决定后续是否继续投入** | 最高 |

**现状**：只知道搜索 0.965 > 人类**中位** 0.690。中位不是高手。

**数据格式与插件方案**：[摆盘标尺样本采集_开发任务书.md](摆盘标尺样本采集_开发任务书.md)

### 7.6 ⑤ 增量路径（产品化必需）

当前所有实验都是冷启动。用户实际用法是**每回合调用**，必须有增量。

**设计要求：**

1. 以上一次摆盘为初值
2. **失效检测**：若被删物品是某加成链的一环，旧摆盘战力可能已崩 ⇒ 回退冷启动
3. 判据：`loss = base_wr(旧) − base_wr(冷启动) > 阈值` ⇒ 冷启动
4. **速度要求**：每回合总耗时应 < 30 s（按 24.6 场/s，约 700 场预算）

**待回答**：旧摆盘能省多少搜索？物品变化后布局可复用多少？（全未实验）

## 8. 验收闸（所有实验通用）

| 闸 | 标准 |
|---|---|
| 1. 合法性 | 候选过 `layout_rules.check_layout` |
| 2. 复现性 | 同 (候选对, seed_base) 重跑必须完全一致（修复后应满足） |
| 3. 双种子族 | `Δ₁ > +0.02 且 Δ₂ > 0` 才接受（**采样噪声仍在，必须保留**） |
| 4. 泛化 | 池 A 优化，池 B/C 验收（§9） |
| 5. 回合覆盖 | 结论必须标注适用回合（§7.2 之后） |
| 6. 数据来源 | 报任何数字都要给 `trainer/*.json` 路径 + 命令 |

**池构造**：池 A = `[target, target+200]` 优化用；池 B = `[target−200, target]` 验收；
池 C = 全分布泛化。**优化用 A，验收用 B/C**，防单池过拟合。

**四指标**：平均胜率 / 对手间 std / 最差对手 / 对高分对手胜率。

## 9. 开放问题

1. **包加成强度量级**：speed +0.007/条是单锚点，样本仅 360，需扩大复核。
2. **"少上物品换拓扑"的净收益**：动作权重 1/12，**从未单列实验**（用户明确关心）。
3. **极端策略**（全铺包、只放 3 件）是否合法最优：搜索没探索到。
4. **天梯分布是否按职业分层**：7 职业差异可能很大，当前对手池未分层。
5. **上分加权**：当前用平均胜率；实际目标是"对高分对手胜率"，池 A 部分体现但未显式加权。
6. **储物箱策略**：`x≥9` 不参战，是否存在"故意放储物箱"的战术？
7. **H 分布注入多少**：注入 10% 超容够不够？30%？影响"训出来的取舍能力有多泛化"。
8. **每回合要多快**：当前一次搜索 24 次评估 ≈ 3 分钟，对每回合调用可能太慢。
   是否降到 50 对手 + 单种子族？或用解析分主排序、只少量实测？
