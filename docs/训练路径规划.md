## 1. 问题定义

### 1.1 任务

输入：玩家**拥有的全部物品**（含包）。
输出：一套摆盘（上哪些包、放在哪、上哪些其它物品、放在哪、朝向）。
目标：**在天梯真实分布上期望胜率最大**。

用户明确要求：
- 物品上/不上**由模型判断**（不是预设好的集合）；
- 最优是对**天梯真实分布**最优，用 `database/corpus.sqlite` 的抓取池子模拟多种池子；
- 允许"少上几件物品，腾出空间获得更好的拓扑邻接关系"这种可能性。

### 1.2 形式化【推断】

```
max_{B, I, layout}   E_{o ~ D_ladder}[ win(B, I, layout, o) ]

s.t.  B ⊆ 包池(27 件),  B 在 7×9 基础网格上互不重叠
      I ⊆ 物品池,      每格 ∈ ⋃_{b∈B} occ(b),  I 之间互不重叠
      Σocc(I) ≤ Σocc(B) ≤ 63

目标函数组成：
  f(B, I) = Σ 包自身属性
          + Σ_{i∈I} 物品属性 × (1 + Σ_{b∋i} k_b)     ← k_b = 包 b 对物品 i 的加成
          + 涌现协同（解析算不出，必须模拟）
```

**关键：`Σ_{b∋i} k_b` 同时依赖 B 和 I，所以两层不可解耦。**

## 2. 空间规则（这是全项目最容易错的地方）

### 2.1 两层结构【已核实】

```
层 0（基础层）  7×9 = 63 格
   只能放包。包与包之间不能重叠。包不能叠包。
   没有"基础包"，这 63 格本身不提供物品放置能力。

层 1（容器层）  C(B) = ⋃_{b∈B} occ(b)  ⊆  层 0
   只有这一层能放物品。物品之间不能重叠。
   物品的每一个占格都必须落在 C(B) 内，否则"浮空"→ 被踢进储物箱，不参战。
```

**证据：**
- `oracle/Core/Inventory.gd:717` — `isCellEmpty(cell) = cell in bagCells and not cell in filledCells`
- `oracle/Core/Inventory.gd:395-399` — `isItemFloating()`：任一占格不在 `bagCells` 即为浮空
- `oracle/Core/Inventory.gd:401-408` — `pushFloatingItemsToStorage()`：浮空即踢出背包
- `oracle/Core/Inventory.gd:621-627` — `addItemCells`：包写 `bagCells`，普通物品写 `filledCells`
- `oracle/Core/Inventory.gd:102` — `isPotentialSpace(cell) = isInventoryCell(cell) and not cell in bagCells`

Python 侧对应：`gd_core_py/gd_core/CoreGrid.py:171`（`isCellEmpty`）、`:294`（`addItemCells`）。

### 2.2 面积转换率 = 1:1【已核实】

包占 K 格 → 容器层正好 K 格 → 物品最多占 K 格。

```
Σ|occ(物品)| ≤ Σ|occ(包)| ≤ 63
```

**包不扩容，它只决定"63 格里哪些格可用"。** 空位 `63 − Σocc(包)` 永远闲置。

⚠️ 这条推翻了早期方案里"包是容器增量"的错误模型。

### 2.3 包不能叠包，物品可以跨包【已核实 + 用户确认】

- 包不叠包（用户明确）。
- 物品**可以横跨多个包**：`Bag.getItemsInside()` 用 `getItemsInCells(self.occupiedCells)`，
  按物品去重、只要有一格落在包格上就算"在包内"。
  证据：`gd_core_py/gd_core/CoreGrid.py:192-202`、`gd_core_py/gd_core_items/Bag.py:178-188`

### 2.4 加成可叠加【已核实 + 用户确认】

用户原话："所有它在的包里面都可以生效，也就是按你的举例会加三次。"

代码路径：每个包在自己的 `onCombatStart` / `prepare` 里遍历 `getItemsInside()`，
对 `canApplyEffect(item)` 为真的物品施加加成。多个包各自独立执行 ⇒ **同一物品被 N 个包覆盖就连吃 N 次加成**。

### 2.5 包的三重价值【推断】

| 价值 | 来源 | 可否解析计算 |
|---|---|---|
| ① 容器 | 占几格就给几格 | ✅ 直接数 |
| ② 加成 | `canApplyEffect` 匹配的物品，按包各自施加 | ⚠️ 可算，但依赖覆盖关系 |
| ③ 自身属性 | 包自己的 `descr.params` | ✅ 直接读 |

### 2.6 包池全集（27 件）【已核实】

数据源：`assets/gd_core_runtime.json` 的 `items`，按脚本继承链判定 `isBag()`。
注意：包脚本分布在 `gd_core_py/gd_core_items/` 与 `gd_core_py/gd_core_items/Exclusive/` **两个目录**，
只用非递归 glob 会漏掉 Exclusive 里的 20 个。

| 占格 | 数量 | 物品 |
|---|---|---|
| 1 | 1 | Protective Purse |
| 2 | 1 | Fanny Pack |
| 3 | 1 | Stamina Sack |
| 4 | 12 | Box of Prosperity, Leather Bag, Portable Altar, Potion Belt, Puzzlebag J/L/S/T/Z, Random Loadout Bag, Relic Case |
| 6 | 7 | Bag of Giving, Berserker Bag, Engineer Box, Holdall, Puzzlebox, Ranger Bag, Scholar Bag, Sewing Case |
| 8 | 3 | Engineer Bag 2, Storage Coffin, Toolbox |
| 9 | 2 | Fire Pit, Vineweave Basket |

已知的 `canApplyEffect` 覆写【已核实】：

| 包 | 加成条件 |
|---|---|
| FannyPack | `toItem.hasCooldown() and not toItem.isBag()`（所有带冷却的武器） |

## 4. 已判否路线（**不要重走**）

### 4.1 旧 CNN 胜率代理模型的失败模式【实测】

遗留代码 `ai/`（model.py / train.py / placer.py / gen_dataset.py / encoding.py）已从仓库退库（提交 `03ae1f6c`），
但代码仍在本地，权重与数据集已清理。

`ai/placer.py` 文件头记载的实测事故：

> "代理分在真值阵容上会饱和到 0.94+ 而引擎实测只有 0.0–0.6，只按代理分交付等于在盲区爬坡"

**根因诊断【推断】**：那个双塔 CNN 学的是"这种阵容过去赢了多少"，是**绝对值回归**；
而搜索需要的是"把 A 从 (2,3) 挪到 (2,4) 会怎样"，是**反事实增量**。后者是对 1–3 格的扰动，
绝对值模型在训练分布外完全无分辨力。

### 4.2 三条已判否的做法

| 做法 | 为什么否 |
|---|---|
| **直接训练网络输出摆盘** | 无法保证约束（摆不下），无法保证最优，出错无法归因 |
| **用人类对局学绝对胜率** | 学的是人类分布而非最优；标签混杂了"对手弱"和"运气"，同阵容在不同对手下标签矛盾 |
| **分层解耦（先选包再装箱）** | 两层强耦合（§2.4 / §2.5），先选包会使物品布局整体失效 |

### 4.3 旧 placer 的动作空间作废

`ai/placer.py` 的主动作是"形状类内的物品循环置换"，保持占位多重集不变。
在两层模型下这个动作**收益极低**——它不改变容器层 C(B)，也不改变加成覆盖关系，只改影响格。

真正有效的动作在 §7.2 重列。

## 5. 目标函数与评估设计

### 5.1 不要只报一个数

建议同时给出四条指标：

| 指标 | 含义 | 用途 |
|---|---|---|
| 平均胜率 | 对池子的期望 | 主指标 |
| 胜率方差 | 稳健性 | 避免"忽强忽弱" |
| 最差对局胜率 | 鲁棒性 | 避免被特定对手克制 |
| 对高分对手胜率 | 上分力 | 实际天梯目标是越级赢 |

### 5.2 对手池构造【推断】

用户要求"对天梯真实分布最优"，建议用**固定池子组合**而非动态采样：

- 池 A：`rating ∈ [当前, 当前+200]`，抽 200 个终盘阵容（上分目标）
- 池 B：`rating ∈ [当前-200, 当前]`，200 个（保底）
- 池 C：全分布抽 200 个（泛化检验）

**优化用 A，验收用 B/C**，防止对单一池子过拟合。

### 5.3 共同随机数（CRN）降方差【推断，需先验证】

同一对手、同一 seed 下比较两个候选摆盘，两者共享全部随机流。
理论上 Δ 的方差远小于独立采样，能把"需要几百场才能测出 0.02 差异"降到个位数场次。

**这是整个训练路径的性能前提，必须在 P1 阶段先验证。**

### 5.4 解析目标 + 模拟精评 的两级结构【推断】

```
一级（免费）：解析算 A 类（无条件属性）+ B 类（覆盖加成型属性，给定布局可精确算）
二级（付费）：引擎实测算 C 类（涌现协同），用于终评与排序
```

旧模型的问题就是把 A/B/C 塞进一个网络，浪费容量在确定性关系上。

## 6. 未验证假设红名单（**动工前必须逐条验证**）

### 【未验证 1】|occ(b)| 是否真的等于该包提供的容器格数？

游戏里包登记进 `bagCells` 的是 **`extensionCells`**（`oracle/Items/Item.gd:728`，Tile 类型 2），
但运行时资产 `assets/gd_core_runtime.json` 的 `rot` **只有 `collision` / `affected` / `charge_frame`，没有任何 `extension` 字段**（实测 0 件物品有）。

引擎 `simulator/gd_core_engine.py:_place_of` 用 `collision` 同时当 `occupied`。

**若某包的 Extension 格数 ≠ Collision 格数，则本文件 §2.2 的面积会计全错，装箱求解器整体失效。**

验证方式：对 27 个包逐一从 `oracle/Items/*.tscn` 的 CollisionMap 里数 Tile 类型 2 的格数，与 `collision` 格数比对。

### 【未验证 2】corpus 中"同坐标同 gid 多条记录"与"包不能叠包"矛盾

实测：`run_id:a8bfb956-…` 在 `round_no=18` 的 `(x=9,y=6)` 出现 **10 条 `gid=24`**，
`(x=9,y=7)` 出现 9 条。在"包不能叠包 + 物品不能重叠"下这不可能。

可能解释（均未验证）：
- (a) `x,y` 是**锚点**而非占格，不同物品锚点可重合；
- (b) corpus 提取时有重复记录；
- (c) 存在某种多层嵌套/堆叠机制我们还没看到。

**这直接决定对手池里的阵容是否合法摆盘。若池子非法，整个评估体系失真。**

### 【未验证 3】Exclusive/ 目录下的包实战是否可得

`Bagtacular` / `Engineer Bag 2` / `Berserker Bag` / `Scholar Bag` / `Random Loadout Bag` / `Bag of Giving` / `Extra Bags` 等位于 `gd_core_items/Exclusive/`，rarity 全为 5。
需确认它们是"特定职业专属"还是"普遍可得"，否则包池有效性打折扣。

### 【未验证 4】加成是开局一次性还是每 tick 生效

`FannyPack.onCombatStart` 是一次性；但其它包有的在 `prepare`、有的在 `onAffectedItemInsideAdded`。
需逐包确认作用时机，否则目标函数里 k_b 的权重会算错。

### 【未验证 5】物品能否跨包（每格只要都有包垫即可）

代码上 `getItemsInCells` 按格查 `filledCells`，看起来支持跨包；用户也确认"物品可以跨包"。
但需确认**游戏层是否有额外限制**（例如物品必须完整落在"某一个"包的范围内才算入包）。

### 【未验证 6】63 格是否有禁区

`ai/encoding.py:82` 硬编码 `ROWS, COLS = 7, 9`，`CoreGrid` 本身不限尺寸。
需确认正式游戏中是否有不可放置的格（边界/固定障碍）。

## 7. 分阶段路线

> 原则：**先建立可判定、可测量的基座，再上学习。**
> 每个阶段结束都有明确的"继续/放弃"判据。

### P0 · 形式化基座（1–2 天）

**产出：**

1. **双层合法性判定器**
   ```
   legal(B, I) ⟺ 包在 63 格上互不重叠
               ∧ ∀i∈I: occ(i) ⊆ ⋃occ(b)
               ∧ I 之间互不重叠
   ```
2. **加成指派提取器**
   ```
   assign(B, I) → { i: [(b, kind, k_b), ...] }
   ```
   必须能处理跨包（一个物品对应多个包）与全局协同（Bagtacular 类）。
3. **失败诊断器**（返回原因，不是 bool）：
   - `NO_CONTAINER` — 某格没有包垫
   - `SHAPE_FIT` — 容器层有空位，但形状塞不进
   - `OCCUPIED` — 格位被冲突物品占用
   - `NO_SYNERGY` — 摆得下但吃不到任何加成
4. **解析目标函数**（不含模拟部分），即 §1.2 里 A/B 两类。

**为什么先做这个：** 没有它，后续所有模型输出的阵容都无法验证"能不能真摆出来"。
旧方案跳过这一步，直接训练，是这个路线最大的工程缺陷。

**继续判据：** 判定器对 corpus 里 1000 个真实终盘阵容的合法率。若 <50%，
说明 §6【未验证 2】是真问题，先解数据口径。

### P1 · 评估器（2 天）

**产出：**
1. 对手池构造（分层采样，§5.2）
2. CRN 配对比较器
3. 多指标报告

**先验证 CRN 是否真的降方差**（这是全路径的前提）：
取 20 个真实阵容，各做 10 个随机扰动，对 100 个对手用 CRN 比较 Δ。
若扰动间 Δ 的标准差 < 0.03 ⇒ 通过。

**继续判据：** CRN 使单次模拟即可分辨 0.02 级别的差异。
若不通过 ⇒ 回到"解析目标主导 + 少量精评"路线，弱化搜索。

---

### P2 · 纯搜索基线（3–4 天，**关键对照**）

**不做任何学习**，只用引擎实测排序。

外层：包组合 + 包布局（贪心 + LNS 大邻域）
内层：物品集合 + 物品布局（装箱 + 局部搜索）
中层：指派优化（把物品挪到能吃到更多加成的包上，近似最大权重匹配）
三层交替迭代。

**有效动作空间（取代旧 placer 的置换动作）：**

| 动作 | 影响 | 连锁性 |
|---|---|---|
| 换包 | 容器层 + 加成域 + 自身属性 全变 | 极强，物品布局可能全废 |
| 加/减包 | 同上，且改容量 | 强 |
| 加/减物品 | 改占格 + 改加成对象 | 中 |
| 物品挪位 | 改跨包数 + 拓扑邻接 | 中 |
| 包挪位 | 改形状匹配，影响整体可行性 | 强 |

**继续判据：** 纯搜索的最佳摆盘在池 A 上击败**人类终盘阵容的中位水平**。
- 若击败 ⇒ 证明"搜索有效"，可以进入 P3 用学习加速（提升搜索效率）
- 若未击败 ⇒ **学习不是当务之急**，应先查评估口径或动作空间是否残缺

**这个对照必须做，否则无法判断学习是否值得。**

### P3 · 学习加速（在 P2 证明有效之后）

只学解析算不出的部分：

1. **学差分偏好**：同一基准摆盘的扰动前后 Δ 胜率，不是绝对胜率
2. **输入必须是完整布局**（因为两层耦合，不能只看物品集合）
3. 三个可学对象：
   - 包的边际价值（条件于已有 B）
   - 物品的边际价值（条件于 B）
   - 覆盖边权（物品-包-加成）
4. 作用：在搜索中做**初筛**，把千级候选压到几十个再精评

**继续判据：** 学习初筛 + 精评的组合，在相同模拟预算下优于纯搜索。

### P4 · 自举（可选）

## 8. 与模拟器性能优化的关系

**这不是两条线，是同一条链。**

- 单场 11.8 ms 已可支撑大规模实测，但 R18 大阵容预计 30–60 ms
- 模拟器再快 2 倍 ⇒ P2/P4 的迭代次数翻倍
- 正在进行的 A 类优化（`docs/性能优化下一步规划.md` §C，消除调用次数冗余）直接服务本路径

因此：**训练路径不阻塞于性能优化，但性能优化会显著加速它。**

## 附：一句话总结

> 这是一个**带覆盖加权的双层装箱 + 子集选择**问题。
> 包不是容器增量，而是"把 63 格里某几格变成可用"的开关；
> 它的价值 = 容器面积 + 加成覆盖 + 自身属性，三者耦合，不能分层解耦。
> 之前的失败源于**用绝对值回归模型代替反事实搜索**。
> 正确顺序：先建可判定的可行性基座（P0），再建可信的评估器（P1），
> 再做纯搜索对照（P2），最后才考虑学习加速（P3）。
