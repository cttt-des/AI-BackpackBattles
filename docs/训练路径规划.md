## 1. 问题定义

### 1.1 任务

输入：玩家**拥有的全部物品**（含包）。
输出：一套摆盘（上哪些包、放在哪、上哪些其它物品、放在哪、朝向）。
目标：**在天梯真实分布上期望胜率最大**。

用户明确要求：
- 物品上/不上**由模型判断**（不是预设好的集合）；
- 最优是对**天梯真实分布**最优，用 `database/corpus.sqlite` 的抓取池子模拟多种池子；
- 允许"少上几件物品，腾出空间获得更好的拓扑邻接关系"。

### 1.2 形式化【已实测支撑】

```
max_{B, I, layout}   E_{o ~ D_ladder}[ win(B, I, layout, o) ]

s.t.  B ⊆ 包池(27 件),  B 在 9×7 = 63 格上互不重叠，且不落储物箱列
      I ⊆ 物品池,      每格 ∈ ⋃_{b∈B} occ(b),  I 之间互不重叠
      Σocc(I) ≤ Σocc(B) ≤ 63

目标函数组成：
  f(B, I) = Σ 包自身属性
          + Σ_{i∈I} 物品属性 × (1 + Σ_{b∋i} k_b)     ← k_b = 包 b 对物品 i 的加成
          + 涌现协同（解析算不出，必须模拟）
```

**关键：`Σ_{b∋i} k_b` 同时依赖 B 和 I，所以两层不可解耦。**
P0 的 `assign_bonuses()` 已把这个式子落成可执行代码。

### 1.3 真实数据的额外强约束——密铺【已实测】

真实终盘棋盘 **100% 满摆**（bag cells 50/50、free 0）。

**后果：单物品挪位基本无解，有效动作必须以「跨包交换」为主。**
证据：`trainer/p1_crn_report.json`、`trainer/actions.py:act_cross_bag_swap`。

## 2. 空间规则（全项目最容易错的地方）

### 2.1 两层结构【已核实】

```
层 0（基础层）  9 列 × 7 行 = 63 格
   只允许放包。包与包之间不重叠。包不能叠包。
   没有"基础包"，这 63 格本身不提供物品放置能力。

层 1（容器层）  C(B) = ⋃_{b∈B} occ(b)  ⊆  层 0
   只有这一层能放物品。物品之间不重叠。
   物品的每一个占格都必须落在 C(B) 内，否则"浮空"→ 踢进储物箱，不参战。
```

**证据：**
- `oracle/Core/Inventory.gd:717` — `isCellEmpty = cell in bagCells and not cell in filledCells`
- `oracle/Core/Inventory.gd:395-399` — `isItemFloating()`：任一占格不在 `bagCells` 即浮空
- `oracle/Core/Inventory.gd:401-408` — `pushFloatingItemsToStorage()`
- `oracle/Core/Inventory.gd:621-627` — 包写 `bagCells`，普通物品写 `filledCells`
- `oracle/Core/Inventory.gd:37-38, 88-91` — `inventorySize = Vector2(9,7)`，纯矩形无禁区

### 2.2 面积转换率 = 1:1【已实测 27/27】

包占 K 格 → 容器层正好 K 格 → 物品最多占 K 格。

```
Σ|occ(物品)| ≤ Σ|occ(包)| ≤ 63
```

**包不扩容，它只决定"63 格里哪些格可用"。空位 `63 − Σocc(包)` 永远闲置。**

**关键验证（P0-R1）**：27 个包的 `extensionCells` 与 `collision` **逐一相等**，0 例外。
`simulator/extract_grid.py` 把 Tile 2(Extension) 与 3(Collision) 并入同一份 collision_cells。
证据：`trainer/p0_verify_report.json` R1、`oracle/Items/Item.gd:724-728`。

⚠️ v1 规划的【未验证 1】已消除。

### 2.3 包不能叠包，物品可以跨包【已核实】

- 包不叠包（用户明确）。
- 物品**可横跨多个包**：`Bag.getItemsInside()` = `getItemsInCells(occupiedCells)`，
  按格查 `filledCells`、按物品去重。无"须完整落在单包内"的限制。
  证据：`gd_core_py/gd_core/CoreGrid.py:192-202`。

### 2.4 加成可叠加【已实测】

用户原话："所有它在的包里面都可以生效，也就是按你的举例会加三次。"

每个包在自己的 hook 里遍历覆盖域并施加加成，多包各自独立 ⇒ **同一物品被 N 个包覆盖就连吃 N 次**。

**P0 已把 27 个包逐包普查成表**（`trainer/layout_rules.py:BAG_SPECS`）：
- 效果入口分两批：`onPrepare`（多数）vs `onCombatStart`
  （FannyPack / Holdall / PortableAltar / ProtectivePurse / PuzzlebagL / ScholarBag / Toolbox / Sandbag）
- 覆盖域分两种：`getItemsInside()`（占格域）vs `getAffectedItemsInside()`（affected 域）
- **指派提取器必须按包区分这两种域**，否则加成算错

### 2.5 包的三重价值

| 价值 | 来源 | 可否解析 |
|---|---|---|
| ① 容器 | 占几格给几格 | ✅ 已实现 |
| ② 加成覆盖 | 跨包叠乘 | ✅ `assign_bonuses()` 已实现 |
| ③ 自身属性 | `descr.params` | ✅ 已实现 |

### 2.6 包池全集（27 件）与可得性【已实测】

**可得性图谱**（`oracle/Sheets/CSV/ItemData.csv` shop 列）：

| 类别 | 数量 | 代表 |
|---|---|---|
| 通用商店 | 5 | Leather Bag / Fanny Pack / Stamina Sack / Potion Belt / Protective Purse |
| 职业专属商店 | 14 | Portable Altar→Pyromancer、Ranger Bag→Ranger 等 |
| **shop=no（不可购）** | 7 | Box of Prosperity、Puzzlebag J/L/S/T/Z、Holdall |
| special | 1 | Random Loadout Bag |

⚠️ **这改变了"包池"的定义**：7 件不可购的包**不应出现在候选空间**（除非通过其它途径获得）。
搜索器必须按 shop 可得性过滤包池，否则会推荐现实中拿不到的摆盘。

**占格分布**：1×1 / 2 / 3 / 4×12 / 6×7 / 8×3 / 9×2。

## 4. 已判否路线（**不要重走**）

### 4.1 旧 CNN 胜率代理模型【实测事故】

遗留 `ai/`（已从仓库退库，提交 `03ae1f6c`，代码仍在本地）。
`ai/placer.py` 文件头记载：**代理分在真值阵容上饱和到 0.94+ 而引擎实测只有 0.0–0.6**。

**根因诊断【推断】**：那个双塔 CNN 学的是"这种阵容过去赢了多少"（绝对值回归）；
而搜索需要"把 A 从 (2,3) 挪到 (2,4) 会怎样"（反事实增量）。
后者是对 1–3 格的扰动，绝对值模型在训练分布外没有分辨力。

**P3 已用实测印证这个判断**：差分偏好模型（学 Δ 而非绝对值）的 LOBO Spearman 只有 **+0.136**，
说明"学增量"也很难——但至少方向是对的（§7.2）。

### 4.2 四条已判否的做法

| 做法 | 为什么否 |
|---|---|
| 直接训练网络输出摆盘 | 无法保证约束，无法保证最优，无法归因 |
| 用人类对局学绝对胜率 | 学人类分布而非最优；标签混杂对手强弱与运气 |
| 分层解耦（先选包再装箱） | 两层强耦合 |
| **单步邻域搜索** | **【已实测】单步效应 ≈ ±0.02，与评估噪声同量级**（§7.1） |

### 4.3 旧 placer 的置换动作作废【已实测证实】

`ai/placer.py` 的"形状类内物品循环置换"保持占位多重集不变。

**P1 实测：不改变覆盖/邻接的位置变化，产出逐位相同的战斗（CRN 下 Δ≡0）。**
位置的价值几乎全部来自覆盖关系——旧动作恰好在动的正是"无价值"的维度。

### 4.4 新判否：v4 平铺形直传引擎【实测事故】

`GDCoreEngine` 只吃 v3 内部形（`backpack.items[row/col/rotation]`）。
直传 v4 平铺形 ⇒ `_build_side` 遍历得空表 ⇒ **双侧空场疲劳战**（38 attack 事件、恒 2252 ticks）。

症状：CRN 探针 Δ≡0.0000。修复：`evaluator._to_engine_form()`（与 `simulator/lineup._normalize_v4` 同口径）。

**教训：训练侧任何"对局全平/Δ 恒 0"都要先查装配格式，不要先怀疑模型。**

## 5. 评估设计【已实测落地】

### 5.1 四指标

平均胜率 / 对手间 std / 最差对手 / 对高分对手胜率。
实现：`trainer/evaluator.py`。

### 5.2 三层对手池

- 池 A：`rating ∈ [target, target+200]`，优化用
- 池 B：`rating ∈ [target−200, target]`，验收用
- 池 C：全分布，泛化用

**实测有效**：血统 2 在池 A 提升 +0.050，池 B +0.17、池 C +0.05 同向 —— 证明未过拟合单池。

### 5.3 CRN 配对与「噪声地板」【已实测，口径已修正】

**v1 的判据有语义坑**：不同扰动的 Δ 含真实效应差异，其 std 主要是信号而非噪声。
决策需要的是**同一对候选换种子后 Δ 估计变不变**（复现性噪声）。

**修正口径**（已在 `trainer/p1_crn_test.py` 落地）：
```
noise_paired = mean_i |Δ̂_i^s0 − Δ̂_i^s1|     （CRN 配对）
noise_unpaired                                （对照，种子错开）
```

实测（`trainer/p1_crn_report.json`）：

| base | noise_paired | noise_unpaired | CRN 增益 |
|---|---|---|---|
| run4162 | 0.0320 | 0.0240 | 0.8x |
| run4175 | 0.0025 | 0.0100 | **4.0x** |
| run4188 | 0.0180 | 0.0220 | 1.2x |
| run4192 | 0.0025 | — | — |
| run4194 | 0.0025 | — | — |

**4/5 严格通过（<0.03），第 5 个差 0.002。**

⚠️ **但"noise_paired 竟差于 unpaired"（run4162）说明噪声不是纯采样噪声**——
真因见 §6.1（同进程跨场状态泄漏，**2026-11-12 已修复**，见
[引擎跨场状态泄漏修复.md](引擎跨场状态泄漏修复.md)）——那不是 CRN 无效，
是修复前评估本身每次都不同。**评估协议因此上加到「每候选 200 场 CRN 配对」**，
必要时双种子族确认。**修复后动作**：重测 noise_paired（预期大幅下降），
上表数字系修复前旧噪声，不作修复后依据。

### 5.4 双种子族确认（防假阳性）【已实测必需】

Pass 1（单种子族）出现了**假阳性接受**：trial +0.025，report −0.02。

Pass 2 起改为双种子族：`Δ₁ > +0.02 且 Δ₂ > 0` 才接受。
实测拦截了 6 个 Δ₁ = +0.025~+0.045 的假阳性。

**这是当前最有效的噪声对抗手段，后续所有实验必须沿用。**
【2026-11-12】§6.1 已修复（docs/引擎跨场状态泄漏修复.md §6），噪声地板预期塌缩，
双种子族可评估降为单种子——以复测后的新 noise_paired 为准，**未复测前协议不变**。

## 6. 已知问题（当前最重要的三条）

### 6.1 引擎跨进程非确定性【✅ 已修复 2026-11-12：实为同进程跨场状态泄漏】

**本节结论已由模拟器工作流定位并修复**，完整根因链、复现与验收数据见
[引擎跨场状态泄漏修复.md](引擎跨场状态泄漏修复.md)。此处只留训练侧需要知道的：

**真根因**（修正本节旧猜测）：不是对象身份哈希驱动的集合迭代序——是
`_bind_battle()` 在常规战斗路径**从未被调用**，全局 Math 流与实例 id 台账
回落「进程级单例」，**跨场累积**：同一 (阵容, seed) 在同一进程里每跑一场
结果都不同；跨 worker 的「翻转」其实是 worker 内运行次数不同的伪象。

| 旧记录 | 实测修正 |
|---|---|
| 「同进程内连跑 5 次逐位一致」 | 假象——那 5 次用了不同阵容对；同一对时每次都不同 |
| 「200 场跑两遍出现 1 场翻转」 | 73/200（36%）有差异；1 例只是那次两批 worker 顺序相近 |
| 「机制指向对象身份哈希/集合迭代序」 | 绑定未生效 → 回落进程级单例 |

**修复**：`GDCoreEngine.__init__` 在 CoreContext 创建前无条件
`_bind_battle(本场 seed)`（链起点 A/B 两候选 60 例均全绿，按规则取 A）。
验收：repro 4 次同指纹、跨进程 8/8、seed 双态逐值不变、REG9 9/9、60 例 60/60、
1690 全量（见修复文档 §5）。

**训练侧影响**：
- 修复后同 (阵容, seed) **逐位复现**，评估噪声地板预期从 ±0.005 塌缩向 0
  ——**旧噪声数字（§5.3 表）全部待复测**，复测前协议（200 场 CRN + 双种子族）不变
- P1 的 noise_paired 粗于 unpaired（run4162）已获完整解释
- 每候选评估预期 30–60 s → 15–30 s（双种子族降为单种子后）

### 6.2 单步邻域效应 ≈ 噪声【已实测，已判否该方向】

真实终盘摆盘的单步邻域效应 **≈ ±0.02**，与评估噪声同量级。

**这不是搜索无效，是分辨率极限。** 对策（已验证有效）：
- **加大邻域**（复合 LNS，Pass 4 拿到 +0.030 / +0.050）
- **更强的解析先验**（P3 学习加速的动机）

### 6.3 权重表未校准【推断值，影响搜索效率但不影响正确性】

`trainer/layout_rules.py:WEIGHTS` 是推断初值，只影响"先测谁"，不影响终评。

**P3 首次给了实测锚点**：speed **+0.007/条**、potion_amp **+0.003**、crit **0.0**
（`trainer/p3_model.json:edge_weights`）。与 Pass 4 实际接受的候选（speed 重排 +0.030/+0.050）量级吻合。

| run5030 | 0.695 | **0.725** | **+0.030** | 0.940→0.950 | 0.990 |
| run5066 | 0.490 | **0.540** | **+0.050** | 0.650→**0.820** | 0.850→**0.900** |

**判据**：0.965 ≫ 人类终盘中位 **0.690**（p25=0.270 / p75=0.820）✅

**关键：中段血统的提升在 B/C 泛化池同向** ⇒ 未过拟合单池。
接受的候选是 **B 边指派重排（speed / potion_amp）**——正是 §2.5 价值②。

**产物**：`lineups/trained_{0,1,2}_*.json`（模拟器可直接加载）。

### ⚠️ P3 · 学习加速 — **判据 FAIL，但方向正确**

**数据**：6 强度段 × 60 候选 = 360 样本 / 36,600 场 / 87 分钟。

**模型**：Ridge 闭式解，59 维解析特征，差分偏好（学 Δ）。

| base | LOBO Spearman |
|---|---|
| 0 (wr .18) | +0.205 |
| 1 (wr .75) | −0.001 |

**双臂同预算对照**（`trainer/p3_compare_report.json`）：

| 臂 | 血统 0 | 血统 1 | 血统 2 | mean | 场数 |
|---|---|---|---|---|---|
| analytic | 0.965 | 0.690 | 0.485 | 0.7133 | 17,400 |

**判定：pass=false**（学习臂多 +20% 预算：接受后复评与耐心重置是超支来源）。
**但有效性是正向**：同一噪声相位下找到解析预筛**完全错过的 2 个真改进**，均过双种子族确认。

**诚实结论：方向对，判据未过，本轮不作定论。**

### 延拓 P3′ · 复测（**下一优先，须先满足三个前置**）

| 前置 | 内容 | 为什么 |

**复测通过判据（预注册，不许事后改）**：
> 同预算（场数差 ≤2%）下，学习臂的平均最终 wr 比解析臂高 ≥0.01，

### 延拓 P2′ · 深化（与 P3′ 可并行）

Pass 4 的复合 LNS 只走到「每血统接受 1 步就撞耐心闸」，**空间开发极浅**。
可做：

1. **复合深度加大**：2–4 步 → 3–8 步；每迭代测 3 候选 → 8–12 候选
2. **顶分段用强对手池**：血统 0 在 [450,650] 已 1.000 触顶，

   效应量应该远大于单步，**值得单独做一轮动作消融实验**
4. **减物品动作**：用户明确关心的"少上几件换拓扑"，目前权重 1/12，应单列实验

前置：P3′ 通过 + §6.1 修复。理由：自举会把噪声放大成偏差。
