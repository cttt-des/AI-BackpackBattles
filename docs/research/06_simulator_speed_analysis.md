# 调研报告 06：仿真内核速度瓶颈分析与提速路线

> 问题-方法导向。回答：**`engine/`（纯 Python）会不会成为速度瓶颈？C++/Rust 重写值不值？提升空间多大？**
> 方法：从反编译源码刻画每帧语义工作量（不做基准）+ 已有的单次数值与 profile 佐证 + 分阶段需求对照。
> 基线数据（2026-09-22 单次测量，3 组阵容 × 30 seed）：**12.6 场/s 单核，每场中位 67ms**；profile 显示热点约 2/3 在非语义开销。

---

## Q1 每帧到底有多少活？——从反编译源码估计

**关键参照：游戏本体就是解释型语言跑的。** 原版游戏用 GDScript（Godot 3 解释执行，单操作速度与 CPython 同量级）在普通笔记本 CPU 上**边渲染边 60fps** 跑完整战斗——说明原始语义工作量本身不大，我们的瓶颈是解释器开销的放大，不是算法复杂。

从 `decompiled_full/` 逐帧语义（对齐 `engine_truth.md`）：

| 每帧（1/60s） | 操作 | 量级 |
|---|---|---|
| 物品冷却推进 | 每物品 `triggerTime -= dt*speed`；speed = 查 heat/cold 栈 +  clamp（`Item.gd:3742-3757`） | 双方 ~40-60 物品 tick → **10² 次属性读 + 少量算术** |
| 触发 | 到期物品的 `doCooldownEffect`（行为函数，多为几次属性读写 + 发事件） | 每物品 1~4 次/秒 → 每场 10²~10³ 次 |
| 角色 tick | 1s 一次：回复/中毒分流（`Character.gd:401-414`） | 每场 ~30 次 |
| 伤害链 | 命中一次走 17 步（`Character.gd:495-653`），每步几个标志位判断 + 浮点运算 | 每场 10²~10³ 次命中 |
| 事件/日志 | 惰性事件 append | 每场 10³ 条量级 |

**估计：一场 30s 战斗 ≈ 1800 帧 × (10²~10³) 次小操作 ≈ 10⁵~10⁶ 次语义操作。**
CPython 小操作吞吐 ~10⁷~10⁸/s → 10~100ms/场（与实测 67ms 吻合）；C++ 同等工作量 ~10⁸~10⁹/s → **1~5ms/场**。即 C++ 的理论单核提速空间 ≈ **20~50×**；但这只换掉解释器，不改任何算法。

## Q3 提升路线（按性价比排序）

| 档位 | 内容 | 估计提升 | 保真风险 | 成本 |
|---|---|---|---|---|
| **L1 Python 机械优化** | snake 名预编译缓存（消灭 61 万次正则）；行为解析结果 memoize；`__getattr__` 加实例字典快路径；消 `hasattr` | **2~5×**（热点直接占 ~2/3） | **零**——纯等价变换，56 场指纹回归裁决 | 1~2 天 |
| **L2 多进程** | 引擎无单例可 deepcopy（v2 既定设计），进程池近线性扩展 | ×14~16（本机 16 物理核/24 线程） | 零 | 半天 |
| **L3 C++ codegen 后端** | 不给 transpiler 加 C++ 后端：3174 个行为函数从 GDScript AST 再生成一份 C++；`engine/` 的 runtime shell（Character/Item/Buff/EventBus/Combat）手工移植（估 2~4k 行） | **单核 20~50×**；16 核 ~10³~10⁴ 场/s | 中——指纹回归（固定种子逐事件比对）兜底 | 2~4 周 |
| L4 GPU batched（engine_batch） | RL 阶段需求，与 C++ 正交 | 见报告 01 | 中 | 大 |
| ~~Rust 手写移植~~ | 无 codegen 路径，3174 行为人工翻译 | 同 L3 | **最高**（双份维护 + 翻译漂移） | 最大 |

|---|---|---|---|
| 启发式搜索：单决策 MCTS | 每决策 10²~10³ rollout → 秒级~十秒级 | 够用 | **不用重写** |
| 专家轨迹量产（beam 评估：18 回合 × 宽 10 × 每候选 30 rollout ≈ 5.4k 场/轨迹） | 万条轨迹 ≈ 5×10⁷ 场 | 10~30 小时机时，可通宵批跑 | 勉强够，紧张时再上 L3 |
| 自博弈/搜索自我对局 | 10⁶~10⁷ 场 | 紧张 | **L3（C++ codegen）在此阶段前评估** |
| RL 训练采样 | 10⁴~10⁶ 场/s | 差 2~4 个数量级 | 走 L4（GPU）或 L3+L2 组合，届时用 spike 数据定 |

## Q5 GPU 采样可行吗？

**能，但没有"把现有引擎搬上 GPU"的捷径。** 本作负载是分派密集的规则逻辑（每帧几十次异构行为调用），不是稠密线性代数——`vmap`/torch.compile 都吃不动动态属性 + 3174 个异构行为函数。GPU 采样的唯一正路就是报告 01 的十条设计模式：把内核重写成**定长张量程序**（engine_batch），这与 C++ codegen（L3）是**同量级的重写决策**，二者在轨迹量产瓶颈点二选一，由 M0.5 spike 数据定。

**先例支持可行性**：Craftax（含战斗/掉落/合成的 crafting 游戏，与本作同构）在单卡 GPU 上 26~40 万 SPS——比 L3 C++ 的 10³~10⁴ 场/s 再高 1~2 个数量级，是 RL 阶段的唯一现实解。

**与搜索/轨迹量产的适配性意外地好**：

- 专家轨迹量产的最自然模式 = **CPU 决策 + GPU rollout 农场**：启发式策略在 CPU 出决策，把 K 条候选各 M 个 rollout 作为批量独立战斗一次性发射进 GPU。批量独立 rollout 是 GPU 上最简单的模式，不需要设备内树搜索。
- 状态很小（每 env 定长张量约几十 KB），snapshot/restore = gather/复制切片，MCTS 分叉在 GPU 上也便宜（Pgx + mctx 已有批量 MCTS 先例，需要时可用）。
- RTX 5080 16GB 按每 env 100KB 估，理论可驻留 10⁵ envs，实际受 kernel 复杂度限制，B=4096~16384 是合理预期（Craftax 4096 有实测）。

**保真度警示**：GPU 内核按架构文档的行为分档（P0 精确 top80 / P1 DSL / P2 长尾近似）——采样轨迹对长尾物品含近似成分。对专家轨迹用途可接受（top80 覆盖 90%+ 实战出场），但 56 场指纹回归只裁决 P0 覆盖的部分，这一条纪律不变。

**M0.5 spike 的具体做法**（2~3 天小成本，一次回答 L3/L4 选择）：用 20 个 P0 物品做一个最小战斗 kernel（JAX 与 PyTorch 各一版，各几百行），在 RTX 5080 上测单 substep 成本与 B=4096 吞吐；同时 L1 优化后的 `engine/` 跑多进程基线。两份数据放一起，L3（C++/CPU 10³~10⁴/s）与 L4（GPU 10⁵+/s）谁该上、什么时候上，就不用再争论了。

## 结论

1. **你的直觉方向对**：纯 Python 内核在轨迹量产与自博弈阶段会成为瓶颈，C++ 化的理论空间（单核 20~50×）真实存在。
2. **但现在不该重写**：① 2/3 热点是未缓存、未优化的 Python 机制，L1 有 2~5× 免费午餐且零保真风险；② 引擎 API 在服务协议/搜索开发期还会变，现在写 C++ 会返工；③ 搜索阶段 L1+L2 就够。
3. **若将来重写，唯一正路是 codegen**：transpiler 已有 AST 管线，加 C++ 后端 = 一份真值（GDScript）两个后端，保真由 56 场指纹回归机器裁决而非人工信仰。**不要选 Rust 手写移植**——无 codegen 路径、双份维护、翻译漂移风险最大。
4. **决策触发点**写死：专家轨迹量产实测吞吐 <300 场/s（16 核）→ 启动 L3/L4 评估（GPU 采样可行性与 C++ 二选一，依据 M0.5 spike：20 物品最小 kernel 实测 vs 多进程基线）；RL 阶段启动前 → spike 数据定最终路线。
