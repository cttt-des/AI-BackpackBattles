# 引擎跨场状态泄漏 — 根因与修复（训练报告 §5.4 的 6.1）

> 状态：**根因已定位、修复方法已验证**，待落地。
> 2026-11-12。本文件可直接作为交接说明，不必再读对话。
> 复现脚本：`tools/repro_battle_drift.py`（已固化，可直接跑）。

---

## 0. 一句话

`_rt._bind_battle()` 在常规战斗路径**从未被调用**，导致全局 Math 流与实例 id 台账
回落到「进程级单例」，跨场累积。同一 (阵容, seed) 在同一进程里连跑，**每场结果都不同**。

---

## 1. 根因

`simulator/gd_core_engine.py:1195` 附近的调用**只在 `p_activation_order` 分支里**：

```python
if p_activation_order is not None or o_activation_order is not None:
    ...
    from gd_core_py._rt import _bind_battle, _math_rng
    _bind_battle(int(self._seed))        # ← 只在这条分支
    _m = _math_rng()
    for _n in (len(self._p_items), len(self._o_items)):
        for _i in range(_n - 1, 0, -1):
            _j = _m.randi() % (_i + 1)   # 对齐 activation_order 的两条 shuffle
    combat.startBattle(...)
else:
    combat.startBattle(self._p_items, self._o_items)   # ← 常规路径，无绑定
```

后果：`_MATH_BIND` 与 `_GID_CUR` **恒为空**，于是

| 全局 | 设计意图 | 实际行为 |
|---|---|---|
| `_MATH_BIND` | 本场专属 Math 流 | 空 → 回落 `_MATH_RNG`（`DEFAULT_SEED` 起步，**跨场累积**） |
| `_GID_CUR` | 每场从 1 重计 gid | 空 → 回落 `_GID_MAP`（**跨场只增不减**，`id()` 复用还会串号） |

`_rt.py:883` 的 docstring 声称「由 `CoreContext._init` 在战斗装配最早期调用」——
**实际全局搜索后没有任何调用点**（`grep -rn "_bind_battle(" gd_core_py/` 只有定义）。
**注释与实现脱节。**

**对照组（已做过，不要重复）**：

| 实验 | 结果 | 排除了什么 |
|---|---|---|
| 每进程只跑 1 场 × 8 次 | **8/8 全同** | 首场确定；不是环境随机 |
| `PYTHONHASHSEED=0/1/12345` | 无影响 | 不是 str 哈希随机化 |
| monkeypatch `_gid` 换稳定序号 | 无影响 | 不只是 gid 的问题 |
| 清空 `_GID_MAP/_GID_NEXT/_GID_KEEP` | 无影响 | 因 `_bind_battle` 会重建 `_GID_CUR`；当前 `_GID_CUR` 是空的才回落，清空别的没用 |
| 32 worker × 同 job | 4 种结果各 8 次 | 曾被误读为「跨进程不确定」，实为 worker 内运行次数不同 |

⚠️ **重要修正**：早期实验「同进程连跑 3 次一致」是假象——那 3 次用了不同阵容对。
用同一对时，**每一次都不同**（见 §5）。

## 3. 修复方法

在 `GDCoreEngine.__init__` 里，**`CoreContext` 创建之前、第一批物品构造之前**，
无条件调用一次 `_bind_battle`：

```python
from gd_core_py._rt import _bind_battle
_bind_battle(<链起点>)
```

**位置要求（硬约束）**：必须早于任何物品的 `_readyInit`。
物品脚本可能消耗全局链（`CoreItem.py:2912` 的 `shuffleEngine`），
一旦先消耗再绑定，绑定就无效。

**不要做的事**：

| 禁止 | 原因 |
|---|---|
| 照抄现有那段代码 | 它绑定后还补消耗两条 shuffle，是 `activation_order` 路径专用；常规路径补了会错位 |
| 用 `try/except` 兜住 | 兜住就变静默错误 |
| 改 `_rt.py` 的绑定机制 | 机制本身是对的，只是没人调用 |
| 手改 `gd_core_py/**` 生成产物 | 只能改生成器或 `_rt.py` |

`<链起点>` 取什么，是本任务唯一需要判定的问题，见 §4。

## 4. 必须先判定：链起点取 seed 还是 DEFAULT_SEED

这是本任务的核心风险。**两种候选，含义完全不同：**

| 候选 | 语义 | 依据 |
|---|---|---|
| **A. `_bind_battle(int(self._seed))`** | 每场用本场 seed 起链 | `CoreRng.py:470-473` 注：`oracle_fight` 装配段每场 `seed(S)` 播种全局链后补两条 shuffle |
| **B. `_bind_battle(DEFAULT_SEED)`** | 每场重置回 `DEFAULT_SEED` | 若 oracle 录制时**每场是新 Godot 进程**，链恒从 `DEFAULT_SEED` 起步、不跨场累积 |

**判定方法（按顺序，每步记录数据）：**

```bash
# 基线：修复前先跑一遍，记录当前绿数
python tools/verify_oracle.py --limit 60

# 改法 A
# ...（改代码）...
python tools/verify_oracle.py --limit 60
git checkout simulator/gd_core_engine.py

# 改法 B
# ...（改代码）...
python tools/verify_oracle.py --limit 60
```

**选择规则：**

| 情况 | 决定 |
|---|---|
| 只有一种让 60 例保持全绿（或不低于基线） | 用那一种 |
| 两种都全绿 | **用 A**（`self._seed`），与 `activation_order` 路径语义一致 |
| 两种都变红 | **停下来报告**，附两种各自失败用例与首个分歧事件 |

> ⚠️ `tools/verify_oracle.py` 会重写 `--cases-json` 指定的夹具文件。
> **不要**把 `output/oracle/expand/fights/**` 的 `lineups.json` 作为 `--cases-json` 传入
> （历史事故：曾把 1690 全量夹具覆盖成子集，需 `git checkout` 恢复）。

## 7. 顺带纠正训练报告 §5.4 的错误结论

训练报告（`trainer/训练初步报告.md` §5.4）写道：

> 「同 (阵容对, seed) 的对局结果在跨 worker 进程时可翻转（同进程内连跑 5 次逐位一致；
> 隔离实验 200 场两遍出现 1 场翻转，`PYTHONHASHSEED=0` 无效）」

**三处需要改写：**

| 报告说法 | 实测 |
|---|---|
| 「同进程内连跑 5 次逐位一致」 | **假象**——那 5 次用了不同阵容对；同一对时每次都不同 |
| 「200 场出现 1 场翻转」 | **73/200 有差异（36%）**——报告那次两次跑在同一批 worker、顺序相近，累积状态接近才只看到 1 例 |
| 「跨进程非确定性，机制指向对象身份哈希」 | **是同进程跨场状态泄漏**，机制是「绑定未生效 → 回落进程级单例」 |

**修正后**：§5.4 的标题与结论应改为「同进程跨场状态泄漏」，
并指向本文件。这也意味着 P1 的 noise_paired 有时粗于 unpaired（run4162 的 0.8x）
有了完整解释——那不是 CRN 无效，是评估本身每次都不同。
