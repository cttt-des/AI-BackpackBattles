## 3 旧路径（2026-11-12 中午，**已被 §8 取代**——3.1 L3 float 与 3.2 绑核均判否）

### 3.1 L3 float 面（1–2 天，**最高优先**）

**为什么是它**：这是唯一能把「换语言值不值」变成实测的问题。当前 float 面覆盖率 0，
而热路径（速度/冷却/伤害/生命/热度）全是 float。

| 关键判断 | 结论 |
|---|---|
| GDScript `float` 宽度 | **64 位** ⇒ 与 `double` 同宽，不降精度 |
| f32 从哪来 | 只在 3 模块用**显式垫片**（CoreBuff 4 / CoreCharacter 3 / CoreTimer 3 处），与槽类型无关 |
| 会不会破 f32 | **不会**：`double` 槽 + 显式 `f32(x)` ≡ 原 `object` 槽 + `f32(x)` 逐位相同 |
| 风险 | 字段被赋 `None`/`int` → 编译态 `TypeError` **立刻炸**（不静默） |
| 已抽查干净字段 | `speedScale`/`triggerTime`/`_cooldown_active`/`fatigue_next_tick`：引擎零动态赋值、源码零 `None` |

**三步**：① 放宽 `_l3_numeric_types`（加 `float`→`double`，采集面扩到 items 全树）→ 目标 ≥90 槽；
② 编译迭代 + `_L3_BLOCKLIST` 收敛到零失败；③ 三闸 + 三点微基准 + 1690。

**判读（✅ 已实测，2026-11-12）**：

- float/double 槽落地（119 槽/55 模块全量重编）后，**热三点回归 -9~-24%**
  （getspeed 0.578→0.72 / phystack 1.25→1.48 / gainStacks 0.449→0.488µs，
  静窗口负载 3-25% 两轮一致）——**机理：复合表达式里 C double 槽与 object
  值（跨模块 def 返回值、object 形参）混算，每次运算都付装/拆箱转换，
  抵消并反超槽读收益**。§H-2 的 13-40x 是孤立全-C 循环形态，不适用于
  真实复合路径。
- **处置**：float 面整体回退 `object` 槽（bool/int bint/long long 保留，
  零回归）；518 模块重编回验证态。
- **终审**：微基准 ≈1.0x（回退后）+ float 面 ≈0.8x（负收益）→ **84% 是
  算法本身，C++ 正式关闭（有证据）**；数值槽方向就此收口（bool/int
  24 槽保留，零回归）。

## 5 纪律（血泪条款）

| 纪律 | 为什么 |
|---|---|
| **账本 mtime 与代码提交时间相近**（2026-11-12 放宽，原「必须晚于提交」——单提交流程下不可满足） | 防的仍是陈旧账本绿：曾出现「声称晚于提交，实际差 1.5 小时」 |
| **编译态结论必须证明 pyd 比源新** | `build_cython` 曾「pyd 存在即跳过」，导致多轮「重编」空转 |
| **只报交错 A/B 比值，不报跨机绝对值** | `process_time` 刻度 15.6ms + 睿频抖动，p50 分辨率 ±4–10% |
| **单点微基准要加大 n** | 200k 次时跳动是刻度噪声；800k–1M 才收敛 |
| **看剖面要看总量，不只 top30 名单** | 事件计数回归就是 top1，但按名单看永远看不出 |
| **`@property` 惰性视图的计数必须 O(1)** | 每 tick 访问一次聚合视图 = 全量物化 |
| **不许改判据**（`canonical_stream`/`render_lines`/语料） | 改判据 = 作弊 |
| **不许重生成夹具** | 会造出 13 场假红 |
| **`--force` 不可与 `--skip-godot` 同用** | 假阳性 |
| **`--cases-json` 不可传全量夹具** | 脚本会写回覆盖 |
| **大文档禁止「读局部 → 整体写回」** | 曾因此截掉 45 行 |
| **判否前先确认判据测的是不是同一件事** | 「object 槽无收益」被用来否定「数值槽」，是循环论证（§H 已翻案） |

**三闸**：seed 双态（`20260923≡907`、`42≡1042`）→ REG 九场 → 60 场；1690 走里程碑。
**A 类主判据**：调用数下降 ≥80%（`--profile-out`，绕开墙钟地板）。

### 8.2 本轮重大发现：跨场状态泄漏（已修，`58b78f35`）

`_bind_battle` 只在 `activation_order` 分支调用，常规路径 `_MATH_BIND/_GID_CUR` 恒空，
回落进程级 `_MATH_RNG/_GID_MAP` 导致**同 (阵容, seed) 同进程连跑结果每场不同**。

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 同进程连跑 4 次 | **4 个不同指纹** | 同一指纹 |
| 跨 worker 差异 | 伪象（worker 内运行次数不同） | 消除 |

**影响面**：单进程多场的绝对耗时历史数字（265ms/155ms 等）可能被污染；**`bench_ab` 每轮独立子进程，比值不受影响**。

### 8.5 第 1 项的实现要点（常驻池）

```python
pad = '''
pool = MCPool(workers=4)        # 进程池常驻，worker 内 kernel() 只付一次
for batch in batches:
    agg = pool.run_mc_mem(p, o, seed, runs=16)   # 复用同一批 worker
pool.close()
'''
```

**必须处理的四件事**（否则会引入新问题）：

1. **worker 崩溃恢复**：`BrokenProcessPool` 要能重建池并报告；训练循环不能因一次崩溃全丢。
2. **内存增长**：worker 常驻会累积对象；需定期重建（如每 N 千场）或显式 `gc.collect`。
3. **spawn 语义**：Windows spawn 要求调用方在 `if __name__ == '__main__'` 内、且**不可从 stdin 运行**（本轮踩过：`OSError: '<stdin>'`）。
4. **确定性不变**：worker 复用时须确认无跨场状态泄漏——`58b78f35` 修的就是这类问题，需加「同池连跑 N 次指纹一致」的回归测试。

**✅ 执行实录（2026-11-12）**：`MCPool` 已落地 simulator/simulate.py（复用
`_mc_mem_worker`/`_pool_init_mem`/聚合助手 `_mc_mem_agg`）。验证
（tools/_mcpool_check.py，下划线件不入库）：①同池同 seed 批次指纹一致 PASS；
②串行逐 seed 对拍 PASS；③runs=64 吞吐 7.81 场/s。**runs=8 交错 3 轮 A/B**：
常驻池 r2/r3 稳定 11.1-11.5 场/s vs run_mc_mem 3.2-3.4（**3.45x**，r1 4.01 系
池首轮 kernel 装载）。**踩坑实录**：验收脚本初版漏 `if __name__ == '__main__'`
守卫——Windows spawn 子进程重导主模块递归建池，机器假死（§8.5 要点 3 的
活体标本）；守卫加上后干净复现 3.45x。**生产面未动**：run_mc_pool/run_mc_mem
原语义保留，MCPool 是新增 opt-in 类。

### 9.3 第一项：`_run_jobs` 常驻化（预计端到端 2–3x）

**为什么高优先**：不用改内核、不碰判据、收益已由 §8.4 第 1 项在仿真侧证实（3.45x）。
训练侧的搜索循环是**大量小批量评估**，正是常驻池的典型受益场景。

**接口差异（必须处理）**：

| 项 | MCPool 现状 | trainer 需要 |
|---|---|---|
| 任务形状 | `(player, opponent, seed, runs)` 同质大批量 | **`(player, opponent, seed)` 异质对手池** |
| 返回 | 聚合 dict | 逐 job 胜负列表（`_run_jobs` 返回 `List[int]`） |
| 池复用 | walk `run_mc_mem` | 需要 `submit_jobs(jobs)` 通用入口 |

**做法（二选一，建议 A）**：

- **A：给 MCPool 加 `submit_jobs(jobs) -> List[int]`**，内部用同一 `_battle(job)` 的池化版本；
  trainer 的 `_run_jobs` 改成模块级单例池（惰性创建、进程退出时 close）。
- B：新建 `trainer/eval_pool.py`，把 MCPool 的重建/重建策略抄一份——**不推荐**（两份实现会漂）

**三个必须保住的不变量**：

1. **CRN seed 映射不变**：`seed_base + oi*10000 + k` 必须原样进 worker；排序不许变。
2. **逐位结果一致**：常驻池跑出的 `List[int]` 与新建池、与串行**逐元素相等**（用现有 pool 的 3 场 × 2 seeds 做对拍即可）。
3. **跨场无状态泄漏**：worker 常驻后必须能在同一 worker 内连跑 N 场指纹一致（`58b78f35` 修的就是这类）。

**验收**：

| 闸 | 判据 |
|---|---|
| 吞吐 | `jobs=24` 从 2.9 → **≥8 场/s** |
| 一致性 | 常驻池 vs 新建池 vs 串行，逐 job 胜负全等 |
| 确定性 | 同池连跑 4 轮，胜负序列指纹一致 |
| 内存 | 000 场后 RSS 无单调增长（`max_pool_fights` 透明重建生效） |
