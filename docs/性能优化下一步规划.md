### 0.1 判定阈值（本轮修正，**取代旧的 10% 门**）

旧台账用「整场 p50 降 ≥10%」当有效性判据。实测噪声地板（同配置 n=40 重复 6 次）：

| 口径 | 极差 | stdev | SEM | **3σ 可辨** |
|---|---|---|---|---|
| `mean_ms` | 3.49% | 1.25% | 0.51% | **1.52%** |
| `p50_ms` | 7.18% | 3.71% | 1.51% | 4.54% |

**`p50` 的读数落在 `process_time` 15.62 ms 刻度的整数倍上**（实测一半 203.1、一半 218.8），
它的散布一半是量化噪声。⇒ **10% 那道门不是太高，而是用错了口径**：

| 场景 | 判据 |
|---|---|
| **整场改动** | `mean_ms` 降 **≥2%**（3σ=1.52%，留余量）；拿 `p50` 报 2% 级结论一律无效 |
| **微基准（日常）** | **≥1.05x**；≥1.3x 只留给「要不要换语言」这种量级决策 |
| **<2% 的改动** | 进「待累积清单」，凑够 ≥2% 合并测一次（见 §4.4） |
| **零收益但零风险且降复杂度** | **免收益判据**直接合（`load_for` 属此类） |
| 判据本身（`canonical_stream`/`render_lines`/语料） | **永远不许改** |

### 4.2 第二步：D1 热循环类型化（**预期收益最大，但要全量重编**）

**问题**（本轮实测）：`gd_core_py/gd_core/CoreCombat.py` **一条 `cimport` 都没有**，物品循环变量是纯 PyObject：

```python
for item in _iter__loc(self.opponent.inventory.getItems()):    # 纯 PyObject
    if item._cooldown_active:                          # PyObject_GetAttr
        if not (item.character().stunnedDuration > 0):  # 属性 + 调用 + 属性
            item.triggerTime -= delta * item.getSpeed() # 属性 + cpdef 调用
```

每 item-tick 约 **8–10 次 `PyObject_GetAttr`**，**93k item-ticks/场**。

**微基准**（`tools/typed_loop_probe/`，103 物品 × 100k 轮 = 10.3M item-ticks，MSVC `/O2`）：

| 写法 | µs/item-tick |
|---|---|
| untyped（现状） | **0.272** |
| typed（`cdef Base item` + `<Base>items[i]`） | **0.008** |
| | **35.8x（仅该段）** |

**边界（必须写清）**：真实内核每 item-tick 是 **1.8 µs**，而基准里 untyped 只有 0.272 µs——
差的 1.5 µs 是 `trigger()` 触发链与真实计算，**类型化动不了**。
正确预期是「属性访问这一段」快 35.8x，**折合单场上限约 24 ms（−8~12%）**，
不是「physicsTick 167 ms → 5 ms」。

**做什么**：生成器给 `CoreCombat.py` 发射 `cimport`（`CoreItem`/`CoreCharacter`）+ 循环首行 `cdef CoreItem item`；
`item.character()` 返回类型需要能从 C 侧强转。

**判据**：`mean_ms` 降 **≥3%**（预期 8–12%）；三闸全绿；1690 走里程碑。

**风险（两条，都已实证）**：
1. **类型不匹配**：物品可能是 Gem 等子类，强转失败会抛 `TypeError`（安全失败，不静默）——
   需先确认所有参战物品的类都在 `CoreItem` 继承链上（已确认：`Exclusive__BerserkerBag → Bag_2 → Item_2 → CoreItem`）。
2. **ABI 级联**：`CoreItem.pxd` 被 **240 个模块** cimport。本轮我只重编 3 个热点模块，
   就撞上 `ValueError: CoreItem size changed, expected 576, got 24`，21 个模块导入失败。
   ⇒ **必须全量重编**（约 20–26 min），且要等并行会话未提交的 `.pxd` 定稿。

## 7 事故：62 场群编译层回归 + 「1690/1690」假绿记录（2026-11-13 晚，D1 里程碑揭出）

**起因**：§4.2/D1 判据要求的 1690 里程碑（`--force` 全量重模拟）只到
**1627 一致 + 62 py 缺产物 + 1 比对异常**（`_d1_1690.json`）。追查发现这不是 D1 引入：

1. **权威账本自证**：`alignment_expand.json`（mtime 2026-11-13 11:06）本身记的就是
   **1628 三方一致 + 62「py 缺产物」**——此前台账 §0/归档 §11.7/`ce47a982` 提交信息里的
   「1690/1690 全绿」**与账本矛盾**（账本 mtime 晚于声明、内容为 1628+62）。
   62 场名单与 `_miss62.json` 逐位同构——缺口跨多次「全绿」声明持续存在。
   ⛔ 本条为**假绿记录事故**：里程碑声明未回读账本 `match` 分布，只看了场次总数。
2. **根因（已定位+已修）**：`super(): __class__ cell not found` @ `Greatsword_2.
   getStaminaCost` 零参 super()。三元组合 = `cpdef double getStaminaCost`（§11.4/8cedd5ac
   引入）+ plain 子类 def 覆写 + 零参 super()，Cython 3.3.1 编译态回归；纯 py 臂同场
   **1/1 全绿**（语义层无恙）。`binding=True` 不救（11:26 重编产物、fresh 重编、
   旧 CoreCombat.pyd 三路复现全崩）；`character()` 虚派发等红线无关。
   **修复**：`CoreItem.pxd` 撤 `cpdef double getStaminaCost`（退 plain def 动态派发，
   §11.7 闭环已判 1.07-1.10x 不划算——让微收益换正确性）。实证：崩签名 2→0。
3. **第二层（未修，62 场群继续项）**：super 修后同场（`run101668_r12_o704449_r12`）
   在更深处露出 `ZeroDivisionError`：`BustedBlade.onBattleRageEnded → updateBaseCooldown
   → _div(triggerTime=-5.55, iterationCooldown=0.0)`。纯 py 臂同场全绿 ⇒ 编译 vs 纯
   **状态发散**（编译臂 rage 结束时 iterationCooldown 已 0.0，纯臂未达此态）。
   需要双臂状态差分战役（逐 case 定位首个发散写点），非当晚可毕。
4. **教训入账**：①「全量里程碑」的验收必须回读账本 `match` 分布（总数≠一致数）；
   ②binding=True 修 binding=False 事故后，当时未对 62 场专项复跑——闸三件套
   （seed/REG9/60）不覆盖该路径，62 场群缺专项快闸；③编译层回归必须双臂
   （pyd vs GD_PURE_PY）对跑定位——本次两处编译特有问题纯臂均绿。
5. **处置**：pxd 修复随 §4.3 捆批全量重编一并部署（pxd 变更=ABI 级联，本就要
   全量）；重编后里程碑预期「1628 一致 + 62 场进第二层战役」——62 全绿前，
   §0 全量行保持修正态，不回填 1690/1690。

6. **结案链（同晚追记，全部实证）**：
   - **手动 pxd 修正不可持久**：CoreItem.pxd 是生成器产物，重跑生成器即回填
     cpdef 声明。永久修复 = 生成器级：`getStaminaCost` 进 `_L2_BLOCKLIST`
     （tools/gd_to_py.py，与 §11.4 止损位同机制）。
   - **崩场复验**：`run101668_r12_o704449_r12` 在干净树（662 模块无旗标全量
     重编 + pxd 修复）上 **0/1 → 1/1 三方一致**——super 层修复实证。
   - **第二层 ZeroDivision 未复现**：干净树上该场全程无零除——此前那层
     「编译 vs 纯状态发散」是**毒树伪影**（见下条），62 场群第二层战役撤销。
   - **段错误事故（当晚第二节）**：§4.3 捆批（D5/D6/D8）全量重编把**包根手写
     辅助模块**（`_registry`/`_bootstrap`/`_colors`/`__init__`）也编成了 pyd
     （构建清单从存活 pyd 反推 + 我未排除非转译产物）→ 加载器 pyd 优先遮蔽
     纯 py 语义 → 全树导入段错误（seed 闸即崩）。**当时所有旗标二分全部无效**
     ——测试树本身被污染（`_registry.pyd` 在场）。12:0x 的旧 CoreItem.pyd 二进制
     也崩，证明与产物无关、与加载环境有关。
   - **护栏**：`build_cython.py` 新增包根辅助模块拒绝闸（`_FORBID` 四文件）；
     构建清单刷新为 664 模块（`_all_list2.txt`，排除根辅助 .py）。
   - **D5/D6/D8 捆批判否（止损）**：闸红即弃，全树回退无旗标态；旗标本身
     （boundscheck/AVX2/LTO）是否有罪**未定**（二分被污染树作废）。重试条件：
     ①干净清单（已备）②逐旗标 bisect（每步全闸）③每次重编后先跑 seed 闸
