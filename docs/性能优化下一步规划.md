### M0 已完成（2026-11-10 晚，替代方案，未改电源）

用户裁定**先不动电源**，改用「方差免疫」的测量口径。已落地三件工具：

| 交付 | 路径 | 作用 |
|---|---|---|
| CPU 计时 + 热身 | [tools/bench_sim.py](tools/bench_sim.py) 参数 `--cpu-time` / `--warmup` | 用 `process_time` 替代 `perf_counter`：排除降频/抢占造成的墙钟等待 |
| 交错 A/B | [tools/bench_ab.py](tools/bench_ab.py) | 每轮交替跑两个臂（各自独立子进程），只比**配对差值**；奇偶轮反向抵消轮内漂移 |
| 纯 py 臂 | [tools/_purepy_arm.py](tools/_purepy_arm.py) | `GD_PURE_PY=1` 经 `sys.meta_path` 屏蔽扩展加载 → **不删 .pyd 也能跑源码臂** |

**实测对比（同一命令、同一机器）：**

| 口径 | 单臂散布 | 结论 |
|---|---|---|
| 墙钟 `perf_counter`（旧） | **68%** | 不可用 |
| CPU `process_time` + 热身 | **4.8% / 13.6%** | 可复现 |
| 配对 A/B 比值（n=40, 5 轮） | `cy/py = 1.0749`（散布 18.6%） | 编译臂约快 7.5% |

**散布 18.6% 的原因**：Windows `process_time` 实测粒度 **15.62ms**（1/64 秒系统节拍），单场 ~320ms 只有约 20 个刻度。要更稳就**加大 n**（n=40 约 12.5s/臂）或增加轮数——是分辨率问题，不是方法错。

**顺带纠正一个此前的误判**：机器是 **HP ProBook 440 G6（4P/8L、基准 1.6–1.8GHz、插电 100%）**，并非「被锁到 800MHz」；波动来自睿频频繁开关。`--pin` 失败是 `SetProcessAffinityMask` 被拒，已记录，未强改系统。

**M0 剩余（可选，非阻塞）：**

- `--pin` 改用 `psutil.Process().cpu_affinity()` 重试；仍失败则记档「本机不支持绑核」
- 记分卡加 `bg_load` 字段（跑前采一次 CPU 负载，>15% 的数字标灰）
- 想要与 v0.5.2 的 207ms 对齐的绝对数字，仍需用户同意改电源（M0-1，默认不做）

> **给接手者的第一句话**：任何优化结论都用 `tools/bench_ab.py --cpu-time --n 40` 出**比值**，
> 不要用 `bench_sim.py` 的绝对值；报数字时同时给 `spread_ratio_pct`，>5% 就加大 n 重测。

## 3 剩余优化空间（按 profile v13 实测）

`profile_v13.json`（3 场，n=3）top 调用，已排除内核实名后归成三簇：

| 簇 | 代表调用 | 3 场合计 | 性质 |
|---|---|---|---|
| **事件对象化** | `CoreEvent.id` 13559 / `getDepth` 6571 / `setParam` 6554 / `_init_fields`+`_init` 10272 / `createEvent` 5136 | ~4.2 万 | 每条事件构造 Python 对象 + 属性链 |
| **空钩子派发** | `snapshotCharacterStat` 13605 / `snapshotItemMetric` 5144（`CoreHooks` 51 个方法**全是 `pass`**） | ~1.9 万 | 纯派发，零行为 |
| **日志/桥接旁路** | `_side` 11356 / `kernel` 10489 / `_json_safe` 7122 / `_actor_of`+`_count`+`_origin_key` 15405 / `_EventOut.__init__` 5138 | ~5 万 | `_LogMixin` 事件桥 |
| 环境读取残量 | `_Environ.__getitem__` 12385（C17c 快照已装，仍有 engine 层直读） | 1.24 万 | 见 M2-5 |

合计约 **12 万调用/3 场**残量，而 v11 时 top30 是 22 万——**事件与钩子路径现在是最大的一块**，且几乎全在「判定链下游」的旁路上。

## 4 主线规划

### 判定记号

✅ 直接可做 / 🔶 需审计或不变量证明 / 🧪 需实验取证 / ❌ 不做。

### M1 Cython 类型化（1–2 周，主收益）

**现状：现在是「纯编译」**——`cython -3` 直译，**零类型注解、无 .pxd、无编译旗标**。
这档收益通常只有 1.2–1.5x；真正到 3–6x 的是**类型化**。今天 1690 全绿说明编译态本身安全，可以放心往上加类型。

| 编号 | 做法 | 预期 | 判定 |
|---|---|---|---|
| M1-1 | 手写 `gd_core_py/_rt.pxd`：`f32`（`double→float→double` 用 `float` 中转）、`_div/_mod`（`long long`）、`PCG32`（`unsigned long long` state/inc） | 5–10% | ✅ |
| M1-2 | 生成器输出 `.pxd`：给 `_init_fields` 里的声明字段生成 `cdef public` 槽（仅 `float/int/bool` 面，Variant 保持 PyObject） | 15–30% | 🔶 |
| M1-3 | 热 8 模块的 `cdef class` 化（先 `CoreRng`/`CoreTimer`，后 `CoreBuff`） | 10–20% | 🔶 |
| M1-4 | 编译旗标：`binding=False`、`embedsignature=False`、`freelist`、`/O2` 已有 | 3–8% | ✅ |
| M1-5 | `-fno-semantic-interposition`+LTO（MSVC `/GL /LTCG`） | 2–5% | 🧪 |
| M1-6 | 局部变量用 `cdef double` 声明（在生成的 tick 函数内） | 视函数 | 🔶 |

**M1 的闸门比以往更严**：每个 `.pxd` 批次都要跑 **seed 逐位（907/1042）+ REG 九场 + 60 场 + 1690**。
类型化改的是**数值路径**，一个 `double` 写错就能让 f32 舍入漂移——这是本项目历史上最贵的一类 bug（见 v1 §0 的 `randf` 链）。

### M2 事件与钩子路径（2–3 天，零语义风险，性价比最高）

这批全在**判定链下游**（`logEvent` 是纯旁路：不消耗 rng、不改内核状态），所以风险最低、验证最容易。

| 编号 | 做法 | 预期 | 判定 |
|---|---|---|---|
| M2-1 | **空钩子调用点剥离**：生成器识别目标方法体为 `pass` 的 `ctx.hooks.*` 调用并删除（51 个方法，约 1.9 万调用/3 场） | 5–10% | 🔶 |
| M2-2 | `CoreEvent` 加 `__slots__`（`_init_fields` 已知字段集），免 `__dict__` | 3–6% | 🔶 |
| M2-3 | `_json_safe` 深拷贝改「已知标量直通」（事件 params 实际只有 int/float/str/bool） | 2–5% | ✅ |
| M2-4 | `_LogMixin` 合并小函数：`_actor_of`/`_origin_key`/`_side` 在 `logEvent` 内联 | 3–6% | ✅ |
| M2-5 | env 快照覆盖 engine 层 4 处直读（`gd_core_engine.py:154/715/721`） | 1–2% | ✅ |
| M2-6 | MC 模式（runs>1）关闭事件对象构造，只累加统计 | 8–15%（MC 口径） | ✅ |
| M2-7 | 事件对象复用池（需证明无跨 tick 存活引用） | — | ❌ 风险>收益，不做 |

**M2-1 的关键审计**：剥离只允许对「`CoreHooks` 里体为 `pass` 且**无子类覆写**」的方法做。
引擎用 `_make_probe_class` 动态派生探针类覆写 `logEvent` 等——**这些绝对不能剥离**，否则事件流静默变空（`_LogMixin` 的注释已经记过这个坑）。
做法：生成期只删 `CoreHooks` 自身的 define，不删基类虚派发；再在装配期断言「剥离清单 ∩ 探针覆写清单 = ∅」。

## 5.1 交接任务书（给执行 agent）

### 任务 M2-1：空钩子调用点剥离（先做这个，1 天）

**目标**：`CoreHooks` 里 51 个方法全是 `pass`，热路径每 3 场调用约 1.9 万次（`snapshotCharacterStat` 13605、`snapshotItemMetric` 5144）。剥离这些调用点。

**做法**：
1. 在 `tools/gd_to_py.py` 加一趟 `_strip_noop_hooks`：扫描 `ctx.hooks.<name>(...)` 调用点，若 `<name>` 在 `CoreHooks` 中方法体只有 `pass`/`return None`，删除该调用语句。
2. **安全规则（必须实现）**：只删 `CoreHooks` 自身定义的方法调用；`logEvent` 等被 `_make_probe_class` 动态派生类覆写的方法**严禁剥离**（剥了事件流会静默变空、判定还全对——这是历史上踩过的坑）。
3. 装配期加断言：`剥离清单 ∩ 探针覆写清单 == ∅`，违反直接抛异常。

**验收**：`bench_ab.py --cpu-time --n 40` 比值 ≥1.05；60 场 60/60；REG 九场 9/9；seed 907/1042 逐位。
**止损**：60 场绿但 REG 出现新红 → 立即整趟回滚（旁路优化不该影响判定，出现即说明假设错）。

### 任务 M1：Cython 类型化（1–2 周，主收益）

**开工前提**：M2 收口、账本比代码新。

**分批顺序（每批独立上闸，任一批红只回滚该批）**：
1. `M1-1` 手写 `gd_core_py/_rt.pxd`：`f32`（`float` 中转）、`_div/_mod`（`long long`）、`PCG32`（`unsigned long long`）——**先做这个，收益确定且面最小**

**止损**：投入 2 天未能过某闸 → 回滚该批 `.pxd`，结论写回本文。

## 5.3 纪律（接手第一件事先读这条）

- **账本 mtime 必须晚于代码提交**，否则「全绿」不算数（本项目已踩过一次）
- 只报**交错 A/B 比值**，不报跨机器绝对值
- 不许改判据（`canonical_stream` / `render_lines` / 语料）来变绿
- 不许用「重生成夹具」来修问题（会凭空造出假红）

## 8 本规划不做（写下来防回潮）

| 项 | 结论 |
|---|---|
| `character()` 内联 | Gem 覆写，虚派发必须保留 |
| 跨模块合并 | 破坏 `__module__` / `_is_behavior_tree` 语义 |
| 事件驱动调度 | 改帧内调用集合，等于换内核 |
| 事件对象复用池 | 跨 tick 存活引用无法证明 |
| 改 `f32` 精度 / 降 tick 频率 | 直接破确定性 |
| Godot 无头当产品运行时 | v1 已排除 |
