### 8.5 第 1 项的实现要点（常驻池）

```python
pad = '''
pool = MCPool(workers=4)        # 进程池常驻，worker 内 kernel() 只付一次
for batch in batches:
    agg = pool.run_mc_mem(p, o, seed, runs=16)   # 复用同一批 worker
pool.close()
'''
```

**必须处理的四件事**（否则会引入新问题）：

1. **worker 崩溃恢复**：`BrokenProcessPool` 要能重建池并报告；训练循环不能因一次崩溃全丢。
2. **内存增长**：worker 常驻会累积对象；需定期重建（如每 N 千场）或显式 `gc.collect`。
3. **spawn 语义**：Windows spawn 要求调用方在 `if __name__ == '__main__'` 内、且**不可从 stdin 运行**（本轮踩过：`OSError: '<stdin>'`）。
4. **确定性不变**：worker 复用时须确认无跨场状态泄漏——`58b78f35` 修的就是这类问题，需加「同池连跑 N 次指纹一致」的回归测试。

**✅ 执行实录（2026-11-12）**：`MCPool` 已落地 simulator/simulate.py（复用
`_mc_mem_worker`/`_pool_init_mem`/聚合助手 `_mc_mem_agg`）。验证

## 11 模拟器性能：剩余空间的重新量化（2026-11-12 晚，专注模拟器）

> 上一轮我把性能线标为「全部收口」，但用户要求继续。重测后发现：**收口的理由是错的**——
> 判据都建在「Python 层还能榨」这个假设上，而真正的大头是 **C 层里的 PyObject 开销**，从未被单独测量。

### 11.1 实测：Python 层确实见底（这半句没错）

| 测量 | 结果 |
|---|---|
| cProfile 总量 | `physicsTick` **83.5%** / `logEvent` 11.6% / 其余 <1% |
| 纯 Python 帧合计 | **24.3 ms**（单场 190 ms 中），其中 `logEvent` 占 **21.6 ms** |
| `logEvent` 旁路上限（`light_log` 对照） | full 218.8 vs light 203.1 → **仅 7.1%** |
| `character()` 缓存探针 | **+1.7%**（噪声内，已证无用） |

结论：Python 层（含事件旁路）总共只剩 **~24 ms / 190 ms = 13%**，且其中大半是必要的。
**这一半收口是对的。**

### 11.2 但 C 层 83.5% 从未被拆开看：里面是 PyObject 访问

关键事实（本轮新测）：

| 类 | cdef 槽数 | 其中数值槽 |
|---|---|---|
| `CoreItem` | **77** | **0** |
| `CoreCombat` | 20 | 0 |

每 tick 每物品都要读 `triggerTime`、`_cooldown_active`、`character_`、`getSpeed()` 等，
而这些字段全是 **`cdef public object`**——Cython 每次读写都要走 PyObject 引用计数 + 类型解引用。
**83.5% 的「C 时间」里有相当比例是这些开销，不是算法本身。**

### 11.3 为什么 L3 float 那次失败、这次不一样

| 项 | L3 float（失败） | 这次提案 |
|---|---|---|
| 字段 | 改 `double` | 改 `double` |
| 访问器 | **仍是 Python 调用方** | **调用方一起 C 化** |
| 运算 | `double` 槽 ⊕ `object` 值 → **每次都装/拆箱** | 两端皆 C 类型 → 无转换 |
| 结果 | −9~−24% | 待测 |

**L3 失败的根因是「混算」**：一半 C 一半 object，转换成本 > 收益。
要兑现必须**整条链 C 化**：字段 + getter + tick 循环三处统一为 C 类型。

### 11.4 最小闭环实验（**先做这个，1–2 天**）

**目标**：验证「整条链 C 化」能否 ≥1.3x。只动 3 条最高频链，不动全树。

| 链 | 现状 | 提案 | 频率 |
|---|---|---|---|
| `triggerTime` 递减 | `item.triggerTime -= delta * item.getSpeed()`（object 字段 + Python 调用） | 字段 `double` + `getSpeed` 改 `cpdef double` + 循环内直接取 | 每 tick × 103 物品 |
| `_cooldown_active` 判定 | `object` 槽 + Python 属性读 | 字段 `bint` | 同上 |
| `stunnedDuration` 判定 | 经 `item.character()` 再取字段（**两次间接**） | 角色上 `double` 槽 + 循环里缓存在局部 C 变量 | 同上 |

**实现约束（必须全部满足）**：

1. **只改 `.gd` 真源 + 生成器 + pxd**，不手改产物。
2. `getSpeed` 改 `cpdef double` 后，**所有调用方必须在同模块或已 cimport**，否则退回 Python 调用、等于没改。
3. 字段若可能被赋 `None`/`int`，编译态会 `TypeError` 炸——用 `_L3_BLOCKLIST` 剔除，**不要 try/except 兜**。
4. 三闸：seed 双态 → REG 九场 → 60 场；1690 走里程碑。

**判据（三道，缺一不可）**：

| 判据 | 阈值 | 方法 |
|---|---|---|
| 单点微基准 `physicsTick` | **≥1.3x** | 10⁶ tick 级循环，`process_time`，n≥5 取中位 |
| 整场单场耗时 | ≥10% 降 | 交错 A/B（`bench_ab`，n=40，5 轮） |
| 确定性 | 全绿 | 三闸 + 1690 |

**判读**：

- **≥1.3x** → 整条链 C 化成立，**扩展到其余数值字段**（分批，每批三闸）；
- **<1.1x** → PyObject 开销假设被证伪，**C++ 重写正式关闭**（那时才有证据）；

### 11.5 若闭环失败后的备选（不重叠）

> 而后者此前所有结论都被外部负载污染过。

### 12.1 已落地：`load_for` 索引化（`5e092dde`）

| 项 | 优化前 | 优化后 | 证据 |
|---|---|---|---|
| `load_for` | **7.5 ms/call** | **0.18 ms/call（41x）** | `tools/_loadfor_cost2.py`，`process_time` 累计 300 次 |
| 装配 p50 | 31.2 ms | **28.6 ms** | `tools/_asm_acc.py`，`perf_counter` 累计 12 场 × 7 轮取中位 |

**根因**：`load_for` 对每个阵容脚本线性扫一遍 `_ITEM_ORDER` 全表（108 脚本 × 505 项 = **5.5 万次 `str.rsplit`**），
且是**每场都付的边际成本**（不是冷启动摊薄——这点此前被 §9.1 记成「首场-only」，与实测矛盾，已纠正）。

**做法**：生成器发射 `_ITEM_STEM`（stem→rel，生成期断言无重名）与 `_ITEM_MODULES`（拓扑序导入表），
`load_for` 改为 O(1) 查表 + 按需循环导入，取代 505 条静态 `if` 链（`_bootstrap.py` 7620 → 6121 行）。

**等价性（全量非抽样）**：505 个 stem × 3 种写法 + 真实 R19 双方 108 脚本 + 边界输入的 `want` 集合
**全等，TOTAL FAILS = 0**；三闸 **seed 双态 907/1548、1042/1991 逐位不变 / REG9 9/9 / 60 场 60/60**。

### 12.2 被证伪 ①：并行效率不是内核问题，是外部负载（**推翻 §3.2 的判据基础**）

起因：4 worker 实测 5.46 场/s vs 单核 3.2 场/s，效率只有 **0.40–0.45**——看起来有 2x 空间。
第一反应是 SMT 争抢（4 物理 / 8 逻辑）。**用 `process_time` 逐项证伪**：

| 组 | 亲和性 | p50_cpu/场 | 说明 |
|---|---|---|---|
| serial | 无 | **625.0 ms** | 单进程基准 |
| w4_free | 无 | **687.5 ms** | 并发下每场 CPU 只多 **+10%** |
| w4_p0123 | 0,1,2,3 | 609.4 ms | 四个不同物理核 |
| w4_p0246 | 0,2,4,6 | 593.8 ms | 四个不同物理核 |

**判读（关键）**：`process_time` 已排除被抢占时间，四组相差 **<15%** ⇒ **既没有 SMT 惩罚，也没有 L3 墙**。
`cores_eff` 只有 1.4–1.8 / 4，是因为测量时**外部负载 93–96%**（ZCode/WeChat 等），不是内核并行性不足。

**同时暴露一处历史误判**：`tools/_par_cores.py` 测到「4 worker 每场 625 ms vs 单跑 312 ms = 慢一倍」，
当时极易被读成「内核并行退化」；实际 312 与 625 是**两次不同负载下**的读数（27% vs 95%），不是同一个数。
⇒ **吞吐结论必须带负载，或用 `cores_eff` 归一化**（§9 那条纪律的具体办法）。

**绑核复测（顺带）**：静窗口 2 轮 × 128 场，`0,2,4,6` 中位 **6.34**、`1,3,5,7` **6.18**、
`none` 5.47、`0,1,2,3` 5.56 场/s ⇒ 集合间差 **+16%**，但仍低于负载噪声，**只能算待重测，不能算收益**。

### 12.3 被证伪 ②：`physicsTick` 已内联，`character()` 冗余只值 1.2%

**发现**：物品的 `physicsTick` 并不存在——它已被内联进 `CoreCombat.physicsTick` 的物品循环：

```python
for item in _iter__loc(self.opponent.inventory.getItems()):
    if item._cooldown_active:
        if not (item.character().stunnedDuration > 0):   # ← 每物品每 tick
            item.triggerTime -= delta * item.getSpeed()  # ← 每物品每 tick
            if item.triggerTime <= 0:
                item.trigger()
```

所以「`physicsTick` 84%」指的是**这个循环体**，不是方法调用开销。剩下的可疑项是 `item.character()`
每 tick 每物品都解析一次（51 物品 × 907 tick ≈ **9.2 万次/场**），而物品归属角色**装配后恒定**（已实测 True）。

**实测收益（102 万次调用）**：72 ms → 79 ms，**0.907x（缓存反而略慢）**；单次 `character()` 只 **0.07 µs**，
折算单场 **3.2 ms ≈ 1.2%**。⇒ **这条线不值得做**，§11.1「Python 层见底」的结论成立且更硬。

### 12.4 装配的精确构成（下一步主战场）

`cProfile` 逐函数拆（12 场，表内为**每场**摊销）：

| 位置 | tottime | cumtime | 判读 |
|---|---|---|---|
| `_build_side` 自身 | **16.13 ms** | 29.16 ms | 纯 Python 循环开销：108 物品 × 每物品 0.15 ms |
| `_make_item` | **8.18 ms** | 8.69 ms | `R.C(script)()` + `setup()` + 三组 Vector2 列表推导 |
| `_place` | 2.26 ms | 12.80 ms | 几何 + `_readyInit` |
| `_place_of` | 0.82 ms | 1.04 ms | 每次重建 `collision`/`affected`/`occupied` 三个结构 |
| `load_for` | 0.30 ms | 5.70 ms | ✅ 本轮已消（→0.18 ms） |

**结构性冗余（可做，零语义风险）**：

1. `_build_side` 每物品重复 `self._K`/`k["_R"]`/`k["Vector2"]` 查找与 `getattr(self, "_pending_crafted", None)` —
   提到循环外做局部绑定（与 S3-C6「访问器内联」同型手法，已验证有效）。
2. `_place_of(data, key, row, col, rot)` 里 `r = ent["rot"][str(rot)]` 部分**只依赖 (key, rot)**，
   可缓存「未平移的 anchor/affected/occupied」，再叠加 `(row,col)` 平移——现在每场对同 key 同朝向重算一遍。
3. `it.chargeFrame = [vec(...)] * 4` 与 `collisionCells` 的 `vec()` 逐物品分配：`chargeFrame` 四项同值，
   可共享同一个不可变 `Vector2`（构造期一次性）。

**判读**：这三项合计目标 **28.6 → ≤22 ms（≥20% 降）**。装配占整场约 **11%**，故整场收益约 2–3%；
**这是当前唯一还能拿到确定性收益的地方**（单场 tick 侧已见底）。

### 12.6 一句话

> 单场延迟**三个假设证伪两个**（并行效率是外部负载、`character()` 冗余 1.2%），
> 唯一落地的是 `load_for` 索引化（7.5 → 0.18 ms，41x，装配 −3 ms）。

### 12.8 P2 绑核重测证据（2026-11-13，静窗口 4 轮，负载门控 2–20%）

`python -X utf8 tools/bench_parallel.py --n 256 --workers 4 --aff none --aff 0,2,4,6 --aff 4,5,6,7`
（`_p2b_r{0..3}.json`；单核基线 n=16 同轮测，`core_fps` 5.99–6.17 场/s）

| 集合 | r0 | r1 | r2 | r3 | 中位 tput | 中位 pool_eff | p50_cpu/场 |
|---|---|---|---|---|---|---|---|
| none | 14.98 | 15.79 | 12.65 | 12.97 | **13.98** | 0.567 | 234–313 ms |
| `0,2,4,6` | 14.07 | 14.78 | 15.34 | 13.79 | **14.29**（+2.2%） | 0.588 | 250–266 ms |
| `4,5,6,7` | 10.49 | 11.11 | 11.17 | 10.54 | **10.83**（**−22%**） | 0.446 | 344–375 ms |

**判读**：
① **绑核收益判否**：`0,2,4,6` vs `none` 差 +2.2%（<10% 判据）；r2/r3 里两集合轮换领先，
方向都不稳。§12.2 当晚「`0,2,4,6`=6.34 vs none=5.47（+16%）」的读数被推翻——
当时两轮中位落在负载噪声里（同日志内 `1,3,5,7` 一度 3.15→10.94）。
② **绑错集合有害且可复现**：`4,5,6,7`（Windows 编号下是 0–3 号物理核的 SMT 兄弟线程）
4/4 轮 −22~30%，每场 CPU 时间 +20~60%——同规格 256 场在兄弟线程上做功更多，
是缓存/执行端口与主线程争用，不是调度问题（`cores_eff` 三组都 3.73–3.84）。
③ **并行效率的真实上限**：单核每场 156.2 ms 四轮逐位不变（15.6ms 刻度整 10 格），
而 4 进程并发时每场 CPU 膨胀到 234–313 ms（none，+50~100%）——即使 `cores_eff`
3.8/4（外部负载已除净），`pool_eff` 也只有 0.53–0.66。剩余 34–47% 是**进程间
缓存/内存带宽争用**，属内核可并行度的物理上限，吞吐侧再无可拿的确定性收益。
⇒ **吞吐线有证据收口**（与 §11.7 单场延迟收口并立）。
