### 0.1 判定阈值（本轮修正，**取代旧的 10% 门**）

旧台账用「整场 p50 降 ≥10%」当有效性判据。实测噪声地板（同配置 n=40 重复 6 次）：

| 口径 | 极差 | stdev | SEM | **3σ 可辨** |
|---|---|---|---|---|
| `mean_ms` | 3.49% | 1.25% | 0.51% | **1.52%** |
| `p50_ms` | 7.18% | 3.71% | 1.51% | 4.54% |

**`p50` 的读数落在 `process_time` 15.62 ms 刻度的整数倍上**（实测一半 203.1、一半 218.8），
它的散布一半是量化噪声。⇒ **10% 那道门不是太高，而是用错了口径**：

| 场景 | 判据 |
|---|---|
| **整场改动** | `mean_ms` 降 **≥2%**（3σ=1.52%，留余量）；拿 `p50` 报 2% 级结论一律无效 |
| **微基准（日常）** | **≥1.05x**；≥1.3x 只留给「要不要换语言」这种量级决策 |
| **<2% 的改动** | 进「待累积清单」，凑够 ≥2% 合并测一次（见 §4.4） |
| **零收益但零风险且降复杂度** | **免收益判据**直接合（`load_for` 属此类） |
| 判据本身（`canonical_stream`/`render_lines`/语料） | **永远不许改** |

## 1 纪律（血泪条款）

| 纪律 | 为什么 |
|---|---|
| 账本 mtime 与代码提交时间相近 | 曾出现「声称晚于提交，实际差 1.5 小时」 |
| 编译态结论必须证明 pyd 比源新 | `build_cython` 曾「pyd 存在即跳过」，多轮「重编」空转 |
| **吞吐结论必须附负载，或用 `cores_eff` 归一化** | 同命令场/s 可差 2 倍（5.5–11.7），历史上据此得出的「4w 饱和」「绑核无收益」全被污染过 |
| **跨实现对比的每条「我方浪费」，必须在对方代码里找到对应实现** | N1「lineup 只传一次」凭想象发明，实测 pickle 仅 0.17%；C++ 每场同样建 108 个物品实例 |
| **固定成本要用 1-tick 隔离法测，且 fixed 臂不能用 `light_log=True`** | light 下 `event_count` 不涨 → gate 永不触发，「1 tick」实测跑满 948 tick（本轮首版就这么错） |
| **对比两臂必须同源 lineup + 配对 seed + 断言 ticks 相等** | `native_sim_cpp/lineups/` 与 `lineups/` 是两份不同文件；曾用单 seed 对 12 seed 中位数，得出 2.25x 假差距（真值 1.81x） |
| **⭐ 跨实现对比必须逐字段证明输入同源，不只是"物品数一样"** | C++ `PackedSide` 缺 `activation_order`/`rng_state`/`gem_lens` 三项 case 级覆盖 ⇒ 30 场里 ticks 只 1/30 相同，29 场不是同一局；据此写出的报告结论不成立 |
| **`ticks` 不是跨实现可比指标** | 神谕 `result.txt` ticks=730 而 py 腿同场 881，但事件数 30/30 完全一致 ⇒ 只认事件流 |
| **⚠️ 说「做不到」之前必须先查工具链** | 「GdVal 定义不在 bundle」「无法逐抽追踪」两条论断，实际是 `grep` 写法漏 `alignas(8)`、以及没查 `g++`/`build_windows.py` 就在仓库里 |
| **哨兵值不能与合法值域重叠** | `rng_state` 用 `-1` 当未指定，而它是 uint64、负值是合法 state ⇒ 注入被静默跳过（878→1002 的诡异读数） |
| **⭐ 跨实现对比要逐一列出「我方调用方传了哪些参数」，不只对比核心输入** | `custom_health_multiplier=200` 漏传导致 `run101490_*` 全族 5 场开局 maxHP 45 vs 90；补后 5 场全绿 |
| **改了数组要确认它是「数据」还是「副本」** | 就地重排 `p_items` 连带改掉 inventory 顺序；py 的 `prepareItems` 有 `if item.placed: continue` ⇒ inventory 恒为装配序 |
| **改编译期类型/pxd 后必须全量重编** | 只重编热点模块 → `Item size changed, expected 576, got 24`，21 模块崩（本轮实证） |
| 单点微基准要加大 n | 200k 次时跳动是刻度噪声；800k–1M 才收敛 |
| 看剖面要看总量，不只 top30 名单 | 事件计数回归就是 top1，按名单看永远看不出 |
| `@property` 惰性视图的计数必须 O(1) | 每 tick 访问聚合视图 = 全量物化 |
| 不许重生成夹具 | 会造出 13 场假红 |
| `--force` 不可与 `--skip-godot` 同用；`--cases-json` 不可传全量夹具 | 假阳性 / 脚本写回覆盖 |
| 大文档禁止「读局部 → 整体写回」 | 曾因此截掉 45 行 |
| 判否前先确认判据测的是不是同一件事 | 「object 槽无收益」被用来否定「数值槽」，是循环论证 |
| **进程池不能从 stdin 跑** | Windows spawn 重导主模块；探针必须落文件 + `if __name__ == "__main__"` |
| **⭐ 长时编译前置三查（全过才准启动）** | 2026-11-14 用户纪律：D6/D8/PGO 多轮 10–25min 无效重编（旗标没进 bat/语法错/LTCG 缺失）全因启动前没查完。三查 = ①`py_compile` 构建器与全部待编源 ②**改过构建脚本后必须先用单模块真编一次**，python 读回 bat 文本确认预期旗标（/GL /LTCG /GENPROFILE…）逐个在场 ③确认 mtime 会判 stale（touch 生效）。三查不过 = 修复，**不许带病挂后台** |
| **全量里程碑必须回读账本 `match` 分布** | 「1690/1690」被声明三次，账本实为 1628+62「py 缺产物」——只报总数=没验（§7.1） |
| **编译层回归必须双臂（pyd vs GD_PURE_PY）对跑** | 62 场群崩溃纯 py 臂全绿，单臂永远定位不到（§7.2） |
| **pxd/生成物不可手改** | 重跑生成器即回填；修复必须落在生成器层（`_L2_BLOCKLIST`） |
| **构建清单必须显式排除包根辅助模块** | 否则 `_registry.pyd` 等遮蔽纯 py 语义 → 全树导入段错误（§7.3） |
| **热路径的「探针成本」≠「可省成本」** | 探针折算 43.4 ms，D1 全类型化后实省 1.7 ms，**差 25 倍**（§4.1） |
| **有风险 ≠ 不做，但先备份** | 顺序是「commit+**push** → 隔离分支 → 偏移检测 → 修实现 → 修不动才退」（§4.5）。前提是语义偏移**可检测**（1690 逐行 + 三闸），本项目具备 |
| **高成本方向先要「可测假设」** | G2（C++ 重写）被要求先回答「省哪一项、省多少」；本轮已证伪「消除调用边界」这个理由（编译态只剩 6.1 帧/tick） |

**三闸**：seed 双态 → REG 九场 → 60 场；1690 走里程碑。

## 4 下一步：做什么、什么顺序

> 本节的排序依据是**实测占比 × 可兑现性 ÷ 成本**，不是猜想的收益。
> 成本：S ≤0.5 天，M 1–2 天，L ≥3 天。判据统一用 `mean_ms` 交错 A/B（≥2%）；
> 零风险且降复杂度者免测（§0.1）。
>
> **方向池分两段**（2026-11-14 起）：
> - **A–F 类**：低风险，直接做。
> - **G 类（§4.3 末尾）**：**高风险高收益，但不再是"不敢碰"**。
>   走 §4.5 受控试错协议——先 `commit`+**`push`** 备份，再在隔离分支动手，
>   语义偏移先尽力修实现，修不动才回退。**试错记录进 §4.6**，失败也留证据。
>
> G 类排在 A–F 之后是**前置依赖**，不是"不敢"：详见 §4.3 G 类末尾的三条理由。

### 4.0 排序原则（2026-11-14 修订：**成本不再是约束**）

> 用户明确：**"不太在意时间成本，但模拟器一定要尽可能快"**。
> ⇒ 排序依据从「收益 ÷ 成本」改为 **「收益上限 × 确定性」**：只有**收益上限**和**会不会白做**这两件事能把它排到后面。
>
> 这条变化让我必须撤回之前几条「因为成本高所以排后面」的判断——**那些理由现在作废**。
> 但有两条**不是因为成本**才排后面的，它们仍然成立：
> ① **收益上限已被实测封顶**（H1 的三层证据）② **必然破坏可检测的语义闸**（GPU 浮点归约、惰性触发）。

### 4.0.1 收益上限表（回答"最快能多快"）

**单场 212.5 ms 的四块主战场，各自的上限与依据**：

| 块 | 现值 | 理论下限 | 可省 | 单项加速 | 下限依据 |
|---|---|---|---|---|---|
| **trigger 链** | 96.0 ms | 30 ms | **66.0** | **1.45x** | 215 次×1380µs → C 化后只剩业务逻辑（伤害/事件/联动），解释与派发省掉 |

**组合后的总上限**：

| 做哪些 | 节省 | 单场 | 加速 |
|---|---|---|---|
| 事件系统 | 38.8 ms | 173.7 ms | 1.22x |
| trigger 链 | 66.0 ms | 146.5 ms | 1.45x |
| 事件 + trigger | 104.8 ms | 107.7 ms | **1.97x** |
| 事件 + trigger + 物品 | 121.2 ms | 91.3 ms | 2.33x |
| **全四项** | **141.8 ms** | **70.7 ms** | **3.01x** |

> **关键读法**：没有任何一块可以忽略——单项最好的 trigger 链也只有 1.45x，但**四块叠加是 3.0x**。
> 这正是"成本不是约束"改变结论的地方：以前会因为「物品循环只值 1.08x」跳过它，
> 但在 3.0x 的路径上，那 16.4 ms 和另外三块**同等必要**。

> ⚠️ **这些是上限估算，不是承诺**。下限依据里「20 ns/item-tick」「200 ns/事件」是同类 C 代码的量级参照，
> 未在本内核上实测过。真正的验证方式是按 §4.5 协议逐块做，每块用 `mean_ms` 交错 A/B 验收。

### 4.1 成本地图（2026-11-14 凌晨实测，负载 6.5%，基频 1600MHz 降频态）

**单场 212.5 ms 的构成（full 模式 = 对齐/验证/产品路径）**：

**关键教训（本轮踩到，必须记住）**：

> 热路径的「探针成本」≠「可省成本」。在真实引擎态测：`character()` 11.8 ms + `getSpeed()` 17.6 ms

> 差 25 倍。原因：CPU 的分支预测/乱序/缓存已经把这些属性访问摊平了，微基准里「每次 getattr 独立付钱」
> 的模型在真实循环里不成立。⇒ **判据只认整场 `mean_ms` 交错 A/B，不认探针折算**。

   「消除函数调用边界」不成立 ⇒ 必须先重新论证，否则是拿 XL 成本赌一个未知数。

> **已同步修正 §2.2**：原「换语言 C++/Rust ❌ 已有证据关闭」已拆成两行——
> 被证伪的是「整链 C 化/字段类型化」（1.07–1.10x），**未被证伪的是「整场实现替换」**，后者移入 G2。

#### H 类：两个结构性方向的定论（2026-11-14 凌晨实测后回答）

> 用户问了两件事：① 有办法让模拟器**彻底成为 C++** 吗？② 能否在**保证语义一致**的前提下
> 让战斗逻辑更快？本轮实测后的结论如下。
>
> **⚠️ 2026-11-14 修订**：用户随后明确「不在意时间成本，只要尽可能快」——
> H1 里「成本 10.8 万行所以不划算」这个理由**已作废**。本类保留的是**收益上限的三层证据**
> （与成本无关，是实测封顶）与 H2 的「逻辑已穷尽」结论。修订见 H1 末尾段与 §4.0。

##### H1「彻底 C++」——三层实测封住了「边界开销」，但封不住「数据结构 C 化」

**规模底数**（本轮实测）：

| 项 | 数量 |
|---|---|
| `gd_core/` 模块 | 158 个 / 6554 行（含核心四类：`CoreItem` 3938、`CoreCharacter` 2070、`CoreCombat` 546、`CoreBuff` 553） |
| `gd_core_items/` 模块 | 505 个 |
| 转译后 Python | **108,455 行** |

**收益上限被三层封顶**：

| 层 | 实测 | 含义 |
|---|---|---|
| ① 调用边界 | 编译态每 tick 仅 **6.1 个 Python 帧**（纯 py 臂 455.9）；帧开销上限 **0.7 ms/场 = 0.3%** | 且这 5552 帧**全部在 `simulator/gd_core_engine.py`**（`logEvent`/`kernel()`/事件对象 `__init__`），内核里几乎没有 |
| ② PyObject 拆装 | §11.7 整链 C 化 **1.07–1.10x** | 这是已有的最接近「C 语义」的实测 |
| ③ 内存布局 | 规模曲线两次测量超线性比 **0.35–0.87**（**亚线性**），R²=0.55 | 物品数涨 7.3x、每千 tick 成本只涨 8.7x ⇒ 缓存局部性不是主导 |

**结论（2026-11-14 修订：成本已不设限）**：

三层证据封住的是**「边界开销」**这一类收益：调用边界（0.3%）、PyObject 拆装（1.07x）、缓存局部性（亚线性）。
所以「**因为跨语言边界很贵，换 C++ 就会快很多**」这个直觉**已被实测证伪**。

**但成本不设限后，结论必须改**：按 §4.0.1 的上限表逐块 C 化（trigger 链 1.45x + 事件 1.22x + 装配 1.11x + 物品 1.08x）
**叠加可达 3.0x**。这 3.0x 的来源**不是**边界开销，而是「把每块的数据结构与主循环改成 C 形态」
（SoA 数组、紧凑二进制事件记录、无 Python 对象中间层）。这与三层证据并不矛盾——
三层测的是「同样的代码换个语言」，3.0x 来自「换数据结构」。

⇒ **G2 的定位改为：收益来源已明确 = 数据结构 C 化，不是「换语言」本身**。
真正该做的不是把 10.8 万行翻译成 C++，而是**按 §4.0.1 的四块逐一 C 化**——
505 个物品脚本（占代码量 90%）可以继续留 Python，因为它们多数只在装配期跑一次、
或只在 trigger 里被调几次，不是每 tick 的批量工作。

> 若仍要做，**推荐的不是"彻底"，而是「热路径 C 化」**——把 `CoreCombat.physicsTick` + `trigger` 链这两段
> （占 45.2%+18%）用 C 重写成单个函数，物品脚本逻辑保留 Python。这样只需触及 ~2000 行，而非 10.8 万行，
> 且语义面窄（无物品脚本覆写），可检测性最高。**这已作为 G2 的推荐降级形态记入。**

### 4.7 执行顺序（2026-11-14 15:30 重写：**目标是超过 native_sim_cpp**）

#### 4.7.0 先把靶子立起来

#### 4.8.2 单场延迟：C++ 快 1.86x（**与线程无关**）

> ⚠️ **2026-11-14 15:00 实测修正**：本节的「装配 46.9 ms / C++ ≈0」拆解**错了**。
> 用 1-tick 隔离法（同 lineup、配对 seed、tick 对齐 8/8）重测：
> 我方固定成本 **31.74 ms**，C++ **14.16 ms**（2.24x，**不是 0**）。
> 差距结构因此变为：装配差 17.6 ms（占 28%）+ 净 run 差 45.9 ms（占 72%）。
> 详见 **§4.8.7**。下面保留原始记录以存证。

逐场交替（10 场 × 3 轮，`process_time`，负载约 20%）：

| 口径 | 我方 | C++ | 比值 |
|---|---|---|---|
| light（对齐后） | **203.1 ms** | **109.4 ms** | **1.86x** |
| full（含事件物化） | 234.4 ms | 109.4 ms | 2.14x |

**拆解（这才是关键）**：

4. **`light_log` 陷阱**：fixed 臂若用 `light_log=True`，`event_count` 不增长 ⇒ gate 永不触发，
   "1 tick" 实测跑满 948 tick（我第一版就这么错了）。fixed 臂用 `light_log=False`，装配成本与它无关

### 7.1 ⛔ 假绿记录（最该记住的一条）

「1690/1690 全绿」被声明过**至少三次**，但权威账本 `alignment_expand.json` 当时记的是
**1628 三方一致 + 62「py 缺产物」**。缺口跨多次声明持续存在，没人发现——
因为声明只看了**场次总数**，没回读账本的 `match` 分布。

**规则**：全量里程碑的验收必须同时满足
①账本 `perCase` 里每条 `match` 都是「三方一致」②账本 mtime 与声明同时刻。
只报总数 = 没验。

### 7.2 62 场群崩溃：三元组合的编译层回归

`super(): __class__ cell not found` @ `Greatsword_2.getStaminaCost`。触发条件是**三元组合**：
`cpdef double getStaminaCost`（§11.4 为闭环实验引入）+ plain 子类 `def` 覆写 + 零参 `super()`。
纯 py 臂同场 1/1 全绿 ⇒ **语义层无恙，是编译层回归**。`binding=True` 救不了。

**修复**：`getStaminaCost` 进生成器的 `_L2_BLOCKLIST`（退 plain def 动态派发）——
让 §11.7 早已判为 1.07–1.10x 的微收益换正确性。崩场复验 0/1 → 1/1。

**教训**：①三元组合类回归必须**双臂（pyd vs GD_PURE_PY）对跑**才能定位；
②`binding=True` 修完 binding=False 事故后未做 62 场专项复跑——三闸不覆盖该路径；
③pxd 是**生成器产物**，手动改会被下次生成覆盖，修复必须落在生成器层。

### 7.3 毒树事故：捆批重编把包根辅助模块编成了 pyd

§4.3 捆批（D5/D6/D8）全量重编时，构建清单从「存活 pyd 反推」，把 `_registry`/`_bootstrap`/
`_colors`/`__init__` 这些**包根手写辅助模块**也编成了 pyd → 加载器 pyd 优先遮蔽纯 py 语义 →
全树导入段错误。**当时所有旗标二分全部无效**，因为测试树本身被污染。

**护栏**：`build_cython.py` 新增 `_FORBID` 四文件拒绝闸；构建清单固定为 664 模块
（`_all_list2.txt`）。
