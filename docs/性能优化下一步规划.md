### M0 已完成（2026-11-10 晚，替代方案，未改电源）

用户裁定**先不动电源**，改用「方差免疫」的测量口径。已落地三件工具：

| 交付 | 路径 | 作用 |
|---|---|---|
| CPU 计时 + 热身 | [tools/bench_sim.py](tools/bench_sim.py) 参数 `--cpu-time` / `--warmup` | 用 `process_time` 替代 `perf_counter`：排除降频/抢占造成的墙钟等待 |
| 交错 A/B | [tools/bench_ab.py](tools/bench_ab.py) | 每轮交替跑两个臂（各自独立子进程），只比**配对差值**；奇偶轮反向抵消轮内漂移 |
| 纯 py 臂 | [tools/_purepy_arm.py](tools/_purepy_arm.py) | `GD_PURE_PY=1` 经 `sys.meta_path` 屏蔽扩展加载 → **不删 .pyd 也能跑源码臂** |

**实测对比（同一命令、同一机器）：**

| 口径 | 单臂散布 | 结论 |
|---|---|---|
| 墙钟 `perf_counter`（旧） | **68%** | 不可用 |
| CPU `process_time` + 热身 | **4.8% / 13.6%** | 可复现 |
| 配对 A/B 比值（n=40, 5 轮） | `cy/py = 1.0749`（散布 18.6%） | 编译臂约快 7.5% |

**散布 18.6% 的原因**：Windows `process_time` 实测粒度 **15.62ms**（1/64 秒系统节拍），单场 ~320ms 只有约 20 个刻度。要更稳就**加大 n**（n=40 约 12.5s/臂）或增加轮数——是分辨率问题，不是方法错。

**顺带纠正一个此前的误判**：机器是 **HP ProBook 440 G6（4P/8L、基准 1.6–1.8GHz、插电 100%）**，并非「被锁到 800MHz」；波动来自睿频频繁开关。`--pin` 失败是 `SetProcessAffinityMask` 被拒，已记录，未强改系统。

**M0 剩余（可选，非阻塞）：**

- `--pin` 改用 `psutil.Process().cpu_affinity()` 重试；仍失败则记档「本机不支持绑核」
- 记分卡加 `bg_load` 字段（跑前采一次 CPU 负载，>15% 的数字标灰）
- 想要与 v0.5.2 的 207ms 对齐的绝对数字，仍需用户同意改电源（M0-1，默认不做）

> **给接手者的第一句话**：任何优化结论都用 `tools/bench_ab.py --cpu-time --n 40` 出**比值**，
> 不要用 `bench_sim.py` 的绝对值；报数字时同时给 `spread_ratio_pct`，>5% 就加大 n 重测。

### M1 Cython 类型化（1–2 周，主收益）

**现状：现在是「纯编译」**——`cython -3` 直译，**零类型注解、无 .pxd、无编译旗标**。
这档收益通常只有 1.2–1.5x；真正到 3–6x 的是**类型化**。今天 1690 全绿说明编译态本身安全，可以放心往上加类型。

| 编号 | 做法 | 预期 | 判定 |
|---|---|---|---|
| M1-1 | 手写 `gd_core_py/_rt.pxd`：`f32`（`double→float→double` 用 `float` 中转）、`_div/_mod`（`long long`）、`PCG32`（`unsigned long long` state/inc） | 5–10% | ✅ **已落地**（`0f00905a`）：pxd C 常量+cdef class PCG32+局部注解；RNG 逐位 1440/1440、seed 双态、60/60、REG9 全绿；墙钟 <测量地板（0.94→0.86µs/抽），机制实证见 §4 末尾——M1-2 的地基 |
| M1-2 | 生成器输出 `.pxd`：给 `_init_fields` 里的声明字段生成 `cdef public` 槽（仅 `float/int/bool` 面，Variant 保持 PyObject） | 15–30% | 🔶→**机制已落地**（`18c4c971`）：GodotObject 转 cdef 基座（_gd_conns 迁正式槽、has_method 字典守卫）+ 生成器伴随 .pxd 发射（`_PXD_WHITELIST` 起步=CoreEvent，8 object 槽）；60/60+REG9+seed 双态全绿。**白名单扩展工序**（每类）：① grep 引擎/工具侧对该类实例的未声明属性赋值（CoreContext 有 label_rng_enabled/below_master/custom_health_multiplier 等 6 个引擎赋值面，必须一并声明或改造）；② 重跑生成器同步 pxd；③ 重编该 .pyd；④ seed 双态+60 场+REG9。数值 C 类型（float/int 槽）须先审计字段全部赋值域（None 混入即 TypeError），object 槽先行 |
| M1-3 | 热 8 模块的 `cdef class` 化（先 `CoreRng`/`CoreTimer`，后 `CoreBuff`） | 10–20% | 🔶 |
| M1-4 | 编译旗标：`binding=False`、`embedsignature=False`、`freelist`、`/O2` 已有 | 3–8% | ✅ |
| M1-5 | `-fno-semantic-interposition`+LTO（MSVC `/GL /LTCG`） | 2–5% | 🧪 |
| M1-6 | 局部变量用 `cdef double` 声明（在生成的 tick 函数内） | 视函数 | 🔶 |

**M1 的闸门比以往更严**：每个 `.pxd` 批次都要跑 **seed 逐位（907/1042）+ REG 九场 + 60 场 + 1690**。
类型化改的是**数值路径**，一个 `double` 写错就能让 f32 舍入漂移——这是本项目历史上最贵的一类 bug（见 v1 §0 的 `randf` 链）。

**M1-1 已落地（2026-11-10 深夜，`0f00905a`）**——`_rt.pxd` + 局部 C 类型，四闸全绿
（seed 双态逐位 / RNG 1440 值逐位 / 60 场 / REG9）。墙钟收益低于测量地板
（PCG32 微基准 0.94→0.86µs/抽），定位为 M1-2 的地基。**给 M1-2 的机制实证
（最小 C 文件实验，省下探索时间）**：

1. **Cython3 安全推断把未注解局部量留在对象域**——pxd 里的 `cdef` 模块常量
   /cdef 类属性**不会**自动让用它的表达式变 C 运算；热路径局部量必须显式
   注解（`old: cython.ulonglong = self.state` 才出 `unsigned PY_LONG_LONG`）。
2. **字符串注解（`x: "long long"`）只告警不生效**（编译态 PyObject 不变）；
   裸 `int` 注解映射为 **Python int 对象而非 C long**（Cython3 破坏性变更，
   Windows 上 long 是 32 位，慎用）。**必须用 `cython.longlong` / `cython.ulonglong` /
   `float`（→C double）**，生成器发注解时照此选名。
3. 伴随 .pxd 模式已验证可用：模块级 `cdef unsigned long long X`（声明在 pxd、
   赋值在 .py）+ `cdef class`（.py 类体作定义体，`__slots__` 被静默容忍）；
   `_rt.pyd` 用它编过（`build_cython --msvc` 零改动，伴随 .pxd 自动拾取）。
4. 局部注解在纯 py 运行态不求值（PEP 526）——生成器发注解零运行时风险；
   `import cython` 需 guarded（`try/except ImportError`），编译态被拦截为 no-op。

**M1-2 槽位化机制实证（`_m12_probe` 实验 + `18c4c971` 落地，2026-11-10 深夜）**：

1. **伴随 .pxd 声明 cdef class + .py 保持普通 class 体** = 官方支持的拆分形态；
   `build_cython --msvc` 零改动自动拾取同名 .pxd。cdef 体里允许**运行时调用类
   属性**（CoreEvent.Target = EnumDict(...) 实测合法），resource_path 字符串类
   属性同合法。
2. **cdef 实例无 `__dict__`**：未声明属性赋值编译态 AttributeError（形态漂移
   即时暴露）；double 槽拒绝 str、接受 int（3→3.0，与 GDScript var float 一致）。
   `has_method` 的实例字典守卫改 `getattr(self,'__dict__',None)` 后对 cdef 实例
   自然退化为「只查 property」。
3. **普通 Python 子类继承 cdef 基类：保留 `__dict__`**——探针类实例影子
   （light_log 的 `self.hooks.logEvent = lambda`）、引擎对 plain 子类实例的动态
   赋值全部不受影响；白名单外的 663 类保持 plain，行为零变化。
4. **property 不是槽**：`self.id = v` 走 setter，槽是 setter 体内的后备 `_id`——
   生成器收集器须排除 property 名（@property 是 Name 装饰器），否则误报影子。
5. **信号连接表**（`_gd_conns`）原存实例 `__dict__`，cdef 化后迁正式槽
   （`cdef public object`，None 初值双保险：对象槽分配即 None + _init_fields）。
6. 跨模块零 ABI 耦合：各 .pyd 独立编译，跨模块属性访问仍是运行期派发——
   未转换模块引用 CoreEvent 实例无需重编（本批实证：仅编 _rt+CoreEvent，
   CoreCombatLog.pyd 旧产物照常跑绿）。

### 9.2 关键测量：瓶颈已经不在「解释器」了

> **现在的时间不是花在「Python 解释器派发」上，而是花在「PyObject 语义」上**——
> 每次属性访问要过 `PyObject_GetAttr`、每个 `dict` 查找要过哈希、每个 `CoreEvent` 要分配一个堆对象。
> Cython 纯编译只是把字节码换成 C 调用，**这些 PyObject 开销一分没少**。

### 9.3 换语言（C++/Rust）判定：**本阶段不做**

上一版 §4 的 M5 写的是「C++ 条件触发」，当时的依据是「h≈0.65 的 cProfile 分布」。现在这个前提被实测推翻了：

| 判据 | 上一版假设 | 现在实测 | 影响 |
|---|---|---|---|
| 解释器执行占比 h | ≈0.65 | **≈0.13**（logEvent 一簇） | 换语言吃掉的部分远小于预期 |
| 编译 vs 源码差 | 1.2–1.5x | **1.075x** | 语言层已接近饱和 |
| 剩余大头 | tick 循环 | **PyObject 属性/dict/分配** | 换语言**也**要重写数据模型才能吃到 |

**所以：C++ / Rust 整场 FFI 在 M1-3 之前做，端到端上限约 1.1x，完全不值得 1–2 个月。**

更关键的是：**M1-3（热 8 `cdef class`）本质上就是把对象图从 PyObject 换成 C struct**——
做完之后，Cython 编译的代码已经和手写 C++ 同构，此时再换语言只剩「语法不同」的差别。

因此本规划把「换语言」**重新定义**为下面这一件事，而不是语言迁移：

### 9.4 换语言真正值钱的地方：nogil 并行（吞吐，不是延迟）

训练 AI 要的不是单场 300ms 变 150ms，而是**每秒能跑多少场**。当前现实：

| 口径 | 实测 |
|---|---|
| 单核 | 约 2.8–3.2 场/s |
| 4 worker 进程池 | **5.51 场/s**（≈2.0x；受 4 物理核 + 睿频限制） |
| 8 逻辑核理论上限 | ≈6–7 场/s（进程池口径） |

进程池的上限由**物理核数**决定，且每 worker 要付一份 1.2s 级启动 + 独立内存。
而 **Cython 的 `nogil` 线程池**在对象图全 cdef 之后可以同进程多线程真并行：

- 收益：省掉 N 份解释器/模块状态内存与启动（短批次尤其明显）
- 代价：要求被并行的那段**完全不碰 PyObject**——也就是必须先完成 M1-3

**触发条件（写死，避免提前上）**：

1. M1-3 完成（≥6 个热模块 cdef class 化，且四闸全绿）；
2. 训练侧实测吞吐缺口：进程池在目标机型上 **< 8 场/s** 且需要 ≥20 场/s；
3. 单场 p50 已 ≤150ms（即延迟优化接近尾声）。

三条同时满足才投入；否则停在 Cython。

### 11.2 关键发现：源码里本来就有类型信息

转译器**没有利用 GDScript 自己写的类型注解**——这是最便宜的一笔：

### 11.3 转译收益分四层（按性价比排序）

#### L1：items 行为树扩白名单（10–25%）

**为什么是最大一块**：gd_core 树 12 模块已 cdef（含 `CoreItem`），但**物品行为脚本 141 个仍 plain**——
而 tick 循环里最热的就是逐个物品调 `physicsTick` / `getSpeed` / `trigger`，这些对象全部有 `__dict__`。

**阻塞点已查清，只有 4 个补充槽**（`_PXD_EXTRA_SLOTS` 同款机制可直接用）：

| 补充槽 | 来源 |

| `occupiedCells` | 装配期按 lineup 坐标写 |
| `faceDirection` | 装配期按 rotation 写 |
| `chargeFrame` | np25 P3-3 电荷格旋转系 |

**注意**：`SignalConnection` 这类同模块辅助类保持 plain（有 `__dict__`，探针/light_log 依赖它）。

#### L2：方法 cpdef 签名（10–20%）

现在所有方法调用仍是 Python 属性查找 + 参数打包。**169 个返回注解 + 68 个形参注解**可以机械生成：

```python
# pxd 里（示意）
cdef class CoreItem(GodotObject):
    cpdef bint hasType(self, int t)
    cpdef double getSpeed(self)
```

**安全边界（必须写进实现）**：只对**注解完整且返回单一类型**的方法生成 cpdef；任何 Variant 返回（`object`）保持 `def`。
原因：cpdef 的返回类型是**编译期强制转换**，把 `None` 转 `double` 会直接抛异常——本项目大量方法在 GDScript 里返回 `Variant`，盲改必炸。

#### L3：槽位数值 C 类型（5–10%）

195 个已注解字段可换成 C 类型槽。收益在于**省掉 PyObject 的引用计数与装箱**，但风险高于 L1/L2：

**必做审计（逐字段，不能机械全改）**：
1. 该字段**全部赋值点**是否都是同一类型（`None` 混入即炸）；
2. 是否被外部（引擎/工具）赋过 `None` 或其它类型；
3. 是否被 `getattr` 动态读取（例如 `_side`/探针按名字取值）。

**建议起点**：只做 `bool` 与 `int`（无浮点舍入语义），`float` 面留到最后（f32 语义敏感）。

#### L4：生成器级代码变换（5–15%，风险最低但零散）

| 变换 | 做法 | 依据 |
|---|---|---|
| **死代码消除** | GDScript 里 `if false:` / `if OS.get_environment(...)` 类门控，转译后仍是运行时判断；静态可判的整块删除 | 需先证明无副作用（同 M2-1 空钩子那套断言） |
| **常量折叠** | `2.0 * PI` / 枚举字面量在生成期算好，避免运行时运算 | 只对**字面量与常量**，不碰含 rng/状态的表达式 |
| **属性链压平** | `self.ctx.combat.combat_time` → 生成期提为 `_loc` 局部绑定 | M2-4 已手工做过一批，可机械推广 |
| **重复模式合并** | `_div/_mod` 的 `__loc` 别名已在 C15 做过；可扩到 `_gd_fmt` 等 | 低收益，收尾做 |

### 11.6 每一项的止损

- L1：单个 items 模块 2 天过不了闸 → 该模块保持 plain（不回滚全局，白名单可增量）
