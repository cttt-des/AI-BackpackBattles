## C 仍开放：算法层（当前唯一有实证空间的方向）

### C-1 为什么是「调用次数」而不是「单次成本」

`profile_v14_purepy.json`（n=3，top30 共 **116 万**调用）：

| 调用 | 3 场合计 | 冗余点 |
|---|---|---|
| `CoreItem.character()` | **245,820** | 虚派发；`getSpeed`/`getStackSpeedMods` 每次各调 1–2 次 |
| `_rt.f32` | 138,806 | float32 垫片，已做整数值快路径 |
| `getCold` / `getHeat` | 各 **71,986** | `getStackSpeedMods` 一次调两个 |
| `CoreItem.getSpeed` | 71,986 | tick 内每物品至少一次 |
| `CoreBuff._tick` | 54,032 | — |
| `_rt._iter` | 51,190 | C1 已消 91.4%，残量是 float/dict 形态 |
| `PCG32.next_u32` | 45,322 | — |
| `isItemAffected` | 32,448 | 影响格判定 |
| `EnumDict.__getattr__` | 29,854 | 枚举点号访问漏网 |
| `isBag` / `_hasBehaviorMethod` | 各 2.8 万 | 行为派发判定 |
| `Vector2.__hash__` | 24,006 | 格集 set 操作 |

**推论**：L1-Q 证明「压低单次成本」已榨干（槽位化只省数十 ns/调用）；
但 `getSpeed` 一次调用会连带 2 次 `getHeat/getCold` + 1–2 次 `character()`，**调用次数仍有结构冗余**。

### C-2 候选与判据

| 编号 | 项 | 预期（调用数） | 风险 | 验收 |
|---|---|---|---|---|
| **A-1** | `getStackSpeedMods` 合并 heat/cold 读取（本地 `ch = self.character()`） | 消 ~7.2 万 `character()` | 低 | 调用数 + 三闸 |
| **A-2** | 生成器趟：同函数内 `self.character()` 重复调用局部绑定 | 消 ~14 万 | 低-中（须排除副作用/可覆写改状态） | 调用数 + 三闸 |
| **A-5** | `_hasBehaviorMethod` 缓存（复用 C6 派发矩阵；`set_script` 须清表） | 消 5–6 万 | 中 | 调用数 + 三闸 |
| **A-4** | `EnumDict.__getattr__` 残量 → 直接下标 | 2–4 万 | 低 | 调用数 |
| **A-6** | `isItemAffected` 空间预筛（先 bounding box 后逐格） | 视分布 | **中（语义面：影响判定）** | **必须逐位等价** + 三闸 |
| **A-7** | `_iter` 残量（float/dict 形态） | 低 | 低 | 调用数 |
| **B-1** | 装配复用实验（先量深拷贝成本） | ~13% 装配占比 | 中 | 单场微基准 |

**优先级**：A-1+A-2（同一类变换，0.5 天）→ A-5（1 天）→ A-4（0.5 天）→ A-6（可选，1 天）→ B-1（实验）。
**合计预期**：A-1+A-2+A-5 消 **约 26 万调用/3 场（top30 的 22%）**。

| 根因 | `events` 改成 `@property` 按需物化后，`run` 主循环仍用 `len(self.log.events) > gate` **每 tick** 判定 → 每次访问全量构造 1548 个对象，907 tick ≈ 140 万次/场 |
| 修复 | `_LogMixin.event_count`（O(1) 不物化）；run 判停与 `result_json.num_events` 改用它；`bench_sim` 两处同步 |
| 结果 | top30 总量 **2,814,015 → 30,603（−98.9%）**，`_EventOut.__init__` 归零 |
| 闸门 | 60/60、REG 九场 9/9、seed 双态逐值不变（907/1548、1042/1991） |
| 提交 | `5bb84d6b` |

**教训（并入 §D）**：`@property` 化的惰性视图，**计数必须走 O(1) 属性**；
任何「每 tick 访问一次聚合视图」的写法都要先看它是否会全量物化。
这条回归在 L1-Q、A 类全部验收里都没被调用数剖面抓到——因为剖面只统计 top30，
而它自己就是 top1（**看总量而不是看名单**才抓到）。

## H 修正：L3 数值槽被判否是**错的**（2026-11-12 凌晨，微基准实证）

> 本节推翻 §B-2 里「L3 门未过」的判定。**判否依据本身不成立，是循环论证。**

### H-1 我错在哪

§13.3 定的门是：`L1-Q ≥1.2x 才做 L3`。但 **L1 做的是 `cdef public object` 槽**——
object 槽只是省掉 `__dict__` 查找，**数值仍要装箱/拆箱**。用它去证明「数值槽没用」，
等于用「A 没收益」去否定「B 有收益」。

### H-2 微基准（`object` 槽 vs 数值 `cdef` 槽，5M 次，process_time 中位）

| 形态 | 耗时 | 每次 |
|---|---|---|
| `cdef public object` + 算术赋值 | 0.2031 s | **40.62 ns** |
| `cdef public double` + 算术赋值 | 0.0156 s | **3.12 ns** |
| `object` 槽属性读 + 减法 + 乘法（模拟 `getSpeed`） | 0.3438 s | **68.75 ns** |
| `double` 槽同式 | <0.0001 s | **≈0（被优化器消除）** |

**差 13x（算术）/ 数十倍（含读取）**。这不是「省几十 ns」，是**两个数量级**。

### H-3 现成的实证就在项目里

`PCG32` 是唯一把状态声明成 `unsigned long long` 的类（`_rt.pxd:38-39`），
它的单点实测是 **1.9x**（0.94 → 0.47 µs/抽）。**同一个项目、同一套工具链、同一个测量手腕**——
数值槽有效这件事早就有证据，只是当时被归因为「`_rt` 类型化的功劳」，没意识到可推广。

### H-4 现状：741 个 object 槽，0 个数值槽

```
cdef public object  : 741 处
cdef public bint / long long / double : 0 处（PCG32 的 u64 是唯一的例外）
```

生成器 `_l3_numeric_types` 的机制**早就写好了**（`.gd` 声明类型 → `bint`/`long long`，
`float`/未注解排除），只是首行 `return {}` 把发射禁掉了（`gd_to_py.py:3661`）。
**解锁它只需要删一行 + 编译迭代。**

### H-5 重开 L3（优先级高于任何新方向）

| 步骤 | 内容 | 风险 |
|---|---|---|
| 1 | 删 `_l3_numeric_types` 首行 `return {}`，重转写 | 低 |
| 2 | 编译 gd_core 树，失败模块逐个加 `_L3_BLOCKLIST` | 中（编译态 `TypeError` 会立刻炸，不静默） |
| 3 | **只做 `bool`→`bint` 与 `int`→`long long`**；`float` 面**暂不做**（f32 语义敏感） | 低 |
| 4 | 三闸：seed 双态 → REG 九场 → 60 场 | — |
| 5 | 单点微基准对比（`getSpeed`/`physicsTick`/`gainStacks`），判据 ≥1.2x | — |
| 6 | 1690 里程碑 | — |

**必做的三个检查**（每条都对应一种已知爆炸形态）：

1. **字段可能被赋 `None`** → 编译态 `TypeError`。加 `_L3_BLOCKLIST` 退回 `object`，**不要 try/except 兜**（兜住就变静默错）。
2. **字段被引擎/探针动态赋值**（`_PXD_EXTRA_SLOTS` 机制）→ 若补槽是数值类型，外部赋 `None` 会炸；外部补槽一律保持 `object`。
3. **`int` 溢出语义**：GDScript int 是 64 位，`long long` 同宽，但生成代码已显式 MASK64 的位置要保持掩码；`long long` 有符号，`MASK64` 结果超 `2^63` 会溢出——**这类字段改用 `unsigned long long` 或保留 `object`**。

### H-6 顺带修正「换语言」的判定

§9.3 当时算 h≈0.13 用的是「logEvent 占 13%」，**这是把旁路当成了解释器执行**。
真实情况是：`physicsTick` 占 83.7%，它**已经是 C 代码**，但内部全是 `PyObject` 数值运算
（读 `object` 槽 → 拆箱 → 算 → 装箱 → 写回）。だから 83.7% 的「C 时间」里有相当比例是
**PyObject 常数因子**，不是算法本身。

**换语言（C++）能消掉这个常数因子，但 L3 也能——而且便宜 20 倍。**
→ **先做 L3。做完若 `physicsTick` 仍占大头且单点没到 2x，再谈 C++。**
