> 基于 2026-10-06 三个探查代理的证据链设计。目标：模拟器（gd_core_py，与 gd_core 同步）

> 生成日期：2026-10-06

## 1. 根因（三个探查代理证据链汇聚）

**gd_core 移植时把原版"表现层 rng 消耗"整体删除了，而原版在战斗判定链中途持续消耗
同一全局 rng 链（Util.rng）**——导致从 preCombatStart 冷却抖动起的每一次掷点全部错位。

量化证据：
- 914 场可比对局中 90.4% 分歧归因 rng-mechanism（全局链消耗面不一致）
- 唯一 3 场全对齐的用例是**双方背包 0 物品**的场（无物品→无命中→无表现消耗→流不错位）；
  ≥12 物品的场 **0% 对齐**——0/1 硬边界
- 63% 的首分歧在 t=0 激活期；>50 才分叉的仅 0.4%
- 判定逻辑本身经逐行抽查是忠实的（trigger/advanceCooldownPercent/activate/takeDamage/
  gainTemporary 全部逐行等价）——**重写不必要，缺的是 rng 消耗面的等量还原**

原版在判定链中途消耗 rng 的位置（gd_core 已删除，需还原等量消耗）：

| 位置 | 消耗次数 | 源码依据 |
|------|---------|---------|
| 受击伤害飘字位置+方向 | 2 次 randf_range | Character.gd:526-527 → :665-668 |
| 受击动画播放速度 | 1 次 randf_range(0.9,1.1) | Character.gd:625 |
| Buff 标签坐标（resist/reflect/protect 时） | 2 次 randf_range | Buff.gd:125/140/237 → Character.gd:688-691 |
| 战怒 pick_random | 全局链 | Character.gd:326（gd_core:278 误改 ctx.rng） |
| 受击动画 playback_speed（伤害>0 时） | 1 次 randf_range | Character.gd:625（damageAnimation.playback_speed） |

## 2. 三阶段消耗链对齐

原理：原版在战斗判定链中途持续消耗全局 rng → 把这些消耗还原到模拟器的相同位置，
两边从同一 state 起跑后每次掷点就完全对齐。三类消耗解耦，逐类对齐：

### 阶段 1：战斗期消耗对齐（证明战斗判定逻辑一致）
- 神谕在**战斗开始时刻** dump rng state（P2 已有 read_rng_state；神谕侧补一行导出）
- gd_core_py / gd_core 用 **state 注入**（P1 已实现 set_state）从该 state 起跑
  ——绕开装配期消耗差异，隔离战斗期
- 逐行比对战斗期事件，分歧即战斗逻辑/数据 bug → 修复循环
- **退出标准**：全部 917 场战斗期事件逐行一致

### 阶段 2：装配期消耗对齐（证明装配顺序一致）
- 改回"种子在装配前设置"约定，逐场比对装配期消耗次数（神谕 rng_log vs 模拟）
- 差异点 = 装配顺序或 BalancedRng 初始化差异 → 修复
- **退出标准**：同 seed 下不注入 state 也逐行一致

### 阶段 3：表现/视觉期消耗对齐（证明与未修改原版完全一致）
- 从 1.1.8 源码全量枚举 Util.rng 消耗点（六族签名对账：
  randf_range(0.2,-0.2)/(0.9,1.1)/(-50,50)/(-70,70)/(0.8,1.2)/(100,160)）
- gd_core/gd_core_py 在相同位置还原等量消耗
- **退出标准**：注入种子 S 的重放与神谕逐事件 100% 一致（含视觉消耗），917 场全绿

## 3. 伴随修复（与三阶段并行，来自前次探查的 R2/R3）
