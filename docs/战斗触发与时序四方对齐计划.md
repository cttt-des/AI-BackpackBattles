# 战斗触发与时序四方对齐计划

本轮只执行触发和时序修复。以现有 1.1.9 Oracle、阵容和数值为基线。原版战斗脚本和原生 Godot 的调度行为用于确定修复目标。完成标准是 Oracle、GDScript、Python、C++ 在本计划覆盖的场次中全部通过同一口径的验收。

## 起点与验收口径

- 装配体力重算已按原版顺序修正。原先分歧的 10 场和额外 20 场，在独立重录目录中通过了 Oracle、GDScript 和 Python 三方验收。正式 1690 场账本仍对应重录前的语料。复用 [30 场验收账本](../output/_handoff10/original_order/alignment.json) 和 [阶段报告](A阶段修复报告_两处真因.md)。
- 既有 C++ 全量结果校验胜负及事件数差值。本轮使用 C++ 已有的逐事件调试导出，比较事件顺序、tick、事件类型、双方归属、来源、参数和父事件，并核对胜负与自然终局。原始流水保留，归一规则沿用现有 Oracle 比对规则。终局合成行仅在确认双方都具有等价终局记录后映射。记录 C++ 调试导出无法表达的字段，补齐有战斗语义的字段后再出具四方结论。参见 [三方比较入口](../tools/verify_oracle.py) 和 [C++ 逐事件工具](../native_sim_cpp/tools/_cmp_events.py)。
- 四路共享同一用例清单、阵容、种子、注入时点、预排序、宝石槽、血量、体力、回复和冷却分支。夹具中的时序覆盖应逐项登记。超时、缺产物、跳过和输入不一致单列为失败。胜负口径相同且事件数相同的场次仍要完成逐事件比较。

## 执行步骤

1. **先建立四方基线。** 复用已重录的 30 场，建立 C++ 逐场比较入口，输出首个分歧及其附近事件。追加能覆盖卡组、光剑、临时 Buff 和同帧致死的定向用例。选取不含这些机制的正常场次作为回归对照。
2. **核实卡组点火和逐张连锁。** 先在原生 Godot 中测定 `call_deferred` 在激活和判胜边界上的行为，包括回调内再次入队。对照首张入队、首张激活、后续卡牌接续和同帧致死。已有实现通过定向验证的部分，直接保留验证结果。参见 [原版卡组](../decompiled_full/Items/DeckofCards.gd)。
3. **验证体力与药水。** 以 30 场重录为入口，核对玩家和对手从装配到开战的体力余额，追踪扣除前信号、药水判定、Bionic Armor 分支和后续攻击。优先验证已有修复在 C++ 链路上的结果。参见 [原版体力重算](../decompiled_full/Core/Character.gd) 和 [Oracle 准备阶段](../oracle/oracle_fight.gd)。
4. **核实光剑和临时 Buff 计时器。** 用原生 Godot 实测 `idle_frame` 与 `call_deferred` 的先后、同值重启、多个计时器同时到期和回调内重启。对照光剑关灯、Buff 替换和到期、疲劳触发，按首个分歧单点修复 Oracle。再同步 GDScript 及测试镜像，更新 Python 和 C++ 生成产物。参见 [Oracle 手动计时器](../oracle/oracle_fight.gd)。
5. **扩大回归并收口。** 每项机制先过定向样本，再用独立输出目录重录并检查 914 场基线和 1690 场扩样。逐条读取四方结果，核对用例集合、完成状态、胜负与事件。记录修前后胜负翻转及其物品分布。用相同对手和种子比较代表性 A/B 摆盘的胜率差，并记录排序或 2 个百分点接受决定是否改变。参见 [配对评估实现](../trainer/evaluator.py)。

## 可并行交接

适合交给另一位 agent 的任务是 **C++ 逐事件验收工具**。它可以在 Oracle 调度修复期间独立推进。

> 从 `output/_handoff10/original_order/` 读取 30 场 Oracle、GDScript、Python 的已验收产物。复用 `native_sim_cpp/tools/_cmp_events.py` 的调试导出，以及 `tools/_full1690.py` 经验证的 C++ 装配路径，增加可指定夹具、参考回放、GDScript 产物、Python 产物、DLL 和输出目录的比较入口。先核对胜负、自然终局和已有逐事件字段，再给出逐场 JSON、首处分歧及命令。明确区分输入不符、表示差异和战斗语义差异。把修改限在 C++ 验收工具，发现需要调整共享引擎或事件导出 ABI 的地方时，先记录具体缺失字段和用例，交给主修复任务统一处理。

主任务负责原版调度取证、Oracle 与三套内核的机制同步、四方全量复验。并行任务使用独立输出目录，集成时使用同一份用例清单、夹具和构建标识。

## 完成条件

- 定向样本、914 场基线和 1690 场扩样各自做到四方全量通过。逐场报告中的缺产物、截断和战斗语义分歧均为零。
- 交付可复跑的命令、逐场账本和修复前后胜负对照。原版实机抽验和四实现对拍分别注明覆盖范围。四方对齐证明的是同版本、同输入下的实现一致性。

## 当前验收结果

- 原生 Godot 3.6 探针确认物理段的 deferred 先于 idle_frame，嵌套 deferred 在同一轮执行。拆分两个队列后，50 场参考回放的事件和胜负均与修前一致，Oracle、GDScript 和 Python 逐事件通过。证据在 `output/_timing_four_way/phase_replay/`。
- 原生一发计时器到期会停倒计时，脚本的 MultiTimer.stop() 会清除排队项。修复后 50 场四方通过，其中 20 场事件变化、2 场胜负翻转。证据在 `output/_timing_four_way/multi_replay/`。
- 临时 Buff 重启由显式标记触发重新同步。最新 65 场四方通过，含前 50 场中的 2 场事件变化和 0 场胜负翻转。默认 C++ DLL 已同步，复跑 65/65。C++ 仍按现有宝石来源口径比较，49 场的调试流只有通用宝石标记。[默认 DLL 账本](../output/_timing_four_way/cpp_default_checked/summary.json)和[替换前 DLL](../output/_timing_four_way/cpp_buff/previous_default/libgdcore.dll)。
- C++ 初次交接账本使用了与 GDScript 回放不同的冷却档和激活排序模式，也将整数和等值浮点视为不同。校正输入、数值、tick 和伤害来源后，原 30 场逐事件及胜负验证均为 30/30。证据在 `output/_timing_four_way/cpp_baseline_checked/`。
- 原生探针还表明物理 Timer 到期早于节点的 `_physics_process`。改变顺序的独立实验通过 14/14 场四方验收，较主补丁有 12 场事件变化和 0 场胜负翻转。[隔离构建账本](../output/_timing_four_way/physics_first_probe/cpp_checked/summary.json)。
- 围绕两场已确认的胜负翻转，分别选取同轮 8 个对手和每个对手 8 个固定种子，对原布局和合法挪位进行配对复算。交换 Snowball 与 Amulet of Fortune 的候选从领先 1.56 个百分点变为落后 1.56 个百分点，两版都低于 2 个百分点的接受阈值。候选排序和接受决定仅用来报告影响。[配对结果](../output/_timing_four_way/paired_layout_check.json)。
- 主补丁的 914 场、1690 场均已启动全量重录，入口依次为 `python -X utf8 output/_timing_four_way/run_base_checkpoint.py` 和 `python -X utf8 output/_timing_four_way/run_full_checkpoint.py`。每个入口使用独立 Oracle 副本、录制产物和验收账本。[914 场日志](../output/_timing_four_way/full_buff_base.log)和[1690 场日志](../output/_timing_four_way/full_buff_expand.log)。
