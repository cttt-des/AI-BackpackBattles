# 战斗触发与时序四方对齐计划

本轮从 1.1.9 的触发和时序修复起步，现按用户后续指令迁移至本机安装的 1.1.10，并重录 914 场基线和 1690 场扩样。原版战斗脚本和原生 Godot 的调度行为用于确定修复目标。四方验收与原版独立回放分别记录覆盖范围，四方内部一致不代替原版验证。

用户补充约束：模拟器要在保证逐事件一致的前提下尽可能精简逻辑、提高模拟速度。完整原版场景仅用于真值录制和差异定位，不能把场景树、界面、动画和刚体系统搬入模拟内核。确实影响随机链的表现层副作用应按源码提取最小实现，并记录必要的重放输入；不得用按场次补抽、在战斗过程中强制覆盖 RNG 状态或复用预期事件来掩盖战斗分歧。每批内核修复同时记录一致性验证与性能影响，性能数据需注明事件导出和日志是否启用。

## 起点与验收口径

- 装配体力重算已按原版顺序修正。原先分歧的 10 场和额外 20 场，在独立重录目录中通过了 Oracle、GDScript 和 Python 三方验收。正式 1690 场账本仍对应重录前的语料。复用 [30 场验收账本](../output/_handoff10/original_order/alignment.json) 和 [阶段报告](A阶段修复报告_两处真因.md)。
- 既有 C++ 全量结果校验胜负及事件数差值。本轮使用 C++ 已有的逐事件调试导出，比较事件顺序、tick、事件类型、双方归属、来源、参数和父事件，并核对胜负与自然终局。原始流水保留，归一规则沿用现有 Oracle 比对规则。终局合成行仅在确认双方都具有等价终局记录后映射。记录 C++ 调试导出无法表达的字段，补齐有战斗语义的字段后再出具四方结论。参见 [三方比较入口](../tools/verify_oracle.py) 和 [C++ 逐事件工具](../native_sim_cpp/tools/_cmp_events.py)。
- 四路共享同一用例清单、阵容、种子、注入时点、预排序、宝石槽、血量、体力、回复和冷却分支。夹具中的时序覆盖应逐项登记。超时、缺产物、跳过和输入不一致单列为失败。胜负口径相同且事件数相同的场次仍要完成逐事件比较。

## 执行步骤

1. **先建立四方基线。** 复用已重录的 30 场，建立 C++ 逐场比较入口，输出首个分歧及其附近事件。追加能覆盖卡组、光剑、临时 Buff 和同帧致死的定向用例。选取不含这些机制的正常场次作为回归对照。
2. **核实卡组点火和逐张连锁。** 先在原生 Godot 中测定 `call_deferred` 在激活和判胜边界上的行为，包括回调内再次入队。对照首张入队、首张激活、后续卡牌接续和同帧致死。已有实现通过定向验证的部分，直接保留验证结果。参见 [原版卡组](../decompiled_full/Items/DeckofCards.gd)。
3. **验证体力与药水。** 以 30 场重录为入口，核对玩家和对手从装配到开战的体力余额，追踪扣除前信号、药水判定、Bionic Armor 分支和后续攻击。优先验证已有修复在 C++ 链路上的结果。参见 [原版体力重算](../decompiled_full/Core/Character.gd) 和 [Oracle 准备阶段](../oracle/oracle_fight.gd)。
4. **核实光剑和临时 Buff 计时器。** 用原生 Godot 实测 `idle_frame` 与 `call_deferred` 的先后、同值重启、多个计时器同时到期和回调内重启。对照光剑关灯、Buff 替换和到期、疲劳触发，按首个分歧单点修复 Oracle。再同步 GDScript 及测试镜像，更新 Python 和 C++ 生成产物。参见 [Oracle 手动计时器](../oracle/oracle_fight.gd)。
5. **扩大回归并收口。** 每项机制先过定向样本，再用独立输出目录重录并检查 914 场基线和 1690 场扩样。逐条读取四方结果，核对用例集合、完成状态、胜负与事件。记录修前后胜负翻转及其物品分布。用相同对手和种子比较代表性 A/B 摆盘的胜率差，并记录排序或 2 个百分点接受决定是否改变。参见 [配对评估实现](../trainer/evaluator.py)。

| 差异 | 源码或原生证据 | 最小内核实现 |

后续先将上述已证实语义同步到独立新版四方构建，删除只为冻结 Oracle 服务的旧闩锁和相位补偿，再用定向样本及 914/1690 全量验证。性能比较使用相同阵容、种子、事件输出开关和重复次数，分别记录装配与战斗 CPU 时间、吞吐量；原版场景录制耗时不计为模拟器性能。现有优化不应因重新生成代码而丢失，合并前需检查生成器及已编译模块是否同步。

## 当前验收结果

### 轻量原生调度候选的首场五方验收

隔离构建 `output/_v1110/sim_native/` 已将上述角色状态机和调度修正同步至 GD、纯 Python 和 C++。原生参照、Oracle、GD、Python、C++ 在 `run101207_r1_o604707_r1` 上通过逐事件、严格宝石身份、胜负及自然终局核对：原生及脚本含终局共 160 行，C++ 为 159 条战斗事件加独立终局结果。[五方账本](../output/_v1110/native_core_check/cpp/summary.json)。该结论仅覆盖一场，尚未替换默认内核，也尚未构建候选 Python 的 Cython 模块。

角色状态机不创建场景节点、Tween、Sprite 或动画资源。独立契约探针将其与真实 Godot Tween 比较 2000 帧，247 次动作切换的位置与前进闩锁逐帧精确一致，覆盖返回中断及负前进时长。必要的单精度转换、线性插值运算顺序、同帧剩余时间和回调阶段来自 Godot 3.6 的 [SceneTreeTween 源码](https://github.com/godotengine/godot/blob/3.6-stable/scene/animation/scene_tree_tween.cpp) 与 [缓动公式](https://github.com/godotengine/godot/blob/3.6-stable/scene/animation/easing_equations.h)。可复现配方为 `stage_native_core.py`、`stage_native_binding.py`，独立探针为 `native_motion_contract.gd`。

`bench_native_core.py` 使用同一已验收阵容和初态，预热后分别计量关闭、开启事件调试导出的单进程 CPU 时间，装配单独计量；不包括文件日志和事件序列化。这是候选性能基线，不能据此宣称相对旧版提速。后续需增加复杂阵容、已编译 Python 和相同语义下的优化前后比较。

旧手动调度 V1 的 1690 场全量四方已完成：1689 场逐事件通过，1690 场胜负一致，严格宝石字段完整。唯一失败为 `run604768_r18_o101694_r18`，Oracle 在索引 232 多出 Twine 效果，随后随机链分叉，不能因胜负一致而忽略。914 场 V1 仍在独立协调器中录制。[V1 四方账本](../output/_v1110/full_corpus/expand/cpp/summary.json)。
