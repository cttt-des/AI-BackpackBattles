# C++ 版（native_sim）与神谕的 1690 场对齐差异报告

> 报告对象：`native_sim_cpp/` 作者　|　测量方：主仓库模拟器侧　|　日期：2026-11-14
>
> 先说结论：**C++ 版的自洽确定性是满分**（同一输入连跑两遍逐位相等，1690/1690），
> **有问题的是与神谕（oracle）的一致性**：1690 场中 **1688 场一致（99.88%）**，
> **2 场胜负不同、30 场事件数有偏差（1.8%）**。本报告给出这 30 场的逐场定位。

## 1 验证方法与口径（请先核对这一节，口径不对结论就不成立）

| 项 | 取值 | 说明 |
|---|---|---|
| 用例集 | `gd_core_test/expand_align_cases.json` 全部 1690 场 | 与主仓库 1690 里程碑同一份 |
| 真值 | 神谕事件流（Godot 录制），主仓库账本 `output/perf/_fix_1690.json` | 该账本 1690/1690 三方一致 |
| C++ 调用 | `sim.run_one(player, opponent, seed=…, round_id=…, below_master=True, native_activation_order=True, reseed_after_player_character=True, formal_ev_gate=500000, max_time=90.0)` | — |
| 对照腿 | 主仓库 py 腿产物 `output/oracle/align_expand/py/<case>/events.json` | **该腿已与神谕逐行一致**，故与它比对等价于与神谕比对 |
| 事件导出 | `gd_sim_set_dbg_events(1)` + `gd_sim_dbg_event_line(i)` | 你提供的调试接口，单线程有效 |

⚠️ **`below_master=True` 是关键**：`alignment_expand.json` 的 `convention` 写的是 `below_master: false`，
但那是陈旧记载。实测 **`below_master=True` 才能复现账本**（我第一轮漏传它，一致率只有 92.1%、134 场假失败）。
补上后 99.88%。如果你们的验证流程用的是 `false`，那这 30 场里可能有相当一部分是参数问题而非代码问题。

## 2 总体结果

| 指标 | 结果 |
|---|---|
| 自洽确定性（同输入跑两遍） | **1690 / 1690 逐位相等** |
| winner 与神谕一致 | **1688 / 1690（99.88%）** |
| 事件数差 = −1 | 1660 场（98.2%）—— 这是**已知口径差**：主仓库 `run()` 末尾多发一条 `emit_combat_end`，C++ 侧无此事件，**不是 bug** |
| 事件数差 ≠ −1 | **30 场（1.8%）** ← 本报告的主题 |
| 其中胜负也不同的 | **2 场** |

## 3 30 场的共同特征（这个比逐场列表更重要）

**共性**：

1. **首个分歧点之前的事件序列完全一致**（type / timestamp / origin 全同）。
2. 从该点起，**事件集合基本不变，但相对顺序发生交换** —— 不是"算了别的东西"，是"同样的事情发得早/晚了一点"。
3. 分歧点分布在 **第 1 ~ 765 条**，其中 24/29 场在第 100 条之前（即战斗前中期）。
4. 有 1 场（`run101490_r12_o704664_r12`）前缀完全一致，仅尾部长度差。

**按 C++ 侧"抢发"的事件类型分三类**：

| 类别 | 场数 | C++ 抢先发出的事件 | 原版在同一位置发出 |
|---|---|---|---|
| **A** | **15** | 栈事件（100–110：Lucky/Regeneration/Vampirism/Spikes/Mana/Empower/Heat/Poison/Cold） | `item_activate` 或 `stack_gain` |
| **B** | **6** | `DealDamage`（type=1） | `stack_gain` / `heal` / `missed` |
| **C** | **8** | 其他状态（`Stun`/`Health`/`Cold`/`Lucky`/`MissedAttack`/`Vampirism`/`DrainStamina`/`InvulnerableStart`/`BattleRageStart`） | `item_activate` / `attack` / `heal` / `stack_gain` |

> **A 类占一半**，而且最集中的模式是「**C++ 先发出栈事件，原版先发出 `Activation`**」。
> 建议优先查这一条：栈事件（`ctx.bus.logEvent` 路径）相对于 `Activation`（`emitSignal` 路径）的**派发顺序**，
> 在双方是不是同一套时序。

## 5 已排除的假设（避免白查）

| 假设 | 检验方式 | 结论 |
|---|---|---|
| `activation_order` 装配/开战排序错 | 比对 `gd_sim_dbg_order(side, phase=1)` 与神谕 `activation_order` | ❌ **完全一致**（player 25 / opponent 21） |
| `below_master` 参数 | 对比 `true/false` 两轮 | ✅ 真问题：`false` 时 92.1%，`true` 时 99.88% |
| 缺键 → `get_index` 返回 null | 查 C++ `setup()` 是否按 `getStacks()` 全填 `buffAmplificationChances` | ❌ 全填了 `0.0`，与 Python 一致 |
| `gd_iter_seq(int)` 语义差异 | 读 `gd_rt.cpp` 实现 | ❌ 返回 `0..n-1`，与 GDScript `for i in amount` 等价 |
| `takeDamage` 实现差异 | 逐行比对 C++ 生成代码与 Python | ❌ **同构**（createEvent_Attack → emitSignal → dealtDamage → set_prop event → emitEvent） |
| `prepareArmor` 未执行 | 在 Python 侧挂 `changeResistChance` 探针 | ❌ 探针 0 次调用是对的——Emerald 挂在 **Hammer（武器）** 上，`getGemMode()` 不是 Armor |
| 事件序列化把 gem 记成 `None` | 比对 `py` 腿与 `gdcore` 腿产物 | ❌ 两条腿都是 `{kind:"gem", ...}`，一致 |

## 6 我这边的可观测性缺口（如果你们愿意补，能大幅加速定位）

我无法进一步定位的原因，都是**缺数据**，不是缺方法：

| 缺什么 | 影响 | 建议 |
|---|---|---|
| C++ 库只导出 6 个接口（`gd_sim_init/register_item/register_character/reset_registry/run_one/run_batch`） | 无法读 RNG 状态、无逐抽追踪，只能靠事件反推 | 若方便，加 `gd_sim_dbg_rng_state()` 或在 `dbg_event` 里附上事件发生时的抽取序号 |
| 该 case 的神谕侧只有 `events.json`、无 `rng_log` | 没有真值抽取序列可比 | 若原项目能提供 `output/oracle/expand/fights/<case>/rng_log`，对位会快很多 |
| `GdVal` 的完整定义不在 bundle 内 | 无法确认 C++ 值语义细节（如 `min(int, float)` 的截断方向） | 提供 `gd_rt.hpp` 的 `GdVal`/`gd_min`/`gd_coerce_int` 部分即可 |

## 7 我建议的排查顺序

1. **先确认 `below_master=True`** —— 如果你们的验证脚本用 `false`，先修参数再看代码。
2. **从 `run101668_r7_o604708_r7` 入手** —— 第 2 条事件就分叉，且是纯顺序对调，最小复现。
3. **重点看 A 类（15 场）** —— 栈事件（`bus.logEvent`）vs `Activation`（`emitSignal`）的派发先后。
   这两条路径在 `CoreEventBus` 里是不同的：`logEvent` 在 `Delayed` 模式下走 `queueSignal`，`emitSignal` 走 `emitEvent`。
   如果 C++ 侧对 `loggingMode` 的切换时机与 Python 不同，就会正好产生「栈事件提前、`Activation` 推后」的现象。
4. `run704879_r14_o704504_r14`（delta **+475**，最夸张）可作为压力用例：修完 A 类后看它是否自然收敛。

## 9 一句话

> **自洽确定性满分，与神谕差 30 场（1.8%）**。这 30 场不是"算错了"，是**事件派发顺序不同**——
> 首个分歧点之前完全一致，之后只是顺序交换。A 类（栈事件抢在 `Activation` 前，15 场）占一半，
> 建议优先查 `CoreEventBus` 里 `logEvent` 与 `emitSignal` 两条路径的时序差异。
