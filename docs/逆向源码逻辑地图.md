## 0. 版本注意事项

- 旧解包（2026-08-18）曾被 **bpb_enhance Mod（v1.1.8）** 污染（33 个文件含 Mod 注入，如 Mod 服务器 URL、版本号改为 1.1.8）。当前目录为干净官方 v1.1.7，`Game.gd:10 var VERSION = "1.1.7"`。

## 1. 总览与统计

### 1.1 目录构成

| 目录 | 规模 | 性质 |

| `Interface/` | 189 个 .gd（约 8300 行） | UI 交互 + 前端显示（**藏有少量真逻辑**，见 §6.2） |
| `Core/` | 15 个 .gd（Game.gd 6113 行为最大） | 游戏总控、战斗、背包、商店 |
| `Utility/` | 49 个 .gd | 随机/事件/序列化等工具，A~C 级混杂 |
| `Sheets/` | `ItemBook.gd`（1890 行，autoload 物品总库）+ `Table.gd` + `CSV/` | 纯逻辑数据层 |

| `Shader/`、`Assets/`、`Items/**/Animations/` | 2 + 4 + 14 个 | 纯显示 |

### 1.2 物品脚本方法分类（3139 个方法统计）

| 类别 | 占比 | 说明 |
|---|---|---|
| 战斗逻辑 | ~46% | damage/attack/block/stack/buff/cooldown/trigger/heal/crit 等 |
| 商店经济 | ~6% | shop/bought/sold/price/sale/roll 等 |
| UI/显示 | ~5% | tooltip/hover/sound/particle/animation 等（**高度集中于基类 Item.gd**，子类里主要是 43 处音效覆盖 + 21 处 getDescription） |
| 其余 | ~43% | 背包格几何、碰撞、旋转、插槽等基础设施（逻辑与表现混杂） |

**结论：527 个物品子类的逻辑部分几乎可原样保留，剥离成本集中在 `Item.gd` 基类与 Core/Interface 层。**

## 2. 运行模型

### 2.1 场景树与 autoload

- 主场景 `Core/Main.tscn`（project.godot，2D 拉伸 1920×1080）。
- 19 个 autoload 单例。核心必需：`Game`（总控）、`Util`、`ItemBook`、`EventBus`、`CraftingManager`、`RunDatabase`；可存根/剔除：`Sound`、`Settings`、`SteamHelper`、`CrazySDK`、`SkinBook`、`InputBlocker`、`InputMapping`、`MaterialCompiler`；随插件剔除：`ControllerIcons`、`SilentWolf`。
- 工程是 Godot 3 场景树深度耦合架构：`Game.gd` 为 `Node2D` autoload 上帝对象，全局状态（gold/round/wins/PLAYER/OPPONENT）都住在场景树里。

### 2.2 帧驱动战斗 + 全局变速

- **不存在独立逻辑时钟**。物品冷却由 `Item._physics_process` 每物理帧推进（`Item.gd:4453-4458`，`triggerTime -= delta * getSpeed()`），战斗加速通过 `Engine.time_scale` 实现（`CombatTimer.gd:198-203`）。
- 做无头核心时必须把 `Item._physics_process` 与 `Character.onTick` 收编到一个显式 `step(delta)` 入口（见 §8 风险点）。
- `Character.gd:401-414 onTick`：tickCounter 奇偶交替处理回复/中毒。

### 2.3 事件与信号体系

- `EventBus`（autoload）：战斗信号中枢，排队/即时发射，`connectForCombat` 走 `Item.gd:5694-5700` → `EventBus.connectEvent`。
- `Game.gd` 约 64 个 signal，绝大多数是逻辑→UI 桥（gold_changed / health_changed / shop_opened / combat_start 等，Interface 层 300+ 处 `Game.connect`）；UI→Core 方向是**直接方法调用**（`Game.switchToCombat()`、`Game.spendGold()` 等）。
- Core↔Interface 之间的输入调度基础设施 `InputBlocker` 被两层共同依赖（`Game.gd`、`Combat.gd:1019-1024` 均引用），不是纯 UI 私有物。

### 2.4 内建回放体系（事件溯源）

`CombatEvent`（单事件数据 + asText 本地化渲染）→ `CombatLog`（事件流 + 回放引擎）→ `CombatSnapshot`（血量/体力/叠层快照，`apply` 回 Character）→ `StatHistory`（eventNum→value 阶梯序列，二分查找）→ `RunData` + `BitStream`（位流序列化，存档/回放/联机码）。这套纯逻辑是"无 UI 战斗验证"的最佳抓手，全部 extends Reference，无场景依赖。

## 3. 主流程时序（Run 生命周期）

状态由 `Game.gd:276 var state = State.Title`（枚举 `Game.gd:102-107`）加一组布尔隐式构成；`isShopActive` = `Game.gd:2889-2890`，`isSwitchToCombatPossible` = `2892`。

```
startFreshRun (2646) → startRun (2829) → titleToShop (2850)
  └─ 每回合商店阶段: startRound (4078) ── gainRoundGold (4155)
        ├─ 自动合成 readyToFuse → startFusing
        ├─ 玩家购买/拖放/刷新（交互层，见 §6）
        └─ 点开战 → switchToCombat (2908) → finishSwitchingToCombat (2928)
              ├─ 保存 run 状态 → instance 对手 → ItemSort.sort_TriggerPriority
              └─ prepareItems → activateItems → COMBAT_DELAY 后开战
  └─ 战斗阶段: 物品 Timer 各自触发，Character.takeDamage 结算
        ├─ 一方死亡: character_died → endCombat (3282)
        └─ 超时: combatTimer → forceLoseCombat
  └─ 结算: combatEndDeferred (3312) → 回血归零/curRound++ → runOver (3388)
        ├─ 未结束: Combat.gd 动画播完 → switchToShop (3792) → 下一回合 startRound
        └─ 结束: endRun (4552) 算 rating/trophies
```

**血量/金币流转**：金币表 `const goldGain`（`Game.gd:203-207`，0,13,10,10,11,11,12,…16，按回合索引取用见 948）；血量回复分段 10/15/20/30（`getHealthGain`，`Game.gd:966-976`）；子职业回合 +10、技能回合 +5（`getGoldGain`，`947-957`）。血量回合间不清零（负者归 0，胜者保留，`combatEndDeferred`）。

**最大的重构点**：场景切换靠 AnimationPlayer 动画回调推进（`onSceneAnimationFinished` 链），逻辑埋在动画回调里——剥离时必须重写为显式状态转换。

- `Character.gd:1149-1164`：gain/lose/use Stacks 系列全部委托 `Buff.gd`。
- `Buff.gd`（361 行，extends Reference）：`gainTemporary`（76-196）含抗性 resistChancePercent 逐层判定、debuff 反射 reflectChancePercent、MAX_STACKS 封顶、临时层 Timer 超时链（`onTimeout` 317）。

### 4.3 随机数体系（种子化对局必须整体保留）

| 组件 | 位置 | 用途 |
|---|---|---|
| `Util.rng` | `Utility/Util.gd` | 全局 RandomNumberGenerator（飘字位置/动画抖动等表现层也用） |
| `BalancedRng` | `Utility/BalancedRandom.gd` | 偏差>0.3 时按 balancedness=3 加权 + 连击惩罚，用于命中/暴击/暴击抗性/眩晕抗性（`Character.gd:94-97` 初始化 accuracyRng/critRng/critResistanceRng） |

### 4.4 物品触发模型（Items/Item.gd，6573 行）

战斗生命周期五段：`prepare`（3361-3369，cache 受影响物品、重置 RNG、递归 gems、onPrepare）→ `preCombatStart`（3375-3385，首次激活冷却）→ `combatStart`（3393-3400）→ `postCombatStart`（3405）→ `combatEnd`。

- 冷却触发：`_physics_process`（4453-4458）→ `trigger`（4426-4433，含 doubleActivationChance 二次触发）→ `doCooldownEffect`（4435 基类空，204 个物品子类覆盖）。
- 联动：`canAffect` 系列（3544-3566：primary/secondary/tertiary/lightning + 分发器 canAffect_color）；受影响物品缓存 + 信号订阅 `connectForCombat`（5694-5700）。
- ⚠️ `activate`（4686-4737）仍是逻辑+动画混合体：combatLog/事件总线（4705-4714）与 z_index/动画/跳砍（4716-4732）同函数；含 `activationsThisFrame` 同帧限流（4697-4702，>3 直接 return）。`activateFromEvent`（4740-4801）是回放渲染分支。
- ⚠️ UI 刷新点：`showCooldownSmooth`（5298-5311，shader tween）、`showCooldown`（5313-5322）。
- 冷却编码/回放：`getCooldownEncoded`（4463）、`reconstructCooldown`（4476）。
- 回放内建支持：战斗冷却可序列化，配合 §2.4 回放体系。

### 4.5 战斗计时与疲劳引擎（藏在 Interface 层！）

`Interface/CombatTimer/CombatTimer.gd`（28 个函数）是**战斗时间的唯一权威**：

- 规则常量：`FATIGUE_TIME = 17`（:4）、`MAX_SPEED = 3.0`（:5）。
- `_physics_process`（122）：`combatTime += delta`——战斗时钟唯一累加器。
- `startFatigue`（145）；`dealFatigueDamage`（153-179）：<60s 用 0.1 系数、≥60s 用 0.2 系数累加，调 `Game.fatigueDamageSource.setDamage()`（:163）与双方 `takeFatigueDamage()`（:167-168）。
- `advanceTime`（184-196）：时间快进并联动疲劳计时器，写 CombatLog 统计。
- `Engine.time_scale` 调速/暂停（198-203）；大厅强制最快速度判定（60-76）。
- 下游依赖：Combat.gd 时间轴同步、CombatLog 时间戳、Game.gd 快/慢战斗成就判定、OwlSpirit 等物品（查 `hasFatigueStarted()`）。
- `Game.fatigueDamageSource` 初始化：`Game.gd:2432-2433`（Type.Fatigue + CanBeBlocked）。

### 4.6 战斗事件流

`CombatLog.gd`（1279 行）：`createEvent`（240）是被 Character/Buff 到处调用的硬依赖；statLoggers（63）、快照（467-529）、回放（366-415）。一半是日志 UI（行渲染/滚动/tooltip），剥离时保留事件数据层 + StatLogger，丢 UI 行渲染。`CombatStatLogger.gd`（152 行）/`StatHistory.gd`（41 行）/`CombatSnapshot.gd`（35 行）/`CombatEvent.gd`（208 行）均为 A 级纯逻辑。

## 8. 剥离顺序建议与风险点

建议顺序（每步可独立验证，利用 §2.4 回放体系做对账）：

1. **Combat.gd 整体去演出** → 保留 endCombat→round_result 语义。
2. **Game.gd 拆 RulesEngine**：回合循环、经济表（goldGain/血量表）、胜负判定、存档字典、rating 计算（3715-3828 旧锚点区，现 4552-4634 endRun）；金币 XOR 编解码原样带走。
3. **Character 拆 Combatant**：纯数值 + Buff 数组；EventBus 换普通 signal/回调；Timer 换 tick 驱动。
4. **Item 基类瘦身**：保留五段生命周期 + 冷却 + canAffect 联动；`activate` 拆成"发事件"与"播动画"两层；`_physics_process` 收编进显式 `step(delta)`。
5. **商店经济域**：Shop.gd 抽池逻辑 + §6.2 的 1-8 项下迁（CombatTimer/ShopOffer/Sellbox/ChestnutTrade/Storagebox 逻辑）。
6. **Inventory 数据驱动化**：TileMap → 数据网格。
7. **对手源注入化**：RunDatabase 网络层换本地 run 池。

风险点：

- **动画驱动状态机**：场景切换（switchToCombat 链）靠 `onSceneAnimationFinished` 回调推进，是 Game.gd 拆分中最难的部分，需重写为显式状态转换。
- **帧驱动 + Engine.time_scale**：战斗没有独立逻辑时钟（§2.2），变速/暂停语义要随 CombatTimer 一起搬。
- **TileMap 网格数据源**：背包形状是场景资源（`Inventory.gd:45-48`），不是数据。
- **Timer 场景树时钟**：Buff 临时层超时（`Buff.gd:25-43`）、Item 冷却、CombatTimer 全依赖 add_child(Timer)，剥离需统一换成战斗内 tick 累计。
- **call_deferred 调度**：CraftingManager 依赖场景树空闲帧。
- **InputBlocker**：两层共用的输入调度设施，Core 代码路径有 `isActive()` 早退，删前清理 Core 侧引用。
- **反编译缺口**：如 `Game.gd:3507-3579` 空白段，剥离重构时不可当作"确实无逻辑"。
- **BalancedRng 状态即对局状态**：确定性模拟要种子化并序列化其内部状态（§4.3）。
