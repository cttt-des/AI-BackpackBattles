# 模拟器性能优化规划（2026-11-09）

> 目标：在**逐位确定性不破**（同 seed → 同事件流 → 1690/1690 对齐保持全绿）的前提下，
> 把 gd_core_py 内核的单场耗时与蒙特卡洛吞吐提高一个数量级以上，并压缩启动开销。
> 本文档是规划；每一步实施时仍以既有验收门为闸，闸门不过 = 优化不落地。

---

## 0. 实测基线（2026-11-09，本机：4 物理/8 逻辑核，功耗受限，Python 3.14.5）

| 项 | 实测值 | 出处 |
|---|---|---|
| 冷启动（`_bootstrap.load_all()` 673 模块 + runtime JSON） | **~1.2 s**（纯导入 626 ms） | `tools/_perf_bench.py` |
| 单场战斗（gd_core_py，中位 / min / max） | **378 / 234 / 404 ms** ≈ 2.6 场·核/s | 同上 ×20 |
| 旧内核 `engine/` | **已损坏**：`engine/context.py:16` 引用不存在的 `rng.flip`，GUI 默认内核一跑即崩 | 实测 |
| 蒙特卡洛并行（ProcessPoolExecutor） | 本机 4 workers ≈ **2.0x**，8 workers ≈ **2.2x**（物理核数+功耗墙限制；8 物理核桌面预期 6–7x） | `tools/_perf_pool.py` ×128 |
| Python 3.14 实验性 JIT（`PYTHON_JIT=1`） | 377 vs 378 ms，**零收益** | A/B 实测 |

cProfile 热点（3 场合计 3.5 s，含 ~2.6x 分析器开销；占比为 profiled cum）：

- `CoreCombat.physicsTick` → `CoreItem.physicsTick`：217k 次调用，**cum 65%** —— 逐 tick 逐物品的解释器派发是绝对大头
- `CoreItem.getSpeed` 62k 次 cum 23%（其中 `getStackSpeedMods` cum 14%）
- `CoreEventBus.emit/emitAndLog` cum ~19%
- `_rt._iter` **513k 次调用**（12%）—— 每个 GDScript `for` 都过一层垫片
- `FuncRef.call_funcv` cum 14%
- RNG `randf_range` 15k 次 cum 7%（非热点，**不要**动 PCG32 的 Python 面）
- 装配阶段（`__init__` 含 `_build_side`）≈ 13%

另有 np51 实验遗留：`gd_core/CoreCombat.gd` 起战段一条**无条件** `print(INJ_ARM …)`
（注释自称「用后即还原」未还原），每场战斗触发一次 stdout 格式化+写。

## 1. 不可妥协的约束

1. **逐位确定性**：PCG32 逐位、`f32` float32 舍入、f64 左结合累加链（`ctx.time += DT`）、
   GDScript int/float 语义（`_div/_mod` 符号规则）——任何优化不得改变求值次序与数值语义。
   `_rt.py` 本身就是这份语义的**规格说明**，重写运行时以它为准。
2. **验收门现成且必须每步过闸**：`tools/_np21_gate.py`（基线 7 场+域代表双腿）→
   全量 1690 场双判据（canonical 事件流+渲染行，`tools/verify_oracle.py`）→
   56 局 Godot 基准逐字符（`tools/check_gd_core_engine.py`）→ RNG 探针逐位
   （`tools/verify_godot_rng.py`，动 PCG32 时必跑）。
3. **唯一真源出口是 `tools/gd_to_py.py`**：性能改动一律改生成器（或 `_rt.py`），
   禁止手改 673 个「勿手改」产物；改后重转写、全量过闸。
4. **双腿保留**：无论编译到哪一档，纯 Python 腿永久保留为对照实现（回归与取证用）。

## 2. 路线总览（按性价比排序）

| 阶段 | 内容 | 工作量 | 预期收益（单核） | 风险 |
|---|---|---|---|---|
| P0 | 卫生+基准基座 | 0.5 天 | — | — |
| P1 | 并行 MC / 启动惰性化 / MC 快速钩子 | 1–2 天 | 并行 2–7x（视核数）；启动 8x | 低 |
| P2 | 生成器级纯 Python 优化 | 数天–1 周 | 1.5–2.5x | 低（全量闸兜底） |
| P3 | **gd_to_py 加 Cython 后端**（类型化编译） | 1–3 周 | 4–10x（叠 P2 后 15–25 场·核/s） | 中 |
| P4 | 原生后端 Rust/C++（整场单次 FFI） | 1–2 月 | 50–150x | 高，**条件触发** |

推荐顺序：P0 → P1.1（并行先行，一周内拿到可用收益）→ P1 其余 → P2 → P3 → 按需 P4。

### 架构前置建议：产品内核收敛到 gd_core_py 单内核

`engine/`（自研转译内核）已损坏、`simulator/combat.py` 旧内核已下线，但 GUI/CLI 默认
引擎仍是 `engine`（`simulator/simulate.py:29`）——「开始战斗」当前实际不可用。
建议：GUI/CLI 默认引擎切到 `GDCoreEngine`，`engine/` 冻结为参考实现。
此后**所有性能工作只对一条内核负责**，回归面减半，也顺手解掉 GUI 的运行时崩溃。

## 3. P0 —— 卫生 + 基准基座（0.5 天）

1. **收编基准工具**：把 `tools/_perf_bench.py` / `tools/_perf_pool.py`（本次规划所用，
   临时脚本）收敛为 `tools/bench_sim.py`：固定 N、输出中位/min/max、`--workers`、
   JSON 结果落盘。所有性能 PR 必须附 before/after 数字 + 闸门状态，防止「感觉变快了」。
2. **还原 np51 遗留**：`gd_core/CoreCombat.gd` 去掉 INJ_ARM 无条件 print（按其自述
   「用后即还原」），四树同步后重转写、过闸。顺手清点产物里其余调试 print
   （`[spdt]` 已有 `_dbg_spdt` 门控，合规）。
3. **机器档案**：记录基准机的物理核/功耗墙（本机全核降频，8 workers 仅 2.2x），
   并行收益数字只按实测机器报告，不跨机器外推。

## 4. P1 —— 零重写快赢（1–2 天，单项独立可回滚）

### 4.1 蒙特卡洛并行化（产品收益最大项）

现状：GUI `_run_battle` 单线程逐场循环（`simulator/gui.py:341`），CLI `--runs` 同样串行。

做法：GUI 后台线程与 CLI 各起 `ProcessPoolExecutor` worker 池；每 worker 进程常驻
（`gd_core_engine.kernel()` 的模块级缓存保证每 worker 只付一次 1.2s 启动，千场摊销后可忽略）；
seed 按块分片，**每场天然独立、逐 seed 确定性不变**，结果按 seed 聚合即可。

- CLI：`--workers N`（默认 `min(4, cpu)`；`--runs 1` 恒单进程）。
- GUI：蒙特卡洛模式自动并行，进度按完成数回报；单场模式不并行（要事件流）。
- Windows spawn：worker 入口走模块函数（可 pickle），参考 `tools/_perf_pool.py` 实测代码。

预期：本机 ~2.0–2.2x（功耗墙），8 物理核桌面 6–7x；蒙特卡洛 1000 场从 ~6.5 min → 本机 ~3 min。

### 4.2 启动惰性化（626 ms → 目标 <150 ms）

现状：`_bootstrap.load_all()` 无条件导入全部 673 模块（626 ms），单场只用到其中 ~30 个。

做法（两选一，先易后难）：
- a) `_registry.C(path)` 改惰性：首次解析时才 import 对应模块（注册表先登记
   path→module 映射，不真导入）；`missing()` 校验改为「按需解析后」断言。
- b) 保守版：`load_all()` 保留但拆两档——核心面（Core*、基类、`gd_core_items` 基类）
   立即导入，物品脚本按阵容引用集导入；工具链（verify_oracle 全量语料）走全量档。

利好：exe 启动、GUI 开窗、**每个并行 worker 的首场延迟**。风险低：注册表仅是
path→class 映射，导入次序不影响战斗语义；过 REG 闸 + 56 局基准即可。

### 4.3 MC 快速钩子（预计 5–10%）

`runs>1` 只需胜负时，装配探针类换轻量版：`logEvent` 保留 `_count`（或一并跳过），
跳过 params 拷贝 / `_json_safe` / `_OriginRef` 构造 / 事件对象化。
**确定性论据**：`logEvent` 是判定链下游的纯旁路（不消耗 rng、不改内核状态），
覆写为轻量不影响任何抽点；单场模式与对照工具仍用全量探针。
闸：REG 7 场 + 蒙特卡洛胜率与全量探针逐 seed 对拍（同 seed 同胜负）。

### 4.4 （可选）GC 调参

`run()` 前 `gc.freeze()`（bootstrap 后常驻代冻结）+ 调 `set_threshold`；
对长批次 MC 实测决定去留。战斗对象图有环（bus 连接、父子互指），不建议直接 `gc.disable()`。

## 5. P2 —— 生成器级纯 Python 优化（数天–1 周，仍纯 Python）

全部是 `tools/gd_to_py.py` 生成策略改动，产物重生成后全量过闸：

1. **`_iter` 直发**（513k 调用消大半）：GDScript `for v in X` 中 X 为 list/数组变量或
   int 表达式时，生成器直发 `for v in X:` / `for v in range(X):`；仅 float、dict、
   语义存疑形态保留 `_iter`。判据是语法形态保守分类，误分类由全量语料兜底。
2. **热循环局部绑定**：`CoreCombat.physicsTick` / `CoreItem.physicsTick` /
   `tickTimersPass` 内把高频方法与属性提为局部变量（`it_getSpeed = item.getSpeed` 等）。
   生成器按「同方法名在同循环体出现 ≥2 次」机械触发。
3. **`getSpeed` 纯函数缓存**（可选，~10%）：62k 次/3 场。前置审计：函数无副作用、
   无 rng、输入只有自身 stacks/speed-mods 状态；缓存 + 显式失效钩子（栈变动点）。
   任何审计不确定即放弃此项——它是本阶段唯一动语义面的项。
4. **Vector2 分配收敛**（次要）：格运算热点（`CoreGrid.addItem` 路径）复用或
   `__slots__` 已有，减 `__setattr__` 包装开销。

预期合计 1.5–2.5x（378 ms → 150–250 ms），零新依赖，零打包变化。

## 6. P3 —— gd_to_py 加 Cython 后端（1–3 周，收益主力）

**核心思路**：真源仍是 `gd_core/*.gd`，生成器新增 `--backend cython` 输出 `.pyx`，
构建期编译为 `.pyd`，照常进 PyInstaller exe——**用户侧零变化**；`--backend py`
输出保留为对照腿（双腿回归永久）。

要点：

- **按模块渐进**：先热核 8 模块（CoreItem/CoreCombat/CoreCharacter/CoreTimer/
  CoreRng/CoreBuff/CoreGrid/CoreEventBus，覆盖 profiled cum 65%+ 的派发面），
  再物品脚本长尾。任何模块编译/对拍不过 → 单模块回落纯 Python，进度不互斥。
- **PCG32 下沉 C u64**：`_rt.PCG32` 的 state/mask/递增链用 `unsigned long long`
  精确复刻（MASK64 显式），以 `tools/verify_godot_rng.py` rng_probe 逐位闸。
- **f32 用 C float 舍入**：替代 struct pack/unpack（同值更快），与 Godot
  `real_t=float32` 语义同源。
- **类型化面**：GDScript 声明为 float/int 的字段与参数 cdef 化（`double` /
  `long long`），Variant 面（dict/list/String/跨类引用）保持 PyObject。
  int 溢出语义：转写代码已显式 MASK64，cdef 后由生成器保证等价掩码；
  不能机械证明处保持 Python int（自动兜底，宁慢勿错）。
- **验收**：每批编译产物过 REG 7 场 → 全量 1690 双判据 → 56 局逐字符；
  同 seed 事件流逐位相等是唯一通过标准。
- **打包**：build_simulator_exe.py 增加编译步骤（Windows 需 MSVC Build Tools，
  一次性环境成本，写进 README 开发环境节）；`dist/` 与 release 流程不变。

预期：端到端 4–10x（叠 P2 后 15–25 场·核/s；378 ms → 40–90 ms）。
1690 语料 py 腿全刷从 ~11–20 min → 1–3 min（对齐修复的开发回路直接提速一档）。
叠加 P1 并行：本机 ~10–20 场/s，8 物理核桌面 40–80 场/s；蒙特卡洛 1000 场 < 30 s。

备选：mypyc（同真源、同验收）——对 Variant 鸭子类型的大面注解改造更重、
内置类型子类（EnumDict 等）支持面窄，列为次选；Cython 的逐模块回落能力是决定性优势。

## 7. P4 —— 原生后端 Rust/C++（条件触发，天花板 50–150x）

**触发条件**（P3 落地后复盘）：RL 自博弈/海量 sweep 成为瓶颈，需要 10⁵–10⁶ 场/小时·核
量级，而「P3 内核 × 更多机器/进程」的线性扩容已不经济。不满足则**不启动**。

形态：`gd_to_py --backend rust|cpp` 生成整场战斗单次 FFI 调用
`simulate_fight(lineup_json, seed) -> (winner, events_json)`——tick 循环全程 native，
零跨界派发。需要用 C/Rust 精确复刻 `_rt.py` 的 Variant 语义（tagged union +
GDScript 容器/String 语义 + PCG32 + float32 规则 + f64 左结合链），运行时约 2–4k LOC，
后端生成器 1–2k LOC 改动。验收门同上（canonical 事件流逐位）。

明确排除：Godot 无头当产品运行时（GDScript VM 更慢、打包重，保留为验证神谕本位）。

## 8. 已评估并排除的路线（留档防回潮）

| 路线 | 结论 | 依据 |
|---|---|---|
| NumPy 向量化 tick | **不可行** | 战斗是严格串行 rng 依赖链，单场内无独立状态可并行；并行只能发生在场间（P1.1） |
| Python 3.14 JIT（`PYTHON_JIT=1`） | **零收益** | 实测 377 vs 378 ms——负载以动态派发为主，copy-and-patch JIT 无从下手 |
| PyPy | **产品端不走**，内部批跑可实验 | 单核潜在 5–15x，但与 PyInstaller 单 exe 分发冲突；若想验证，装 PyPy 3.11 跑 `bench_sim.py` 半小时定结论 |
| 免线程 Python（3.14t） | 不采用 | 单场速度不变；场间并行 ProcessPool 已覆盖，无需同进程多线程 |
| Codon/Nuitka 整程序编译 | 不采用为产品路线 | 对 `_bootstrap` 动态导入/动态 `type()`（`_make_probe_class`）兼容面存疑，收益上限（~2–3x）低于 P3 且不可控回落；Nuitka 仅保留为「启动耗时」专项备选 |

## 9. 里程碑与止损

- **M1（P0+P1 完成）**：蒙特卡洛可用并行 + 启动 <0.5 s + 基准工具常驻。
  闸：REG + 56 局 + 同 seed 胜率对拍。
- **M2（P2 完成）**：单场 ≤250 ms，1690 全绿。
- **M3（P3 完成）**：单场 ≤90 ms，exe 打包链含编译步，1690 全绿 + 56 局逐字符。
- **M4（决策点）**：以 M3 实测吞吐评估 P4 触发条件；默认不启动。

任何一步闸门不过：该步回滚，不影响前序已落地收益（各阶段互相独立、逐项可回退）。
