cProfile 热点（3 场合计 3.5 s，含 ~2.6x 分析器开销）：`physicsTick` 派发面 cum 65%、`getSpeed` cum 23%、`EventBus.emit/emitAndLog` cum 19%、`_rt._iter` 513k 次调用（12%）、`FuncRef.call_funcv` 14%、`randf_range` 7%、装配 ~13%。

★ v2 提醒：这组占比是**cProfile 扭曲后**的分布（分析器把每次 Python 调用都记一次），
派发类热点的占比被系统性放大，C 函数与内联代码被低估。因此 A1 建议先换采样器再定热名单，
避免照着失真分布优化。

## 1 不可妥协的约束（在 v1 四条上补两条）

1. **逐位确定性**：PCG32 逐位、`f32` float32 舍入、f64 左结合累加链（`ctx.time += DT`）、GDScript int/float 语义——不得改求值次序与数值语义。`_rt.py` 是这份语义的规格说明。
2. **每步过闸**：`tools/_np21_gate.py`（7 场+域代表）→ 全量 1690 双判据（`tools/verify_oracle.py`）→ 56 局逐字符（`tools/check_gd_core_engine.py`）→ RNG 逐位（`tools/verify_godot_rng.py`，动 PCG32 必跑）。
3. **唯一真源出口 `tools/gd_to_py.py`**：改生成器或 `_rt.py`，禁手改产物。
4. **双腿保留**：纯 Python 腿永久作为对照实现。
5. **（v2 新增）可观测面不缩水**：原版一帧内**每个**节点的 tick 都会跑完，判胜只挡 EventBus 派发。所以「跳过已死方物品的 tick」「只 tick 冷却到期的物品」这类减少调用次数的想法，即使结果看似相同，也会改变探针/计时器/时间戳的可观测面——除非能逐抽证明，否则不许做（见 D6/D7）。
6. **（v2 新增）缓存必须有失效证据**：任何记忆化（`getSpeed`、装配产物、`has_method` 矩阵、物品列表快照）都必须列出「哪些变动点会让缓存失效」，并在代码里落成显式钩子。写不出失效清单的缓存一律不做。

## 3 逐条判定与理由

### 3.1 A 组：先把尺子造对

- **A1** 采样器不插桩、不失真，能给出「真实」的 C 层与内联占比。3.14 的 `sys.monitoring` 可写极轻量计数器，够定热名单。**先做 A1 再谈其他**，否则可能整轮优化打错位置。
- **A2** 单场 378 ms 的中位掩盖了尾部：180 s 上限的超时场可能是单场成本的数十倍。必须知道时长分布才能判断 E2/D8 值不值得做。
- **A3/A5** 本机全核降频，连测两轮波动可达 10% 以上，交错对照 + p95 是唯一可信口径。
- **A6** 并行收益 2.2x 的上限可能一半来自超线程抢同一条执行单元、一半来自功耗墙；绑核后重测才能分辨，也才能回答「8 物理核桌面到底能到几倍」。

### 3.2 B 组：启动与装载

- **B2 先于 B1**。B1（全惰性）要处理「基类必须在导入期就绪」这件事：`_registry` 的占位类回退会让错序静默变成空基类，机制本身就在告警——所以完全惰性化必须保留「拓扑序前缀」的立即导入，等于把 B2 做一半。先做 B2 拿低风险收益，再评估 B1 是否还需要。
- **B5 的坑**：`_registry._is_behavior_tree()` 靠 `__module__.startswith("gd_core_py.gd_core_items.")` 判真身，模块融合后若 `__module__` 变了，整个物品装配面会静默走错分支（历史上 np24-P3-7 就是这样翻车的）。融合可行，但必须保留每个类的 `__module__` 字符串。
- **B6** 只要数据是常量（不随 seed 变），换序列化格式不影响数值语义；但要在打包链里保证缓存与源 JSON 的版本一致，宁可留哈希校验。
- **B8** PyInstaller 的 bootloader 已改写过 site 逻辑，`-S` 大概率无效，别在这上面花时间。

### 3.3 C 组：单场热路径（收益主力，也最容易出事）

- **C4 优先做**。生成代码里每个跨文件引用都写成 `_R.C("res://gd_core/CoreConst.gd")`，这是一次函数调用加一次 dict 查找；`CoreItem.py` 里这类引用成百上千处，且大量出现在热循环内。生成器可把每个出现的类在模块尾部（拓扑序保证已 reg）绑成模块级常量，引用点直发 `_CLS_CoreConst`。miss 统计照旧在导入期触发，语义不变。
- **C6 是第二大项**。`_behavior` 两级派发靠 `has_method` 判「脚本是否实现了该回调」，每次都是 `getattr + callable`。脚本实现在 `_load`/`set_script` 之后就固定了，所以按「类 → 回调名 → bound 方法或 None」建表是安全的；但**必须**在 `set_script`、`_load`、动态 `type()` 构造探针类的路径上清表，这就是约束 6 说的失效证据。
- **C9（`getSpeed` 缓存）是本组唯一碰数值语义的**。它读的是 stacks 与 speed-mods，只要有任何一个变动点漏了失效钩子，冷却推进就会静默漂移，而漂移只在长局才暴露（1690 全量可能仍能骗过短场）。判定：先写「变更点清单」审计，清单不完整就放弃，收益 10% 不值得冒 1690 破绿的风险。
- **C11（`__slots__`）技术门槛在基类**：`GodotObject` 没有 `__slots__`，子类单独加等于没加。要改就得基类 `__slots__ = ()`、所有字段由生成器从 `_init_fields` 机械产出 slots，而 `_gd_conns`、探针类动态属性、适配层注入都是例外面。收益（内存与少量速度）与波及面（673 模块重生成 + 全部动态注入点）不成比例，**列为 P2.5 备选，默认不做**。
- **C10** `struct` 单值 pack/unpack 每次约 0.5–1 us，`ctypes.c_float` 往返更快但语义要逐值对齐（尤其 NaN/Inf/次正规数）。先用 A1 确认 `f32` 真实占比，再决定。
- **C20 不可行**：把对手/玩家两段物品循环合并会改变帧内求值次序，而次序是本内核的显式契约（见 `CoreCombat.gd` 头部的帧内次序定义），合并即破 1690。

### 3.4 D 组：数据结构与算法

- **D1** 是纯去重语义优化：`itemsInCells` 的结果顺序由遍历顺序决定，用 seen-set 判重、仍按发现顺序 append，输出逐元素相同。安全。
- **D2** 只在「结果只用于成员判断或最终被排序」的位置安全；任何「结果列表顺序参与 rng 抽点」的路径都禁止（本项目 rng 抽点次序对事件流敏感）。
- **D3/D4/D5** 都需要维护一致性索引，本质是把复杂度换成了失效面，收益取决于物品数与 Buff 层数的真实分布——先用 A2 的分布数据决定。
- **D6 不可行（重要）**：事件驱动调度（最小堆只 tick 到期物品）看起来能砍掉大部分空转，但原版语义是「每帧每个物品都跑 `_physics_process`」，冷却递减、同帧限流判定、计时器推进全在这一次调用里，堆调度会改变每帧的调用集合 → 事件流必然分叉。这不是优化，是换内核。
- **D7 不可行**：即便死方物品的结果不参与胜负，它们仍会推进计时器、可能产生探针事件，判胜也只挡 EventBus 派发而不中断本帧剩余节点。跳过即改可观测面。
- **D8** 仅限「只想要胜率分布」的 MC 采样：超时场按原版判负截断并不改变单场结果，但如果 MC 统计口径依赖完整时长分布，就会失真。产品路径不做，统计路径可选并标注。

### 3.5 E 组：并行与吞吐

- **E2 是 v1 的明显缺口**：v1 只写「seed 按块分片」，而本项目的对局时长差异极大（几百 tick 到 180 s 超时），静态块分片会让某个 worker 独自拖着长尾，实测 2.2x 里可能有一部分就是这样丢掉的。改成 worker 拉取小批次任务即可。
- **E3** 一个事件流对象图 pickle 起来比一场战斗还贵，MC 却只要胜负与统计量——只回传统计是零风险大收益。
- **E5 是本版新增支线**：3.14 的 `concurrent.interpreters` 每解释器独立 GIL，可做 CPU 并行而不付进程启动与内存复制成本；限制是不能跨解释器共享对象，而这恰好符合「每场独立对象图 + 只回传统计」。值得花半天 A/B 一下：若单 worker 冷启动从 1.2 s 降到 ~0.3 s，短批次 MC 的收益会很明显。
- **E6** 装配占 13%，同 lineup 在 MC 里反复出现，缓存有吸引力；但 Python 深拷贝一层几百对象的图，成本可能已接近重建。先量再定。
- **E7** 见 A6。

### 3.6 F 组：编译后端

- **F5 是本版新增的结构性前置，建议排在 F1 之前**。现在每 tick 的成本是「Python 方法派发 + 属性查找」，而 Cython/mypyc 对**方法级**代码的加速远不如对「一整个无派发的函数体」的加速。把 tick 主循环生成成一个接受状态的单函数（内部仍是逐物品调用，但循环骨架与时间推进内联），再编译，收益才能从 4–10x 靠近上限。
- **F1/F2/F7** 维持 v1 结论。PCG32 下沉 C 是低风险高确定项，因为 `_rt.PCG32` 的规格已由 `verify_godot_rng.py` 逐位锁定。
- **F6** `nogil` 真并行要求对象图里没有任何 Python 对象访问，等于把整个内核 C 化，属 F4 的形态而非 F1 的形态。仅在 F1 完成后评估。
- **F4** 维持「条件触发、默认不启动」。

### 3.7 G/H 组：卫生与工程纪律

- **G1** 已复核：`gd_core/CoreCombat.gd:251` 仍有无条件 `print("INJ_ARM ...")`，转写产物第 280 行同样存在。删掉后四树同步重转写、过闸。
- **G4** GUI 每场刷新文本在千场 MC 下是真实开销，节流到 50 ms 几乎无感。
- **H2 是本版最有长期价值的一条**：C1/C4/C5 这类「机械变换」若能用 AST 差分证明「只有预期节点被改」，就能把它们从「需要人手核对」降级成「生成后自动验证」，全量过闸只需兜底异常，开发回路能快一倍。
- **H5** Python 优化常见的慢性退化是「每项都只慢 1%」，没有预算约束就发现不了。

## 5 已评估并排除（v1 表 + v2 补 6 条）

| 路线 | 结论 | 依据 |
|---|---|---|
| NumPy 向量化 tick | 不可行 | 单场是严格串行 rng 依赖链，场内无并行度 |
| Python 3.14 JIT（`PYTHON_JIT=1`） | 零收益 | 实测 377 vs 378 ms |
| PyPy | 产品不走 | 与 PyInstaller 单 exe 分发冲突；内部批跑可半小时定结论 |
| 免线程 Python（3.14t） | 不采用 | 单场速度不变，场间并行已覆盖 |
| Codon/Nuitka 整程序编译 | 不作产品主线 | 动态导入/动态 `type()` 兼容面存疑，上限低于 F1 且回落不可控 |
| （v2）`gc.disable()` | 不采用 | 战斗对象图有环（bus 连接、父子互指），全禁会造成无界增长；仅 `gc.freeze()` + 调阈值 |
| （v2）同进程多线程跑多场 | 不可行 | GIL 下 CPU-bound 无收益（与 3.14t 同结论） |
| （v2）对象图换 dataclass / 手写 getter | 不采用 | 改动面覆盖全部 673 模块，收益低于 C4+C6，且必然动行为 |
| （v2）把 `f32` 换 float64 省一次舍入 | 禁止 | 直接破确定性（`randf` 链逐位漂移） |
| （v2）降低 tick 精度 / 合并帧 | 禁止 | 改求值次序与事件时间戳 |
| （v2）Godot 无头当产品运行时 | 排除（v1 已定） | GDScript VM 更慢、打包更重，仅作验证神谕 |
