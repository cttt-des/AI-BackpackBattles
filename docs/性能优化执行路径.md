## 1 分类标尺（先统一口径）

三个维度各自三档，标在每条优化后面，例如 `C4｜D1 R1 G2`。

| 维度 | 档位 | 含义 |
|---|---|---|
| 难度 | **D1** | 机械变换：改生成器一处模板/常量，或删代码 |
| | **D2** | 需要设计：缓存、派发表、索引，要写失效钩子 |
| | **D3** | 架构级：编译后端、构建链、打包方式 |
| 风险 | **R1** | 不触碰求值次序与数值语义，错了也只影响性能 |
| | **R2** | 需审计失效面，写不清清单就不能做 |
| | **R3** | 动语义面 / 构建链，一旦破闸很难二分定位 |
| 收益 | **G1** | < 5% |
| | **G2** | 5–15% |
| | **G3** | > 15%（含吞吐口径的并行收益） |

**排序铁律**（三条，违反任何一条都要在 PR 里写明理由）：

1. **D1R1 先行**：机械且无风险的一律先落地清场，它们同时是后续项的测量基线。
2. **R3 不与其他项同批**：动构建链/语义面的项必须单独上闸，否则破闸时无法二分。
3. **G3 不许排最后**：收益最大的项（并行 E1、静态绑定 C4）越早拿到，后续开发回路越快。

## 4 阶段计划

每阶段都写成：目标 → 条目 → 步骤 → 验收 → 时间 → 退出条件。
「退出条件」指**允许提前结束这一阶段**的条件，避免完美主义拖住后面。

### S0 基座与清场（0.5 天，D1R1）

- **条目**：H1、H2（骨架）、H3、H4、H5、A1、A2、A3、A5、A4、G1
- **步骤**
  1. 把 `tools/_perf_bench.py` 与 `tools/_perf_pool.py` 合并成 `tools/bench_sim.py`：`--n`、`--workers`、`--json out.json`，输出 p50/p95/min/max 与 ms/千 tick。
  2. `python -X importtime` 采一次启动剖面，落 `output/perf/importtime.txt`。
  3. 用 `sys.monitoring`（或 py-spy）采 3 场真实剖面，落 `output/perf/profile.json`，与 v1 的 cProfile 名单对照。
  4. 删 `gd_core/CoreCombat.gd:251` 的无条件 `INJ_ARM` print，四树同步 → 重转写 → REG 7 场。
  5. 连续跑 5 轮 bench，确认 p50 波动 ≤3%（A3 口径），否则先解决降频/后台干扰再继续。
- **验收**：`output/perf/baseline_20261109.json` 入库；同一条命令两次跑出 ±3% 内结果。
- **退出条件**：baseline 可复现即可结束，剖面能给出热名单前 10 名就算达标（不必精确到行）。

### S1 并行快赢（1.5 天，D2R1 + D1R1）

- **条目**：E1、E2、E3、E4、B9、G2、G3、G4
- **步骤**
  1. `simulator/gd_core_engine.py` 暴露模块级 `_run_one(seed, lineup_json)`（可 pickle），供进程池调用。
  2. CLI 加 `--workers N`（默认 `min(4, cpu)`，`--runs 1` 强制单进程）；GUI `_run_battle` 起 `ProcessPoolExecutor`，进度按完成数回报并 50 ms 节流（G4）。
  3. worker 常驻 + 启动后预热一次 kernel 与一次空场（B9）。
  4. 任务改成**小批次动态领取**（E2），不是静态 seed 分块：每 worker 取 8 场，长尾场不再拖住整块。
  5. 结果只回传统计（胜负、tick 数、时长），不回传事件流（E3）。
- **验收**：`bench_sim.py --workers 1/2/4/8` 四档落盘；同 seed 同胜负逐 seed 对拍（对照全量探针单进程结果）；GUI 千场不卡界面。
- **预期**：本机 2.0–2.2x；8 物理核桌面 6–7x。
- **退出条件**：拿到 ≥1.8x 且胜率对拍全等即可收工；E2 的调度优化若只多给 5% 以内，记为已完成不深挖。

### S2 启动（1 天，D2R1 + D1R1）

- **条目**：B2、B3、B7
- **步骤**
  1. `load_all()` 拆两档：`load_core()`（Core*、基类、`gd_core_items` 基类）+ 按阵容 `load_for(items)`；工具链保留 `load_all()`。
  2. 打包链加预编译 pyc，发布产物带 `__pycache__`（B3）。
  3. GUI 开窗后台线程预热 kernel（B7）。
- **验收**：冷启动 < 0.5 s（目标 <150 ms 归 B1 条件项）；REG + 56 局不变；`_R.missing()` 为空。
- **退出条件**：< 0.5 s 即达标。要再往下必须动 B1（全惰性），那属于 E 组，先记着。

### S3 纯 Python 零风险批量（2–3 天，D1R1 主力）

- **条目**：C1、C2、C3、C4、C5、C7、C12、C13、C14、C15、C17、C18、C19、D1
- **步骤（按批次，每批一次 REG，批末一次全量）**
  - 批 1：**C4**（`_R.C` 绑成模块级常量）+ **C5**（`GD_DEFAULT` 展开）—— 收益最大，改动最机械。
  - 批 2：**C1**（`_iter` 直发）+ **C2/C15**（热循环局部绑定）—— 生成器变换，配 H2 的 AST 差分自证。
  - 批 3：**C3/C18**（帧内微调）+ **C7**（信号存 bound 方法）—— 手改 `_rt.py` 为主。
  - 批 4：**C12–C14**（MC 探针轻量）+ **C17/C19/D1** —— 只影响 runs>1 路径与去重实现。
- **验收**：每批 REG 7 场 + 批末全量 1690 双判据 + 56 局逐字符；每批附 before/after JSON。
- **预期**：378 → 180–240 ms。
- **退出条件**：达标即停，不要为了再挤 3% 去碰 C6/C9（那是 S4）。

### S4 审计项（3–4 天，D2R2，逐个上闸）

- **条目顺序按收益/风险比**：C6 → C16 → C8 → D2 → D3 → D4 → D5 → C9（最后，且可放弃）
- **每项固定动作（缺一不可）**
  1. 写「失效清单」：哪些状态变动会让缓存/表失效，落在代码里的钩子位置。
  2. 实现 + 单量测（REG + 全量 1690）。
  3. 若 1690 有任一红：立刻回滚该项，结论写入规划文档 §5，不重试。
- **C9 特别规定**：`getSpeed` 缓存是本阶段唯一碰数值语义的项，收益 8–12%，但漏一个钉点就会在长局漂移。**默认不做**；只有 S3 后仍差 10% 以上才考虑，且必须先过 1690 + 56 局 + 一轮 3000 场 MC 胜率对拍。
- **预期**：180–240 → 130–190 ms。
- **退出条件**：C6 落地后若只剩个位数收益，余项全部推给 N6 条件项。

### S5 结构性改造 + 编译后端（1–2 周，D3R3，单独上闸）

- **条目**：F5 → F1（热 8 模块）→ F2 → F7
- **步骤**
  1. **F5 先行**：生成器把 tick 主循环输出为「无方法派发的单函数」——循环骨架、时间推进、判胜内联；物品回调仍走调用。先以纯 Python 形态过 1690，确认等价。
  2. **F1 分批**：按 CoreItem → CoreCombat → CoreCharacter → CoreTimer → CoreRng → CoreBuff → CoreGrid → CoreEventBus 顺序，每次编译 1–2 个模块，**单模块可回落纯 Python**。
  3. **F2**：`_rt.PCG32` 下沉 C `unsigned long long`，跑 `verify_godot_rng.py` 逐位。
  4. **F7**：`binding=False`、`embedsignature=False`、freelist 等旗标，A/B 一次定去留。
- **验收**：每批 REG → 全量 1690 → 56 局逐字符；打包链加编译步骤后 `dist/` 可跑。
- **预期**：40–90 ms，叠并行本机 10–20 场/s。
- **退出条件**：热 8 模块编译完成、单场 ≤90 ms 即停；物品脚本长尾（145 个）收益递减，留作后续按热名单挑。

## 6 最短路径（只有 3 天时做什么）

按「投入产出比」砍到只剩 5 项，其余全部推迟：

| 顺序 | 项 | 用时 | 累计收益 |
|---|---|---|---|
| 1 | H1 + G1 + A3（基座与清场） | 0.5 天 | 可比基线 |

其余（S2/S3 剩余、S4、S5）按 4–6 周排期。

## 8 风险登记（按可能性排序）

| 风险 | 触发信号 | 预案 |
|---|---|---|
| 机械变换悄悄改语义 | 全量 1690 出现零星红，且随批次不同而变 | H2 AST 差分逐文件核对；无法解释就整批回滚 |
| `_R.C` 静态绑定破基类拓扑序 | 导入期 `_R.missing()` 非空 | 绑定必须放在模块**末尾**（reg 之后）；REG 已有此闸 |
| 并行收益被 IPC/启动吃掉 | 4 workers 只有 1.3x | 先上 E3（只回传统计），再上 B9（预热） |
| 缓存失效漏点 | 全量绿但长局漂移（MC 胜率偏） | 依赖清单审计 + 3000 场对拍；C9 默认不做 |

| 降频导致结论假 | 两轮 bench 差 >5% | A3 交错对照 + A6 绑核；数字只报同机同日 |
| 优化项反复重试 | 同一项第三次开工 | 止损线：投入 2 天未过全量闸即回滚并写入规划 §5 |

## 10 性能用什么表征（指标口径）

结论先说：**没有单一数字能代表「性能提升」**。本项目要同时回答三个问题——单场快不快、批跑吞吐高不高、开会话/开 exe 等不等得起；
再加一条硬约束：**正确性指标必须和性能指标一起报，否则性能数字无效**（跑得快但 1690 红了的数字不算数）。

### 10.1 一级指标（门禁指标，决定 Go / No-Go）

| 指标 | 定义 | 单位 | 为什么用它 | 现状基线 |
|---|---|---|---|---|
| **单场 p50** | 同 lineup 集合、N 场的中位时长 | ms | 主指标；抗异常场干扰 | 378 ms |
| **单场 p95** | 同上 95 分位 | ms | 长尾代表；防「中位变快、长局变慢」 | 未测（S0 补） |
| **ms/千 tick** | p50 ÷ 平均 tick 数 ×1000 | ms | **归一化**，消除对局长短差异，跨 lineup 可比 | 未测（S0 补） |
| **单核吞吐** | 1000 ÷ p50 | 场/秒·核 | 对外好理解的等价口径 | ≈2.6 |
| **冷启动 TTFB** | 进程启动 → 第一场结果返回 | s | 用户真实等待；比「import 耗时」有意义 | ≈1.2 s |
| **并行吞吐** | `--workers N` 下的 场/秒 | 场/秒 | 必须与 N 一起报，单报无意义 | 4w ≈2.0x，8w ≈2.2x |
| **加速比 S(N)** | `T(1) / T(N)` | 倍 | 衡量并行效率，非单场速度 | 同上 |
| **MC 千场墙钟** | 1000 场从开始到统计输出 | s | 交付级口径，用户最关心 | ≈6.5 min |

**伴随指标（同表必报）**：1690 双判据通过数、56 局逐字符通过数、RNG 探针结果。任一不过，该行性能数字标灰、不得引用。

### 10.2 二级指标（诊断指标，决定「下一步优化谁」）

| 指标 | 定义 | 用途 |
|---|---|---|
| tick 速率 | tick/秒 = 总 tick ÷ 总时长 | 判断瓶颈在「每 tick 成本」还是「tick 数」 |
| 平均 tick 数 / 超时场占比 | 180 s 上限触顶的场数 ÷ 总场数 | 决定 D8、E2 值不值得做 |
| 事件流条数与字节数 | 每场 events 条数、序列化字节 | **语义不变探针**：数字必须严格不变 |
| 峰值 RSS | 单进程峰值内存 | 判断深对象图是否成为并行上限 |
| gen2 GC 次数 | `gc.get_stats()` 前后差 | 验证 C 组与 GC 调参是否真有用 |
| 启动分解 | import / 数据解析 / GUI 初始化 三段 | 启动优化只准打最大那段 |
| 发行物体积 | exe + pyd 总大小 | Cython/打包变更的代价，需要留档 |

### 10.3 明确不采用的表征（反例，写下来防回潮）

| 反例 | 为什么不行 |
|---|---|
| 单场最好成绩（min） | 受 CPU 空闲时机影响，噪声最大的量，最容易「优化成功」 |
| cProfile 累计时间 | 有 ~2.6x 分析器开销，派发类热点被系统性放大（v1 数字已受此影响） |
| 只报 CPU time | 掩盖 IO、GC、进程启动成本 |
| 不带 `--workers` 的加速比 | 「2.2x」在单核上毫无意义，必须绑 worker 数与核数 |
| 换 lineup 集合后的对比 | 不同 lineup 时长差异极大，跨集合比较无效 |
| 胜率变化 | 那是**正确性**信号，不是性能信号；两者混淆会掩盖破闸 |
| 「感觉快了」/ 单次跑 | 降频与后台进程可造成 10% 以上假象 |

### 10.4 口径纪律（`bench_sim.py` 必须固化，不许人工调整）

1. **交错 A/B**：同一进程内交替跑两支配置（A,B,A,B…），避免全核降频漂移；只比较交错后的中位数。
2. **绑核**：并行测试固定物理核，避开超线程争抢；数字必须注明 `--workers` 与核数。
3. **N ≥ 20** 单场、**N ≥ 128** 并行；样本不足只报「趋势」不报倍数。
4. **报 p50 + p95 + ms/千 tick**，三个一起报，缺一视为未完成。
5. **同机同日**：跨机器只写「预期」，并注明核数与功耗约束。
6. **每份数字带命令与 JSON 路径**，任何人可复现。
