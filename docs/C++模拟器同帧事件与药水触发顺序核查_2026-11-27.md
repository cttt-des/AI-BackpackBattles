## 原版真正规定的顺序

以 **1.1.10** 的 `output/_v1110/decompiled/` 为本次源码依据，不把旧版文档的帧阶段注释当成当前实现。

1. `Core/Game.gd:3012` 起，玩家和对手分别取背包物品副本、洗牌，再以 `getTriggerPriority()` 降序排序。`prepareItems` 按该结果逐件 `prepare`，因而决定战斗信号的注册顺序。原版 Godot `sort_custom` 为非稳定排序；相等优先级的最终顺序不能只用稳定排序替代。
2. `Utility/EventBus.gd:56` 的 `emitAndLog` 按连接数组顺序同步执行回调，没有每次按优先级重新排序，也没有统一延至帧末。嵌套派发先执行完，再返回外层下一个监听器。
3. `Core/Character.gd:827` 的 `useStamina` 先打开允许溢出窗口，发出 `character_pre_use_stamina`，待同步回调完成后再判断、扣除和钳制体力。勇气药水在此信号中逐瓶重新检查当前体力；先一瓶补够后，后一瓶可以不喝。
4. `Items/HealthPotion.gd:12` 的生命药水在 `character_damaged` 中重新检查当前相对血量。强效生命药水优先级 1001，普通生命药水 1000，普通默认物品 0；前一瓶治疗后，后一瓶可能不再满足阈值。
5. `Items/Potion.gd:57` 的饮用顺序为：空瓶检查 → `drink` → 自身 `triggerPotion(event)` → 相邻首瓶 `triggerPotion()` 和 `miniActivate()` → 自身 `activate()`。`triggerPotion` 先执行效果，再发 `potion_triggered`；`Potion.activate` 在父类激活后才发 `potion_emptied`。相邻触发不会自动喝空相邻瓶，且原文没有向相邻触发传递自己的 `event`。

原版 Godot 的数组迭代会在每次 `iter_next` 检查**当前数组长度**，依据仓库保存的 Godot 3.6 `core/variant_op.cpp:3136`。监听数组增长／清空的行为必须以这个真值为准。

## 独立复现的结果

测试分别启动真实 Godot 3.6 和独立 EXE。Godot 侧执行从原版提取且函数体保持的药水流程、勇气／生命药水条件、角色 `useStamina`，以及原版 EventBus；后者只去除了四处 `CombatEvent` 类型标注。视觉、日志服务及治疗／补体力服务使用夹具桩，因此这是**控制流、信号次序与最终相关状态**的定向验证，不是新增完整游戏对战语料。

C++ 侧直接链接本次部署 DLL，调用真实生成类的方法，不用新写的模拟器代替真 DLL。Python 侧实际加载 `_rt.pyd` 和 `CoreEventBus.pyd`，不是只检查 `.py` 文本。

## 影响边界与此前验证的缺口

**C++ 默认入口**：`engine_wrapper.cpp:1352` 的默认 `native_activation_order=true` 和训练入口采用专用排序；显式给定 `activation_order` 的回放入口直接采用已观察到的顺序。它们没有命中上面的通用开战排序问题。显式关闭原生顺序且不提供终序时，才会落到 `CoreCombat.startBattle(...,false)` 的通用排序。通用排序还承载其他脚本的 `sort_custom`，需要分别补覆盖，不能因为默认开战正确就忽略。

**Python 现用内核**：`gd_core_py/gd_core/CoreCombat.py:275` 调用 `_sort_custom`。`simulator.simulate` 的默认内核是 `gd_core`；训练器在版本化 native runtime 可用时优先使用 native，显式选 Python 或 native 不可用时才走 Python。不能把旧 Python 引擎与这个现用 Python 内核混称。

**旧 `simulator/item.py:1595`**：另行实测确认 `consume_potion` 在空瓶检查和实际效果前就发 `potion_emptied`；对已经空的瓶子调用，仍额外发一次 emptied。这与原版顺序明确不符。不过 `simulator/combat.py` 已不在 CLI 默认内核列表中，该问题应列为旧入口错误，不能直接用于解释当前 native 用户的反馈。

**C++ 历史测试存在真值错误**：`output/_v1110/test_native_event_kernel.cpp:49、63` 写着“追加监听器等待下一次派发”，并断言首次只有 `[1,2]`。该测试只对比了 C++ 的普通／优化路径，两边共享长度快照，因而会一起通过。真实 Godot 反例已证明这个预期不对。后续修复必须更正此预期，同时保留并记录旧失败证据；不能继续以旧 DLL 为唯一正确性真值。

上一生产 D206 DLL 与当前 291d DLL 在本次完整 native 定向输出上逐项相同，证明上述差异**早于最近的装配成员查询优化**。已有 2604 场逐事件通过仍有效，但它们不能取代新增的派发中变更用例；回放注入 `activation_order` 也不能验证未注入时的默认排序生成。

## 建议的修复顺序

先修现用 Python 与 C++ 通用排序，使等值次序也符合 Godot，保留默认专用路径的既有顺序；再修 C++ 事件总线对数组当前长度的处理，并同步修改转译／优化生成流程和错误测试预期。更广泛的数组迭代也应审计，但不宜把全仓库循环直接替换后仅以旧 DLL 差分判定正确。

修复验收应包括：上述真实 Godot 反例、实际双瓶药水、腰带／相邻触发、派发中增长／缩短／替换／嵌套／终局，以及不注入激活终序的开战用例；随后再进行完整原版语料对比。当前尚未拿到反馈对应的具体战斗输入，不能认定已经定位其唯一根因，也没有将尚未完成整场验收的正确性修复部署。
