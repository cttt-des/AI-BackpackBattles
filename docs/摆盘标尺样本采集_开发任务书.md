## 0. 背景：这批东西是干什么用的

训练侧的搜索已经能产出摆盘（池 A 胜率 0.965 vs 人类中位 0.690），
但**不知道"够不够好"**——没有绝对标尺。

需要 **3–5 个真人高手的摆盘样本**，用途是三个判断（**不是训练标签**）：

| 用途 | 怎么用 | 为什么重要 |
|---|---|---|
| **验证合法性判定器** | 高手不可能摆出非法摆盘 ⇒ 若 `check_layout` 判非法，是**我们规则错了** | 防规则错，最便宜的正确性检验 |
| **校准解析分权重** | 高手摆盘在解析分上排第几 ⇒ 判断方向对不对 | 免去训模型 |
| **高手 vs 搜索** | 搜索能否打赢高手 ⇒ **决定后续是否继续投入** | 最高价值 |

**3–5 个样本训不了任何模型**，所以这不是数据采集，是**标尺采集**。

## 3. 交付物 1：H 生成器（**先做这个**）

### 3.1 接口

```python
# 建议文件：trainer/make_probe_holding.py
def make_holding(round_no: int, character: str | None = None,
                 inject_items: int = 3, overfill: float = 0.10,
                 seed: int = 0, out_dir: str = "probe_samples") -> dict:
    """生成一套带取舍压力的持有列表 H。

    参数:
      round_no:     目标回合 1..18（决定可用稀有度与典型规模）
      character:    职业；None 则从该回合真实阵容里随机取
      inject_items: 注入的额外物品件数（制造取舍压力）
      overfill:     目标超容比例（0.10 = 物品需格比容器多 10%）
      seed:         随机种子（同种子必须产出同一套 H）

    返回: {"H": v4_dict, "baseline": v4_dict, "stats": {...}}
    同时写出三个文件（见 §3.4）
    """
```

**命令行**：

```bash
python trainer/make_probe_holding.py --round 12 --character Ranger --inject 3 --out probe_samples/
python trainer/make_probe_holding.py --preset all      # 一次生成 §3.5 的 5 套
```

### 3.2 构造规则（**每条都要遵守，否则样本没意义**）

| # | 规则 | 理由 |
|---|---|---|
| 1 | **基底 = 该回合真实终盘阵容的已摆集合** | 保证合法、真实、组合合理 |
| 2 | **注入物品取自同回合其他真实阵容** | 分布真实（回合决定稀有度上限） |
| 3 | **`Σ物品需格 > Σ包格 × (1 + overfill)`** | 制造明确取舍压力 |
| 4 | **不要注入包**（只注入非包物品） | 否则容器变大，取舍压力消失 |
| 5 | **至少 3 件"可舍弃"物品** | 让取舍有意义 |
| 6 | **物品 id 必须是 `assets/gd_core_runtime.json` 的 key** | 否则引擎装不上 |
| 7 | **生成后必须跑 `check_layout`** | 基底必须合法；H 可以不合法（这正是压力） |
| 8 | **同 seed 必须可复现** | 便于对照与复算 |

**关键概念**：`H` 表达"持有"而非"摆放"，所以 `H` 的 `at` 坐标**没有约束意义**
（物品必然放不下）。但要给一个**初始摆放**用于：① 玩家有起点 ② 桥接器注入时用。

### 3.3 两个必须正确计算的量

```python
# 容器格：所选包的占格总和（包与包不重叠，所以直接相加）
cap = sum(len(idx.collision_cells(it["id"], it["r"])) for it in H if it["id"] in idx.bag_set())

# 物品需格：非包物品的占格总和
need = sum(len(idx.collision_cells(it["id"], it["r"])) for it in H if it["id"] not in idx.bag_set())

# 取舍压力
over = (need - cap) / max(cap, 1)   # 应 >= overfill
```

⚠️ **实测参考值**（corpus 抽样中位数，用来校验你的统计对不对）：

| 回合 | 包数 | 容器格 | 物品需格 | 充裕度 |
|---|---|---|---|---|
| R1 | 3 | 14 | 11 | +21% |
| R5 | 7 | 28 | 25 | +11% |
| R12 | 15 | 50 | 45 | +10% |
| R18 | 19 | 63 | 61 | +3% |

**若你算出的容器格远超 63，说明统计口径错了**（真实阵容的 distinct 格数 ≤63）。

### 3.4 三个产出文件

**① `<name>.H.json`** —— v4 持有列表（给桥接器）

```json
{
  "version": 4,
  "name": "probe_R12_Ranger",
  "character": "Ranger",
  "round": 12,
  "grid": [7, 9],
  "items": [
    {"id": "Leather Bag", "at": [0, 0], "r": 0},
    {"id": "Lucky Bow",   "at": [1, 0], "r": 0}
  ],
  "meta": {
    "cap": 50, "need": 55, "overfill": 0.10,
    "injected": ["Fancy Fencing Rapier", "Boomerang", "Pan"],
    "baseline_name": "probe_R12_Ranger_base",
    "seed": 0
  }
}
```

**字段语义**（以运行时资产为准）：

| 字段 | 含义 |
|---|---|
| `id` | 物品名（英文，与资产 `items` 的 key 一致） |
| `at` | `[row, col]`，7 行 × 9 列 |
| `r` | 朝向：0 / 90 / 180 / 270 |

**② `<name>.清单.md`** —— 中文表格（给真人玩家）

**样例**（必须严格照这个结构）：

```markdown
# 持有清单：probe_R12_Ranger

- 回合：R12
- 职业：Ranger
- 物品总数：**23 件**（其中包 6 件）
- 容器格：**50 格**；物品需格：**55 格**
- ⇒ **需要舍弃约 5 格，也就是少上 3–4 件物品**
- 目标：对 [450, 650] 分段对手，**期望胜率最大化**

> 表里是你手上的**全部**物品，不要求全上。
> **摆不下是正常的**，请选择你认为最好的组合。

## 背包（容器，占格但提供空间）

| 数量 | 中文名 | 英文名（备查） | 占格 |
|---|---|---|---|
| 3 | 皮革包 | Leather Bag | 4 |
| 2 | 腰包 | Fanny Pack | 2 |
| 1 | 工程师箱 | Engineer Box | 6 |

## 武器与装备

| 数量 | 中文名 | 英文名（备查） | 占格 |
|---|---|---|---|
| 2 | 幸运弓 | Lucky Bow | 2 |
| 1 | 花式击剑刺剑 | Fancy Fencing Rapier | 3 |
...
```

**硬性要求**：

| 要求 | 原因 |
|---|---|
| **必须有中文名**（`simulator.i18n.zh_name`） | 玩家在游戏里看到的是中文 |
| **必须带英文名** | 中文可能重名/歧义，英文是权威 id |
| **必须标数量** | 玩家最关心"要几件" |
| **必须分"背包"与"其它"两块** | 包是容器，性质不同 |
| **必须标占格** | 让玩家预判容器够不够 |
| **必须算出取舍压力** | 明确告诉玩家"要舍弃几件" |
| **必须写"允许舍弃"** | 否则玩家硬塞，样本失效 |

中文名映射已就绪：`simulator/i18n.py:zh_name`，覆盖 **519/519，0 缺失**。
实测：`Lucky Bow`→幸运弓、`Leather Bag`→皮革包、`Fanny Pack`→腰包。

**③ `<name>.初始摆盘.json`** —— 解析分给出的初始布局

用 `layout_rules.analytic_score` 对 H 找一个合法子集 + 布局，作为玩家/桥接器的起点。
**不求最优**（那正是玩家要做的），只求"有个像样的起点"。

## 4. 交付物 2：桥接器 `load_holding`（游戏侧）

### 4.1 目标

玩家打开游戏（沙盒模式），背包里**直接出现 H 的全部物品**，可随手拖拽。

**为什么值得做**：玩家不用手动挑 23–50 件，省掉最容易出错的一步
（挑错一件，整份样本作废）。

### 4.2 只新增一个命令

```json
{"cmd": "load_holding", "args": {"H": { ...v4 完整对象... }}}
// 返回 {"ok": true, "loaded": 23, "failed": [], "skipped": []}
```

外加一个可选的自检命令：

```json
{"cmd": "verify_holding", "args": {"H": {...}}}
// 返回 {"missing": [...], "extra": [...]}
```

**不要实现导出**——已有方法，直接复用。

### 4.3 实现要点

| # | 要点 | 说明 |
|---|---|---|
| 1 | **先清空背包** | 避免残留物品混进样本 |
| 2 | **按初始摆放放置** | 用 `<name>.初始摆盘.json`，让玩家有起点 |
| 3 | **放不下的物品要报告** | `failed` 列表，不要静默跳过 |
| 4 | **宝石要带上** | `H` 里若有 `gems` 字段 |
| 5 | **在沙盒模式下操作** | 不碰真实存档 |
| 6 | **命令名不要与现有命令冲突** | 先 `get_node_methods` 看清单 |

### 4.4 待探明的技术点（**沙盒模式简化了这些**）

| # | 待确认 | 说明 |
|---|---|---|
| A1 | 沙盒模式下怎么造物品 | 沙盒能手动选物品 ⇒ 游戏有现成造物品路径可复用 |
| A2 | `crafted` / `gems` / `mods` 怎么设置 | 不设会变"白板物品"，与真实不同 |
| A3 | 是否必须走 UI 拖拽 | 沙盒有该 API 则可直接调用 |

**建议先花半天做最小探针**（只用现有命令）：

```python
{"cmd": "find_node", "args": {"name": "ItemBook"}}
{"cmd": "get_node_methods", "args": {"path": "<ItemBook 路径>"}}
{"cmd": "find_node", "args": {"name": "INVENTORY"}}
{"cmd": "get_node_methods", "args": {"path": "<INVENTORY 路径>"}}
```

**探针通过标准**：能在这两个节点的 `get_node_methods` 输出里
看到「描述符查询」类方法与「加物品」类方法。

### 4.5 验收标准

| 闸 | 标准 |
|---|---|
| 1 | 注入 20 件的 H，游戏内出现 20 件，`verify_holding` 报 `missing=[]` |

## 5. 路线 B：纯清单方案（**零开发，立即可用**）

**这不是备胎，而是"先拿到样本"的推荐路径。**

因为**游戏有沙盒模式**：

```
H 生成器产出中文清单 → 玩家在沙盒里按清单挑物品 → 摆盘 → 已有方法导出
```

| 维度 | 路线 A（桥接器） | 路线 B（清单） |
|---|---|---|
| 开发成本 | 中（写 GDScript） | **零**（交付物 1 已完成就够） |
| 玩家成本 | **零** | 中（沙盒里手动挑） |
| 样本质量 | **高** | 中（可能漏件/挑错） |
| 加人风险 | 低 | **高**（每多一人多一套手工成本） |

**推荐执行顺序**：

1. **交付物 1 完成 ⇒ 立刻用路线 B 拿第一批样本**（1–2 位玩家，3 套 H）
2. 同时开发交付物 2
3. 桥接器通了之后，后续样本改走 A，B 退为兜底

> ⚠️ **不要为了把桥接器做完美而推迟第一批样本。**
> 3 个样本能立刻回答"我的合法性判定器有没有错"和"搜索能不能打赢高手"，
> 这两个结论比插件本身重要得多。

### 5.1 给玩家的说明（随清单一起发，**必须写**）

1. 「表里是**你手上的全部物品**，不是全部都要上」
2. 「**摆不下时可以少上**，少上几件是允许的，请选你认为最好的组合」
3. 「请**在沙盒模式**里按清单挑出这些物品」（不要碰真实存档）
4. 「摆完请用**现有导出方法**导出当前阵容」
5. 「**请按最大化胜率来摆**，不要按平时习惯随手摆」
6. 「有物品不知道怎么用就忽略它」（避免硬凑）

### 5.2 唯一还需确认的点

**沙盒模式里能不能拿到并放置「包」？**

包是容器，没有包什么都摆不了。若沙盒只给固定网格、不能加包，
路线 B 需要换方式（如让玩家在正式对局中后期导出）。

## 6. 数据契约（两个交付物共用的唯一真相）

### 6.1 H（持有列表）

```json
{
  "version": 4,
  "name": "probe_R12_Ranger",
  "character": "Ranger",
  "round": 12,
  "grid": [7, 9],
  "items": [
    {"id": "Leather Bag", "at": [0, 0], "r": 0},
    {"id": "Lucky Bow",   "at": [1, 0], "r": 0}
  ],
  "meta": {"cap": 50, "need": 55, "overfill": 0.10, "injected": [...], "seed": 0}
}
```

- `version` 恒为 4
- `grid` 恒为 `[7, 9]`（**7 行 × 9 列**，别搞反）
- `at` = `[row, col]`；`r` ∈ {0, 90, 180, 270}
- `id` 用**英文名**，必须与 `assets/gd_core_runtime.json` 的 `items` key 一致
- `meta` 是附加信息，训练侧不依赖（但便于追溯）

### 6.2 S（玩家的摆盘）

由**已有导出方法**产出。训练侧要求它至少含：

```json
{
  "version": 4, "character": "...", "round": 12, "grid": [7, 9],
  "items": [{"id": "...", "at": [r, c], "r": 0}],
  "meta": {"h_name": "probe_R12_Ranger", "player": "A", "excluded": ["..."]}
}
```

| 必须字段 | 为什么 |
|---|---|
| `meta.h_name` | **指回是哪个 H**，否则样本无法配对 |
| `meta.excluded` | 玩家舍弃了哪些（用于对照"高手怎么选"） |
| `meta.player` | 同一 H 有多个玩家时区分 |

⚠️ 如果已有导出方法**不产出 `meta`**，开发侧要补一层包装（读 H 的 items，
逐件比对 S，自动算出 `excluded`）。

## 7. 验收与回报

### 7.1 交付物 1（H 生成器）

| 项 | 标准 |
|---|---|
| 五套预设 | `--preset all` 一次产出 5 套 × 3 职业 |
| 每套三文件 | `.H.json` / `.清单.md` / `.初始摆盘.json` 全齐 |
| **取舍压力** | 每套 `need / cap − 1 ≥ overfill`（默认 10%） |
| **合法性** | `H` 的基底过 `check_layout`；`初始摆盘` 必须过 `check_layout` |

| **可复现** | 同 `seed` 同参数，两次产出逐字节相同 |
| **统计正确** | 容器格 ≤63（若超过，口径错了） |

## 附：为什么只有 3–5 个样本

**不是数据采集，是标尺采集。** 三个用途见 §0。

**质量 > 数量**：宁可 3 套高质量（**同一个 H 由 2 位高手各摆一次**），
也不要 5 套各 1 人且玩家没认真摆。

**同 H 多人的价值**：能看清"高手之间是否一致"——若两位高手给出差异很大的摆盘，
说明这个问题本身有多解，搜索的容差应该放宽。
