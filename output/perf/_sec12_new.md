## 12 本轮实测与下一步规划（2026-11-13，专注模拟器；`5e092dde`）

> 用户要求「继续专注模拟器性能」。本轮不再猜方向，先把**三个从未被量化过的数**测出来：
> 并行效率到底卡在哪、装配的 28 ms 花在哪、`physicsTick` 里还有没有冗余解析。
> 结论：**单场延迟线确实见底**（三个假设两个被证伪），剩余空间在**装配**与**吞吐口径**，
> 而后者此前所有结论都被外部负载污染过。

### 12.1 已落地：`load_for` 索引化（`5e092dde`）

| 项 | 优化前 | 优化后 | 证据 |
|---|---|---|---|
| `load_for` | **7.5 ms/call** | **0.18 ms/call（41x）** | `tools/_loadfor_cost2.py`，`process_time` 累计 300 次 |
| 装配 p50 | 31.2 ms | **28.6 ms** | `tools/_asm_acc.py`，`perf_counter` 累计 12 场 × 7 轮取中位 |

**根因**：`load_for` 对每个阵容脚本线性扫一遍 `_ITEM_ORDER` 全表（108 脚本 × 505 项 = **5.5 万次 `str.rsplit`**），
且是**每场都付的边际成本**（不是冷启动摊薄——这点此前被 §9.1 记成「首场-only」，与实测矛盾，已纠正）。

**做法**：生成器发射 `_ITEM_STEM`（stem→rel，生成期断言无重名）与 `_ITEM_MODULES`（拓扑序导入表），
`load_for` 改为 O(1) 查表 + 按需循环导入，取代 505 条静态 `if` 链（`_bootstrap.py` 7620 → 6121 行）。

**等价性（全量非抽样）**：505 个 stem × 3 种写法 + 真实 R19 双方 108 脚本 + 边界输入的 `want` 集合
**全等，TOTAL FAILS = 0**；三闸 **seed 双态 907/1548、1042/1991 逐位不变 / REG9 9/9 / 60 场 60/60**。

### 12.2 被证伪 ①：并行效率不是内核问题，是外部负载（**推翻 §3.2 的判据基础**）

起因：4 worker 实测 5.46 场/s vs 单核 3.2 场/s，效率只有 **0.40–0.45**——看起来有 2x 空间。
第一反应是 SMT 争抢（4 物理 / 8 逻辑）。**用 `process_time` 逐项证伪**：

| 组 | 亲和性 | p50_cpu/场 | 说明 |
|---|---|---|---|
| serial | 无 | **625.0 ms** | 单进程基准 |
| w4_free | 无 | **687.5 ms** | 并发下每场 CPU 只多 **+10%** |
| w4_p0123 | 0,1,2,3 | 609.4 ms | 四个不同物理核 |
| w4_p0246 | 0,2,4,6 | 593.8 ms | 四个不同物理核 |

**判读（关键）**：`process_time` 已排除被抢占时间，四组相差 **<15%** ⇒ **既没有 SMT 惩罚，也没有 L3 墙**。
`cores_eff` 只有 1.4–1.8 / 4，是因为测量时**外部负载 93–96%**（ZCode/WeChat 等），不是内核并行性不足。

**同时暴露一处历史误判**：`tools/_par_cores.py` 测到「4 worker 每场 625 ms vs 单跑 312 ms = 慢一倍」，
当时极易被读成「内核并行退化」；实际 312 与 625 是**两次不同负载下**的读数（27% vs 95%），不是同一个数。
⇒ **吞吐结论必须带负载，或用 `cores_eff` 归一化**（§9 那条纪律的具体办法）。

**绑核复测（顺带）**：静窗口 2 轮 × 128 场，`0,2,4,6` 中位 **6.34**、`1,3,5,7` **6.18**、
`none` 5.47、`0,1,2,3` 5.56 场/s ⇒ 集合间差 **+16%**，但仍低于负载噪声，**只能算待重测，不能算收益**。

### 12.3 被证伪 ②：`physicsTick` 已内联，`character()` 冗余只值 1.2%

**发现**：物品的 `physicsTick` 并不存在——它已被内联进 `CoreCombat.physicsTick` 的物品循环：

```python
for item in _iter__loc(self.opponent.inventory.getItems()):
    if item._cooldown_active:
        if not (item.character().stunnedDuration > 0):   # ← 每物品每 tick
            item.triggerTime -= delta * item.getSpeed()  # ← 每物品每 tick
            if item.triggerTime <= 0:
                item.trigger()
```

所以「`physicsTick` 84%」指的是**这个循环体**，不是方法调用开销。剩下的可疑项是 `item.character()`
每 tick 每物品都解析一次（51 物品 × 907 tick ≈ **9.2 万次/场**），而物品归属角色**装配后恒定**（已实测 True）。

**实测收益（102 万次调用）**：72 ms → 79 ms，**0.907x（缓存反而略慢）**；单次 `character()` 只 **0.07 µs**，
折算单场 **3.2 ms ≈ 1.2%**。⇒ **这条线不值得做**，§11.1「Python 层见底」的结论成立且更硬。

### 12.4 装配的精确构成（下一步主战场）

`cProfile` 逐函数拆（12 场，表内为**每场**摊销）：

| 位置 | tottime | cumtime | 判读 |
|---|---|---|---|
| `_build_side` 自身 | **16.13 ms** | 29.16 ms | 纯 Python 循环开销：108 物品 × 每物品 0.15 ms |
| `_make_item` | **8.18 ms** | 8.69 ms | `R.C(script)()` + `setup()` + 三组 Vector2 列表推导 |
| `_place` | 2.26 ms | 12.80 ms | 几何 + `_readyInit` |
| `_place_of` | 0.82 ms | 1.04 ms | 每次重建 `collision`/`affected`/`occupied` 三个结构 |
| `load_for` | 0.30 ms | 5.70 ms | ✅ 本轮已消（→0.18 ms） |

**结构性冗余（可做，零语义风险）**：

1. `_build_side` 每物品重复 `self._K`/`k["_R"]`/`k["Vector2"]` 查找与 `getattr(self, "_pending_crafted", None)` —
   提到循环外做局部绑定（与 S3-C6「访问器内联」同型手法，已验证有效）。
2. `_place_of(data, key, row, col, rot)` 里 `r = ent["rot"][str(rot)]` 部分**只依赖 (key, rot)**，
   可缓存「未平移的 anchor/affected/occupied」，再叠加 `(row,col)` 平移——现在每场对同 key 同朝向重算一遍。
3. `it.chargeFrame = [vec(...)] * 4` 与 `collisionCells` 的 `vec()` 逐物品分配：`chargeFrame` 四项同值，
   可共享同一个不可变 `Vector2`（构造期一次性）。

**判读**：这三项合计目标 **28.6 → ≤22 ms（≥20% 降）**。装配占整场约 **11%**，故整场收益约 2–3%；
**这是当前唯一还能拿到确定性收益的地方**（单场 tick 侧已见底）。

### 12.5 下一步（按性价比排序，全部可独立验收）

| 序 | 项 | 做什么 | 判据 | 预期 | 风险 |
|---|---|---|---|---|---|
| **P1** | 装配局部化 + 几何缓存 | §12.4 的三项 | 装配 p50 **≤22 ms**（`_asm_acc.py` 同口径）；三闸全绿 | 整场 −2~3% | 低（不动 tick，不动语义） |
| **P2** | 吞吐口径重建 | `cores_eff` 归一化基线 + 绑核集合重测（`0,2,4,6` vs `4,5,6,7` vs `none`，静窗口，n≥256，≥4 轮） | 同负载下 `cores_eff` ≥0.85 时的场/s 差 ≥10% | 若达标 10–16% | 低（只测量） |
| **P3** | 评估批量口径固化 | 训练侧 `--bench` 固定 200 场批量、报场/s + 负载 + `cores_eff` | 结论不再受负载污染 | 防再犯 | 低 |
| **P4** | 热路径「惰性触发」预研 | 仅**预研**：`triggerTime -= delta*speed` 是否有可折叠的等价批量推进 | 先出**等价性证明**，不出证明不写码 | — | **高（触 §2.1 红线：改帧内调用集合）** |

**P4 为什么排最后**：它数学上可能成立（每 tick 同速递减 ⇒ 可跳 N tick 直接到 `triggerTime≤0`），
但前提是「该物品的 speed/triggerTime 在这 N tick 内不被其他事件改写」——冷却缩短类效果（`adjustCooldown`）、
宝石联动、角色 buff 都会破坏这个前提。**没有等价性证明就动手，等于换内核**（§2.1）。
要做就按「先证明、再实现、1690 全量兜底」的顺序，且只在 P1/P2 都收口后才启动。

### 12.6 一句话

> 单场延迟**三个假设证伪两个**（并行效率是外部负载、`character()` 冗余 1.2%），
> 唯一落地的是 `load_for` 索引化（7.5 → 0.18 ms，41x，装配 −3 ms）。
> 剩余确定性空间只剩**装配 ~11% 里的 20–30%**（P1），以及**吞吐口径重建**（P2/P3）——
> 后者比前者更值钱，因为它决定此前的吞吐结论还能不能用。
