docs: §4.8 与第三方 C++ 版实测对比——单核快 1.86x、并行效率高 1.65x，合起来 3.04x

用户提供的 native_sim_cpp（C++20，libgdcore.dll，663 转译脚本，同一份 GDScript 而来）
实测对比，回答「它真快还是只因为线程多」。

测量前三条对齐（每条都踩过）：
  1. sys.path 必须 append 不能 insert(0)——bundle 里也有一份 simulator/ 副本
  2. 我方用 light_log=True——C++ BattleResult 只有 event_count 无事件列表（只计数不物化）
  3. 逐场 ABBA 配对——负载 65% 时 C++ 196ms、17% 时 109ms，不做交替会伪造 2x 假差距
语义对齐已证实：同 seed 下 tick 完全一致（907 / 1042）、胜负一致。

单场（逐场交替，10场x3轮，light 口径）：
  我方 203.1 ms  vs  C++ 109.4 ms  => 1.86x
  拆解：装配 46.9 ms(23.1%) + run 156.2 ms；C++ 装配 ~0（pack_side 缓存）
  => 装配是我方白付；run 段差距 1.43x

并行（C++ run_batch 用 std::thread + 每线程独立 BattleCtx）：
  1/2/4/8 线程 = 9.07/16.83/21.54/21.67 场/s（4 物理核饱和，8 线程无增益）
  我方 4 进程池 7.08 场/s，并行效率仅 1.44x（C++ 2.38x）
  差距分解：1.86x(单核) x 1.65x(并行效率) = 3.07x ≈ 实测 3.04x
  => 不是「只因为线程多」：单核就快 1.86x，并行效率再高 1.65x

我方并行只有 1.44x 的根因（已定位）：
  每个任务都 pickle 整个 lineup；668 个 .c 里 0 处 Py_BEGIN_ALLOW_THREADS（无 nogil）
  C++ 对应做法：pack_side 一次（约 0ms），之后每场只传指针

四条启示 N1-N4：
  N1 lineup 只传一次（worker 内按指纹缓存 pack，任务只传索引）
     —— S 成本，并行效率 1.44x 到接近 2x+，且不碰内核/语义
  N2 装配复用只读结构（描述符/几何；物品实例仍新建，RNG 必须消耗）—— 最多省 46.9ms
  N3 数据表示去 PyObject —— 对应内核 1.43x，即既有 G1 SoA
  N4 多线程 —— 不推荐（0/668 释放 GIL；强行 nogil 需全 C 化 object 槽，D1 已证只值 -0.8%）

N1 是这次对比才暴露出来的：我方内部测不出「序列化占多少」。
