## 1. 语料失效实证（run844 为例，run1018/1409 同型）

1. **幽灵物品不在装配里**：oracle 装配面 probe（`output/oracle/probe/np12_L2_val/probe_np12.gd`，
   基于 np9_L2/probe_gp_np9.gd 模板，产物 `asm_dump.txt`）对 run844 装配后全量 dump：
   `ASM P [Pine Protector] tl=(2,2)` 一件，**无 Spicy Banana**（双方侧同）。

   **(0,1) 在 lineups.json 里是 Pineapple、(3,1) 无物品**。语料 events 与其自身 lineups.json 冲突。
2. **ItemData 无产出配方**：oracle/Sheets/CSV/ItemData.csv 与 decompiled_full/Sheets/CSV/ItemData_e.csv
   中 Spicy Banana 无任何 recipe 产出者（仅 Spiked Shield 行含 `Pineapple>Pine Protector`），
   Banana 只有 `Mana Crystal*>Mananana`——战斗期也不存在"合成出 Spicy Banana"的合法路径。
3. **现树重放不复现**：`ORACLE_FIGHTS_ROOT=<probe>/np12_L2_val ORACLE_ONLY_CASES=run844_r11

   --script oracle_fight.gd` ⇒ probe events idx34 = `Flame Whip DealDamage`（无 Spicy Banana 治疗事件），
   且 **P 与 gd 痕迹前 1198 条逐位一致**——被 flag 的「Spicy Banana heal 3 缺失」在现树语义下不存在。
4. **重放确定性排除"抽签抖动"**：run1125 两次独立重放（ORACLE_DEBUG 与 ORACLE_STACKTRACE 各一次）
   events 前缀逐位一致（first_diff=None；总条数差 13395/18454 系 60s 墙钟闸
   oracle_fight.gd:745-748 与事件闸 25000（:749-752）截断点不同所致）。
   ⇒ 语料≠现树不是重放抖动，是**语料生成时的装配/语义与现树不同批**。
   语料文件 mtime（run844 18:34-18:35、run1018 18:41-18:42、run906 21:14、run1125 21:29、
   run1409 21:35，均为 2026-10-20）与 oracle 树 mtime（oracle_fight.gd 10-17、Core/Character.gd
   10-16、history.db 10-06）对不上生成批次——**具体由哪次运行/哪个状态生成无法在本阶段查明**。
5. run1018 语料幽灵：`Amulet of Light @6,2`、`Pine Protector @0,4`、`Amulet of Agility @8,2`

## 2. run906_r18 真缺陷（gd 真缺陷，根因已钉）

### 现象
C≡P：玩家 Eggscalibur @1.016667 伤害 12、对手 11；G：11/12 反接，且 t=1.0167 的
Mana Orb 首个 proc gd 落在 @3,5、oracle 落在 @5,5（idx6 起事件分叉）。

### 逐抽定位（oracle rng_log vs gd rng_trace，注入态后第 1 失配 = 玩家蛋首攻表现层块）
- oracle：`(0.9,1.1)×2 → (0.95,1.05) → (100,160)=122.34 → randf×2 → (-50,50) → (-70,70)
  → dir → randi_range(15,16)→16 → InBox×2 → (0.9,1.1)`（13 抽）
- gd：同前 4 抽后 **多出 `(0.9,1.1)×2 + pickRandomElement(0,2) + (0.8,1.2) + pickRandomElement(0,2)`
  共 5 抽**（playAttackAnimation 本体②+③），再 randf×2/pos/dir/roll（18 抽）
- 即：**oracle 玩家角色首攻时 attackMovingForward 已闩死（跳过本体，只耗默认实参
  (100,160)），gd 未闩死（全本体 +5 抽）**。链移位后伤害 roll 值 15(→甲减 11) vs 16(→12)，
  Mana Orb 双球的 roll/序随之翻转。

### 根因（file:line）
- oracle 真源：`oracle/Core/Character.gd:446-462` playAttackAnimation（默认实参先抽 (100,160)，
  `if attackMovingForward: return`，本体抽 2×时长+挥击音 pick+音高，尾置 `attackMovingForward=true`）；
  `:467-481` playActivateAnimation 同旗标；`:484` dealDamage 先 playAttackAnimation。
  **旗标复位只靠 attackMovingBack 的 tween 回调（真机 ~0.3s）**——受控神谕阻塞 tick 循环里
  tween 不推进 ⇒ 一旦置真**全场闩死**（gd 侧同约定注释：`gd_core/CoreCharacter.gd:484-495`）。
- **闩死的初值差**：`oracle/oracle_fight.gd:306` `var warm = run_case(cases[0], true)` —— 批进程先
  跑一场**同种子暖场**，而 `G.PLAYER` 节点跨场复用（`instanceCharacter` 仅职业切换分支重建，
  oracle_fight.gd:570-577；`G.OPPONENT = G.opponentScene.instance()` 每场新建，:610-618）。
  ⇒ 真场开打时**玩家角色旗标=暖场同场重放后的残留 true，对手=新节点 false**。
  实测印证：oracle 玩家首攻跳本体（闩死）、对手首攻（seg9）反而全本体（含 pick(0,2)/(0.8,1.2)）。
- gd 侧：`gd_core/CoreCharacter.gd:513-527` playAttackAnimation 逐抽同构，但
  `attack_moving_forward` 每场新建恒 false（CoreCombat 逐场新建双方角色），且
  `attackMovingForward_reset()` 为空操作（:406-408），**无"玩家开局即闩"的等价初始化**。

### 可能解法（阶段2，改前备份到 output/_round_patches/np12_L2/）
- 方案 A（贴 harness 约定，最小面）：gd_core_probe/OracleAlignBattle.gd 装配后把
  **player 侧** `attack_moving_forward = true`（等价暖场残留）。⚠ 该文件不在本轮允许改面，
  需走夹具面授权或由夹具 owner 执行。
- 方案 B（内核面，在我可改面内）：`gd_core/CoreCharacter.gd` 按 playerId 初始化
  （player=true / opponent=false）。⚠ 把 harness 暖场残留固化进内核，属约定级补丁，
  须 REG（run570_r18…run1514_r18 9 场）全绿才保留；REG 由脚本统一跑（本轮禁自跑）。
- 无论 A/B：只影响"玩家首攻"一次共 +5 抽的链位，之后双侧闩死同构。

## 3. run1125_r18 真缺陷（gd 真缺陷，现象/输入面已钉，oracle 内部双退机制未闭）

### 现象（idx47-50，t=1.25）
- C（语料）：`-11 → Amulet +3 → Amulet +3 → Chili Heat 1`
- P（现树重放，两次重放一致）：`-11 → Amulet +2 → Amulet +3 → Chili Heat 1`
- G（gd）：`-11 → Amulet +3 → Chili Heat 2 → …`（**单退**；heat 2v1 是退回笔数差导致的
  链移位——Chili 的 Owl Spirit 放大 roll（CoreBuff.gd:169-176 totalResistChance<0 分支）
  从不同链位取值）

### 已证事实
- 退回算法面（双源同文）：`oracle/Items/Exclusive/AmuletofAgility.gd` onBuffChanged：
  `usedStacks[type] += used*refund; toRefund=int(round(usedStacks[type])); if>0 {usedStacks-=toRefund; giveStacks(...)}`；
  gd `gd_core_items/Exclusive/AmuletofAgility.gd` 同文。refund 实测 0.25（probe FOCUS dump
  `aoa refund=0.25`）。单次 -11、初值 0 ⇒ 首退必为 round(2.75)=3（**gd 的 +3 与语料一致**）。
- oracle 的 +2/+3 数学上要求 usedStacks[Mana] 事前 ∈ (-1.25,-0.25)（如先有一笔 used=2 的
  退回留 -0.5），**但 P 事件流 idx48 前无任何 Amulet of Agility 退回事件**——oracle 内部
  在何处产生第二笔/首笔 +2 的交付，**本轮未能钉到行**。
- 连接面排除双连：装配 probe CONN dump（EventBus.connections 直读，FuncRef.get_function 解码）：
  `CONN P-CHAR sig=character_mana_changed n=3 methods=[onManaChanged,onManaChanged,onBuffChanged]`
  ——onBuffChanged 仅 1 连（`oracle/Utility/EventBus.gd:110-121` connectEvent 无去重，
  但此处也没有重复连接）。
- 单 emit 面：`oracle/Core/Buff.gd:292-320` changeCurrentLogShowLabel 每 lose 恰一次
  `EventBus.emitEvent(character, signalName, …)`；gd `gd_core/CoreBuff.gd:398-432` 同构。
  `oracle/Core/Character.gd:1287-1290` useMana→useStacks 单调用；EventBus.emitAndLog
  （:56-77）遍历数组期间数组不增长。**静态读码未找到第二交付点。**
- rng_log 旁证：`SRC gain_label Amulet of Agility @t=2.000/+3.000`、`SRC lose_label
  Eggscalibur @t=-11.000`（-11 的标签在两笔退回之后才落）⇒ 两笔退回都在 -11 的
  emit 处理内同步完成，之后才是 -11 自己的标签。

### 可能解法（阶段2 前置条件）
- 需先闭 oracle 双退机制（建议下一步用 ORACLE_STACKTRACE 的调用栈列——本轮该列实测为空，
  get_stack() 在 headless 下返回 null，Util.gd:762-774；可改用临时 BCON/BUS 全信号标记或
  对 Buff.changeCurrentLogShowLabel 加一次性计数桩——**都在 oracle/ 只读面内，本轮不可为**）。
- 机制未闭前**禁止盲改 gd**：gd 现值 +3 与语料一致，若 oracle 双退是语料生成后 oracle 树
  演化的新行为，改 gd 反而制造新的三方分裂。判据不放宽 ⇒ 先定语义源，再动码。
